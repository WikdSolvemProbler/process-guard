# Security policy

## Supported versions

Security fixes are made for the latest release only. Update to the latest release before reporting.

## Reporting a vulnerability

Report vulnerabilities privately through GitHub's private vulnerability reporting: open the repository's **Security** tab and choose **Report a vulnerability**. Do not open a public issue for a vulnerability.

Include the release or commit, the Windows version, the exact command line or hook payload, what you expected, and what happened. A minimal reproduction is the most useful thing you can send.

## In scope

- A process that escapes the job object, or that survives the deadline or the exit of the process that launched the guard. This holds against commands that do not act against the guard on purpose; a hostile process of the same user inside the job can do the things listed under Known behaviour, which are not vulnerabilities.
- A command that passes the hook mode envelope check without being exactly the documented envelope. The envelope may name the executable the hook runs from, or the same executable under its other name (`process-tree-guard.exe` and the 1.x alias `process-guard.exe`) in the same folder; a path in another folder or in another letter case that passes is in scope.
- A hook mode denial that does not exit with code 2 because a standard stream cannot be written (Common Weakness Enumeration, CWE-636, failing to fail securely): the host reads any other status as a non-blocking error and lets the command run.
- A command that passes the envelope check of the hook role (`process-tree-guard-gate`) without naming `process-tree-guard.exe`, `process-guard.exe` or `process-tree-guard-deadline.exe` in the gate's own folder or in the `bin` folder beside a `libexec` folder (the folder name `libexec` is read in any letter case); the gate itself is never a valid envelope, under whatever file name it is installed and in whatever letter case it is started.
- A Google Antigravity `run_command` call that reaches the shell through `hook antigravity` without being wrapped, exactly guarded already (the wrapper form of either name beside the guard, or an envelope of either name), or denied.
- A file used by a program that was found through `PATH` or the current folder instead of relative to the program's own location: the automatic copy a hook rewrites to, or `POLICY.md`.
- Malformed input to the hook's JavaScript Object Notation (JSON) parser or the Base64 decoder that crashes the guard, hangs it, or changes its decision.
- Argument or shell quoting that runs a different command from the one given.
- In an extendable run (`--extendable`, see the README), the channel that the processes in the job use to ask for more time:
  - A request granted to a process that is not alive, is not in the guard's job, or started after it connected; or a hold that outlives its process, or that is kept by a process identifier and so can pass to an unrelated process; or a hold made for a library call (`run`, `run_shell`, `run_auto`) that outlives the call; or a hold that stands for longer than half a second after its client was left without the reply that grants it.
  - A deadline of the run that is later than the latest of its own `--timeout` deadline and the holds of live processes, a hold or a nested guard's start that exceeds `--max-extension` without being refused (exit code 125 for the guard), or a cap that anything but the guard's own launch arguments can change.
  - A change of the deadline, or a hold, that is not in the log; a grant made in a run with no `--extension-log` whose line was not written to standard error, or in a run that started with a standard error that is closed or is the null device; an `--extension-log` that names a device or a pipe and not a file on a disk (the run does not start); a grant made while the audit file named by `--extension-log` cannot take its line (one that cannot be written, or cannot be turned over and has less than 64 kibibytes (KiB) left before twice its limit), other than the lines that were on their way when it became so; a value that can end a log line or start a field of its own (Common Weakness Enumeration, CWE-117); or a log file that grows without the bound of one mebibyte (MiB) and one rotation, or that discards its earlier lines without a line in it saying that its turn over failed.
  - The channel reached by another machine, or by another account on the machine; a second instance of the pipe, or its name predictable.
  - A request that makes the guard hang, crash, or miss its deadline, including a request that is granted after the deadline has passed; a message of a size other than the fixed ones that is not refused; a log destination (a standard error that nobody reads, the audit file) that keeps the tree from being ended or the guard from returning; a client that waits for ever for a reply.
  - A request that reaches the run and is not in its log (other than the refusals the log coalesces and counts), or a flood of refusals, from one process or from processes outside the job, that pushes earlier lines out of the log. (A flood of grants from many short-lived processes in the job is known behaviour; see below.)
  - A client of the channel (`extend`, the start of a nested guard, the library call `extend`) that crashes, hangs, or reports a grant on a reply whose numbers are out of range, in place of refusing it with a reason (Common Weakness Enumeration, CWE-248 and CWE-20).
  - A client outside the job that keeps the channel from serving the processes in the job.
  - A guard started inside an extendable run that is not held to the run's cap; an extendable guard in a job that is not extendable that outlives the outer deadline; the contain role running a command with no extendable run around it.
- The exception above the cap (`--max-extension` over 21600, see the README), which needs the signed-in user's password at the start of the run:
  - A run with a cap over the default that starts its command without the password having been checked as the signed-in user's (`LogonUserW` accepting it, and the security identifier of the logon token equal to that of the guard's own token), or without an `exception-approved` line in the log (a run whose approval could not be recorded does not start, and a refusal is an `exception-refused` line).
  - A prompt shown, or a password asked for, by the contain role, or by automatic mode (which refuses the options) or the hook program (which does not ask: it denies a line that carries the options, or wraps it whole as the command text of the automatic wrapper; the guard that the wrapper then runs was started by a guard and is refused before anything is shown), or in a run inside an extendable run (refused as nested, before anyone is asked), or in a run that another guard started (refused before anything is shown); a desktop prompt shown by a process with no interactive window station or in session 0; a console prompt answered from a standard input that is not a console (a pipe, a file, the null device); more than 3 attempts in one run; a prompt opened beside another prompt of the guard in the same session; a prompt left open, or answered for, after the process that started the guard has exited; a stub, or a way to skip or answer the prompt, in a program that is released (an argument, an environment variable or a file). A guard that is started as the command of automatic mode, or under a guard that is not extendable, was started by a guard and is not asked; the refusal is made by two tests. The first is by file name: the live processes above the guard that its search reaches, nearest first, are looked at for a program of the guard and for any file name ending in `-auto`, which selects automatic mode; the search follows the parent chain while each parent is alive, started before its child and is not one of `explorer.exe`, `services.exe`, `wininit.exe`, `winlogon.exe`, `svchost.exe` or `smss.exe` at its system path (`explorer.exe` in the Windows folder, the other five in `System32`; a program of one of those names in any other folder, one under the Windows folder included, is a copy that a process of the user may be able to make, and is walked past like any other process), for at most 32 levels, and a parent that has already exited ends it, so a command started through a launcher that exits before the guard runs is not seen to be under a guard by this test, and a launcher can name a parent of its choice. The second is by job: every job a guard makes kills its processes when it closes, so a process whose innermost job does so is refused, however its chain of parents looks, unless the process has put itself in a job of its own, which any process of the user can do with three calls (nested jobs are allowed, and the test programs of this repository do it); the test refuses commands that were not written to avoid it; this also refuses any guard started from inside a host that puts its terminal in a job of that kind (continuous integration runners, some editor terminals), which then cannot use an exception and must start the guard from an ordinary terminal. An agent that runs as the same user outside a guard job, that puts its own process in a job of its own (a nested job replaces the innermost job that the job test reads) and starts the guard from a process whose parent has exited, or that can set its own parent, can still summon a prompt; the password is still required. The weaknesses at stake are the Common Weakness Enumeration entries CWE-799 (improper control of interaction frequency) and CWE-307 (improper restriction of excessive authentication attempts). A copy of the guard under a file name that does not end in `-auto` is not recognised by the first test, and making one is possible only for a process of the same user, which this document does not defend against.
  - A password, or the buffer that holds it, that is logged, echoed, put in a string or left unzeroed on a path the guard controls (Common Weakness Enumeration, CWE-316, cleartext storage of sensitive information in memory, and CWE-532); a command line in the prompt that can forge or reorder the text around it (CWE-451, CWE-117), or that is not bounded; a wait of the prompt or of the check of the credentials that has no end; an empty password that approves; a logon tried for a name that is not the account the guard runs as.
  - The lockout of the exception (see the README): a run over the cap that shows a prompt, or asks for a password, for an account that is locked out; a wrong password (a refusal by `LogonUserW` of a password that was not empty, for the account the guard runs as) that is not added to the record before the next attempt is made; a lockout that a correct password, a cancel, a record the guard adds or an attempt while locked ends, shortens or extends; a record, or the folder it is in, that a program of the account without administrator rights can rewrite, shorten, rename, replace or delete, whose permissions or owner it can change, or in which it can make a file; a record that is followed through a link, or that has a second name, and is used; a run over the cap that goes on when its record is missing, cannot be opened for reading and appending, allows more than that, or is not owned by the Administrators group, the system or the installer of the system (as are not the folder of the records, the folder of the programs' data and the folders above it); a lockout that starts while a prompt is open or a wait goes on and does not stop the run before the next prompt and before the logon; a location of the record that the account controls (an environment variable, the profile of the account, the known folder interface, a drive letter that the account has mapped to a tree of its own); a record whose size, or whose garbage, can end or shorten a lockout; a failure of `create-lockout-record` that is not reported, or a folder that the step takes over from an owner other than the Administrators group, the system or the installer of the system. The weaknesses at stake include CWE-307, CWE-367 (time-of-check time-of-use race condition), CWE-59 (improper link resolution before file access) and CWE-732 (incorrect permission assignment for critical resource).

## Out of scope

- Commands that were never routed through the guard. The guard bounds what runs through it; see the Limits section of the README.
- Work on remote machines, in containers or in Windows Subsystem for Linux (WSL).
- Actions by a user who already has administrative rights on the machine.
- Actions by a hostile process of the same user inside the job, such as suspending the guard or asking a system service to start a process outside the job; see Known behaviour. Such a process can also put itself in a job of its own (three calls; nested jobs are allowed), and is then not refused by the job test as a run that another guard started.
- A deadline of up to 24 hours without `--extendable` (`--timeout` takes at most 86400 seconds), and renewal without end by a run at the default cap or below, need no password. The password gates only a `--max-extension` over 21600, which is the size of one request; it is not a limit on how long a run may last.

## Known behaviour

- Extendable runs: access by another process of the same user is not a security boundary. The name of the channel is in the environment of every process in the run, and a process of the same user can read it, or the memory of a process that has it. What limits such a process is that the guard verifies it before it answers (alive, in the job, started before the connection), the cap on every request, the rate limit (12 requests per process in 10 seconds), the limit on holds (256, and 8 for one process) and the log. A same-user process outside the job is refused and logged for its first 12 connections in a window, and disconnected at once after that. The log is an audit record, not a control.
- Extendable runs: any verified process in the job can hold the deadline up, and can replace the hold of its parent through the `extend` program, which asks for the process that ran it. A chain of requests, each within the cap, keeps a run alive for as long as a process keeps asking: renewal without end is the intended mechanism, and there is no limit on the whole life of a run. Each request is capped, in the log and made by a verified process in the job, at every moment the deadline is no more than the cap ahead, and a run whose processes stop asking, or hang, ends at the latest hold. A launcher that wants a run to end by a given time sets `--max-extension` and `--timeout` to it, and a run that nothing renews ends at its `--timeout`.
- Containment is not a boundary against a hostile process of the same user inside the job (Common Weakness Enumeration, CWE-693, protection mechanism failure). Such a process runs with the rights of the user that started the guard, and can do what that user can do to the guard and to the system: open the guard and suspend it (`SuspendThread`) or write to its memory, so that the deadline is not checked or is changed; duplicate a handle to the job; and ask a service of the system, such as Windows Management Instrumentation (WMI, `Win32_Process.Create`), the Task Scheduler or a Component Object Model (COM) server, to start a process, which belongs to that service and not to the job, and so survives the kill. The guard prevents a process from using `CreateProcess` to leave the job, and ends every process that stays in it. The statements in the README and above, that nothing survives the deadline and that a deadline moves only by a logged request, hold for commands that do not do these things on purpose: tests that hang, servers left running, descendants that outlive their parent, the ordinary commands of an automated agent. A host that must resist a hostile command runs it as another user, in a container or in a virtual machine; the guard is not that. The guard process's own access list is not hardened against the same user.
- Extendable runs: the table of holds has 256 places, and one process can hold at most 8 of them, all its holds together whatever their numbers; a ninth is refused with "this process holds too many deadlines", so a single process cannot take the table from the rest. Processes of the job can still fill it between them, each within its 8 and its 12 requests in 10 seconds (32 processes are enough): every other request, and the start of every nested guard, is then refused with "too many processes hold the deadline" until those holds end, each at most the cap from its grant and at the latest when its process exits. That is a denial of the channel to the processes of the run by processes of the run; it never moves the deadline, and every grant is in the log.
- Extendable runs: the client and the run agree about whether a hold exists. The guard sets a hold, then sends the reply and waits half a second (a quarter of a second for a process over its share) for the client to read it; the pipe has no outgoing buffer, so the write completes only when the client has read the reply. A client that sends a valid request and reads later than that gets an error and no reply, and the guard withdraws the grant: the hold goes back to what it was before the request, the deadline is recalculated and the log has a `decision=withdrawn` line after the `granted` line. A nested guard that did not get its reply exits with 125 and runs nothing, and `extend` exits with 125. A reply to a release that is not taken leaves the hold ended, which is what the client asked for. The window between the grant and the withdrawal (up to half a second) is the only time the run holds a deadline that its client was not told of, and the hold in it is within the cap and in the log.
- Extendable runs: the channel is four instances of a pipe, each served by a thread of its own. The guard settles who a client is before it waits for its message; a client outside the job that has used its allowance (12 connections in 10 seconds, all such clients together) is disconnected at once, with no wait and no reply; any other connection costs an instance at most a quarter of a second to send and half a second to take the reply (a tenth of the first, and a quarter of a second for the second, for a process in the job that is over its share), and a connection that sends nothing is charged to its share and logged. A process in the job can still stall: a handful of processes that connect and send nothing, or do not read the refusal, can keep all four instances busy, and another process's request then waits, up to the five seconds a client waits for the channel, and fails. That is a denial of the channel to the processes of the run by a process of the run; it never moves the deadline. The deadline of the run is never delayed by a client. A client waits at most five seconds for the reply and gives up with a reason if the run does not answer. A standard error that nobody reads blocks neither the answers nor the deadline: the log is written from bounded queues by threads of its own, a full queue drops lines (and a notice counts them), the tree is ended before the guard writes anything to standard error, and the guard's own notice is abandoned after half a second.
- Extendable runs: a process in the job can turn the log file over within minutes. Refusals are coalesced (the first of a process for the rate is a line and opens a window of 10 seconds, the rest of that window one line with a count, written when the window ends, also while the process goes on asking, after which the next refusal opens a window of its own; the count of the window that is open when the guard is killed is lost; all clients outside the job count as one process) and at most 24 refusal lines are written in any 10 seconds, so refusals alone cannot do it. Grants are not budgeted: each is a line of its own, a process is limited to 12 per 10 seconds, but processes are cheap, and one that starts many short-lived processes, each asking once, writes the file and its one rotation full in a few minutes (a fast spawner needs about a minute), and every earlier line, the refusals among them, is gone from both files. The bound of one mebibyte and one rotation is a bound on disk space, not a promise to keep lines. The file is evidence of what happened before such a flood only if it is copied off the machine promptly (read it while the run goes on, or keep the run short). The guard and the processes in the job run as the same account, so they can also open the file, append lines in the form of a grant, and delete or replace it; see the next items.
- Extendable runs: a library call (`run`, `run_shell`, `run_auto`) made inside a run is a nested guard in a process that goes on, so its start asks the run for its `seconds` with a hold on the calling process, and the hold is ended when the call returns, by a release request that is a line of its own in the log (`decision=released`). A call returns only after its release has been answered, so it can wait up to the five seconds a client waits when the run does not answer; a release that does not arrive leaves the hold to run out or to end with the process. A release is let past the rate limit when it ends a hold, and is counted like any other request when it finds none. Each call is one request against the 12 per process in 10 seconds, so a host that makes more than 12 calls in 10 seconds inside a run is refused for the rest, with the reason, and the command does not run; each call has a hold of its own, named by a number in the request and in its release (the hold of `extend` is another), so calls that overlap, from threads of one process, do not replace or release one another's holds, and the run waits for the latest of them, each no more than the cap from its grant. The program (`process-tree-guard`, in any role) is not affected: its hold ends with its process.
- Extendable runs: the audit file is turned over by renaming it to `PATH.1`, and a program that follows the file and holds it open without `FILE_SHARE_DELETE` (PowerShell `Get-Content -Wait` is one) stops the rename. The earlier lines are not discarded for that: the file is copied to `PATH.1` and emptied instead, and when that fails too the file grows past one mebibyte, toward twice that, with a notice in it that the turn over failed; the guard tries again once a second, whether or not a line comes, and standard error has every line. `PATH.1` is not held open by the guard, and any process in the job can stop both ways of turning the file over by opening `PATH.1` for reading and sharing reading only (read access is all it needs, and it is the default of .NET's `File.OpenRead`); no setting of the folder prevents that. The run does not carry on and lose lines for it (Common Weakness Enumeration, CWE-778; National Institute of Standards and Technology (NIST) Special Publication (SP) 800-53 control AU-5, response to audit processing failures): when the file cannot be turned over and has less than 64 KiB left before twice its limit, or when its lines cannot be written, the run grants nothing. Every request that would move a deadline is refused, with the reason that the audit file cannot take lines, until a turn over or a write works; deadlines already granted stand, so the deadline never moves later without a line. A run started with a file that is past its limit, cannot be turned over and has no such room does not start (125). The 64 KiB is room for the lines on their way at that moment; a grant is in the file unless more than that was queued behind it. A collector that follows the file should open it with `FILE_SHARE_WRITE` and `FILE_SHARE_DELETE`. The guard holds the file open for appending for the whole run, so a reader that does not share writing (the default of .NET's `File.OpenRead` and `FileStream` for reading, which share reading only) is refused when it opens the file, and cannot make the guard's appends fail by holding it; a reader that opened the file before the run began stops the guard at its start, with 125. A write that fails all the same (the folder went away, a handle opened by another route) is not silent: the guard tells standard error at once, keeps the lines (up to 256), tries again every half second, writes them in order when the file takes lines, and then puts a notice with the counts in the file and on standard error; lines past the 256 are counted in it, and the end of a run says how many lines the file never got. A process that can only read the file can hold it open, but it cannot erase lines by doing so; with the file held open by the guard it cannot make the appends to it fail, and a write that fails is recorded by those notices and stops the grants as above (standard error has every line either way). The file is evidence only against a process that cannot open it. A process in the job runs as the same account as the guard, opens the file with the guard's own access, and can append a line in the exact form of a grant, or delete or replace the file; a folder that the job cannot write to is one that the guard cannot write to either, so no setting of the folder prevents it. Rely on the file only where a boundary of another kind keeps the command from it (the command runs as another user, in a container or in a virtual machine) or where a collector ships the lines off the machine as they are written; copy it off the machine promptly in either case.
- Extendable runs: the table that tells processes apart for the rate limit holds 1024 live processes. A process that has exited is forgotten when the table is full, so any number of short-lived processes can ask in turn; a new process is refused, with a reason of its own, while 1024 others are live.
- Extendable runs: when there is no audit file, standard error is the only record, and the guard holds its grants to it. A run does not start when standard error is closed or is the null device and `--extension-log` was not given; a grant is made only once its line has been written to standard error (the guard waits at most half a second for the write, and takes the grant back with a `withdrawn` line and the refusal "the audit file (or standard error, when there is no audit file) cannot take lines" when it fails or does not finish); and after a write has failed the run grants nothing until one works. The guard cannot tell a standard error that is a pipe or a file whose reader keeps nothing, or reads and discards, from one that records, so the rule that a deadline moves only by a logged request holds without `--extension-log` only as far as the launcher's standard error is kept. A launcher that needs the log as evidence, and not only a refusal where nothing can be written, passes `--extension-log` and reads the file, on the terms of the item on the audit file above.
- Extendable runs: a process in the job shares the guard's standard error and can print a line in the form of a log line. The copy of the log on standard error is not evidence. The file named by `--extension-log` is better evidence, but only on the terms of the item on the audit file above: a process in the job can write to it too.
- Extendable runs: `process-tree-guard extend` holds the process that ran it. Under Git Bash that is the shell that made a short-lived copy of itself to run the program, found by looking through copies of `bash.exe` or `sh.exe` with the same image path; a launcher that is not recognised, and that runs the program through an intermediate process that ends with it, holds that process, and the hold ends with it. The library call holds the process that makes it.
- Extendable runs: the deadline is measured with `GetTickCount64`, which counts the time the machine is asleep and does not follow changes of the clock.
- Extendable runs: the check that a client started before it connected compares its creation time with the system (wall) clock, and the time it compares with is when the thread that serves the instance of the pipe noticed the connection, taken as soon as its wait returns, not the instant the client connected. A process that took the identifier of a client that had connected, written its request and exited, and was created in the gap between the connection and that moment, is not told apart by the comparison (Common Weakness Enumeration, CWE-367 and CWE-362). The gap is the time the serving thread took to run: short on an idle machine, tens of milliseconds or more under load, and the whole time since the connection when the client connected before the thread was waiting. Windows reuses process identifiers readily. The guard closes that gap with a second check, made after it has read the request and before it decides: it asks the pipe whether the client's end is still open (`PeekNamedPipe`), and a request whose end is closed is refused as not verified. A client waits for its reply with its end open, so a client that wrote and exited has closed its end, and the process that took its identifier is refused whenever it was created. What remains is a client that gave a duplicate of its end to another process before it exited: the end is then still open, the check passes, and a process created inside the job in the gap with the client's identifier can be taken for the client; it would get the client's hold (within the cap, in the log, ending with that process), its share of the rate and the log line. The client would need a second process that stays, and the identifier to be reused inside the gap. A step of the system clock backwards across the start of a client makes its creation time later than the connection time, and the client is refused as not verified, which is logged; the deadline is not affected.
- Extendable runs: a value of `PROCESS_TREE_GUARD_CHANNEL` that is not the name of a channel, or names one that is gone, is read as no run around the guard: the guard keeps its own fixed deadline and runs its command, as before extendable runs, so no setting of that variable (a user or project environment setting, a stale shell) can stop the guards of a host from running commands; `extend` and the contain role refuse it, since they have no run to ask. A value that names a pipe that is there and is not an answering run (one that stalls, or answers with something that is not understood) ends the guard that reads it with 125, which is a denial of that one command to a process that can set the variable in the guard's environment; it cannot give the command more time.
- Extendable runs: a client does not check which process serves the channel. A process that can set `PROCESS_TREE_GUARD_CHANNEL` in the environment of a client can point it at a pipe of its own. The client accepts a reply only when it is well formed and its numbers are in range (finite seconds from 0 to 86400, a time that a clock can show) and refuses anything else with exit code 125. A reply from such a server can make `extend` report a grant that no run made; it cannot move the deadline of any run, which is held in the state of the guard that owns the job, and the process that reported it stays bounded by that job.
- An extendable guard in an extendable run asks the outer run for its own deadline and then serves a channel of its own. Holds granted by the inner channel keep the inner tree alive only while the outer run holds the inner guard, because the outer run ends the whole job at its deadline.
- The exception above the cap resists accidents and agents that do not have the password. It does not resist an attacker who runs as the same user and can tamper with the guard process: such a process can suspend the guard, write to its memory, patch the check, or start its own copy of the guard with the check removed, and the signed-in user's password is typed into a program that this attacker can impersonate or alter (National Institute of Standards and Technology (NIST) Special Publication (SP) 800-63B, verifier impersonation resistance). The prompt itself is in scope: the flaws listed above are vulnerabilities, and a same-user attacker's tampering with the guard is not. The exception is a deterrent and a record, not a boundary against that attacker. A program of the account does not need to tamper with the guard to guess the password: it can call `LogonUserW`, `runas` or `net use` for the same account itself, and those tries are counted by the account lockout policy of the system and not by the lockout of the guard. A host that must resist one runs the command as another user, in a container or in a virtual machine, and the guard itself must stay with the signed-in person: the password is that of the account the guard runs as. If the guard runs as an account that the agent also runs as, or whose password the agent can obtain (a service account, or `runas` with a stored password), the exception gives no protection against that agent. The approval is of the text shown, not of the content of the program, which can change between the prompt and the start. A run that sits inside a job with a shorter deadline that the guard did not recognise as a guard (see the two tests described under In scope) ends with that deadline, whatever cap was approved. The parent that the prompt names is chosen by the launcher and can be made to name another process (a process of the same user can name a long-lived parent such as `explorer.exe` when it starts the guard), so the list is information, not proof of who started the run.
- The exception above the cap: what the password is checked with, and what it costs. `LogonUserW` is called with the interactive logon type, which is the check Windows sign-in makes.
  - Logon type and cost. The logon itself works with cached domain credentials. The cost is a logon session (event 4624, logon type 2), which the guard ends at once by closing the token, and the interactive logon type caches the logon information as a sign-in does. Each wrong password writes a failed-logon event (4625) on the machine, or on the domain controller for a domain account, and counts toward the lockout threshold, which writes a lockout event (4740); monitoring will see them, at most three per run. Three attempts per run can equal the lockout threshold of a hardened machine: where the threshold is 3 or fewer (the setting of the Defense Information Systems Agency (DISA) Windows Security Technical Implementation Guide (STIG)), one run in which three wrong passwords are typed locks the account out of Windows, and for a domain account the failures also count toward the threshold of the domain; set the threshold to at least 5 on the machines that use an exception, or enter the password with care. The password is that of the account the guard runs as (the signed-in user in the usual case).
  - Name forms. The look up of the name that comes before the logon is local when the name is the guard's own account name as the system writes it (read with `GetUserNameExW`); a name in another form (a user principal name of a domain account) may contact a domain controller, and where none answers the run is refused with the error of the system. An approval with the domain controller out of reach is not asserted by the tests (the manual check has a step for it), and neither is the form of the user name that comes back for a Microsoft account or for an Azure Active Directory (Azure AD) account (`AzureAD\Name` is split into the domain `AzureAD` and the user `Name`; the guard may refuse a right password if the system does not take that form, and each try counts toward lockout; the manual check records it).
  - Names that are not the guard's account. A name that comes back from the desktop prompt, or is typed at the console prompt when the guard cannot read its own account name (the console prompt otherwise shows the guard's own account name and asks for the password alone; the name cannot be changed there), is looked up before any logon is tried, and a name that is not that account is not tried, so a guess does not count toward the lockout of another account. The reason given is the same text for an unknown name, a wrong password and another account's, and the log does not tell them apart. An empty password has a reason of its own, since it is not a secret and no logon is tried for it, so that the log does not record a rejection by the system of a credential that was never sent.
  - Errors that give a guess away. An account that lacks the right to log on locally cannot approve: the check fails with 1385 (or 1380, which has the same text) and the run is refused. Some errors of the logon (1327, 1328, 1329, 1330, 1331, 1380, 1385, 1793 and 1907) are returned by Windows only for a correct password: an account restriction (1327), invalid logon hours (1328), an invalid workstation (1329), an expired password (1330), a disabled account (1331), an account without the right to log on at this computer (1380 and 1385), an expired account (1793) and a password that must be changed (1907). A refusal that named them would tell a program that drives the console that its guess was right (Common Weakness Enumeration, CWE-204, observable response discrepancy; NIST SP 800-63B section 5.2.2). At the console prompt they are therefore given the reason of a password that is not accepted, in the error and in the log, and each uses an attempt and is counted toward the lockout of the guard as a wrong password (below): if it were not, three wrong passwords would end a run with a lockout and a right password with one of these codes would not, and a program that reads the refusal, or the record, which the account may read, would learn the same thing the masking hides. They cannot approve in any case. Only at the desktop prompt, which a program cannot answer, is the error shown, and nothing is counted for it. A locked out account (1909) is given whatever the password, and stays named.
  - Attempts and waits. Each failed `LogonUserW` counts toward the account lockout policy of the system, and a wrong password also toward the guard's own lockout (what counts is described under "The rule" below), so a run is given at most 3 attempts. After a name or password that was not accepted the guard waits 2 seconds before it asks again, so that a loop of guards that guesses pays for every try; that slows such a loop and does not stop it. Each attempt waits up to 300 seconds and the check of the credentials up to 60, so a run may wait up to 1126 seconds, a little over 18 minutes (3 prompts of 300 seconds, 3 checks of at most 60 seconds, 2 waits of 2 seconds, 10 seconds in all for the reads of the lockout record, 2 seconds for each of the 3 locks of the record, 5 seconds for the name of the account and, with the console method, 5 seconds each for the write of the message and for the notices of the wrong passwords on record that are written before an attempt (at most three), and half a second for the record of the approval on standard error), before it starts; the run's own deadline starts after the approval.
  - Prompts that stack and a loop of runs. The limit of 3 attempts is per run; the lockout of the guard (the third wrong password within six hours locks the prompt for the account for six hours, described below) limits the wrong passwords given to the guard across runs, and a program of the account that tries the password itself is limited only by the account lockout policy of the system, but an agent that starts runs over the cap again and again can still lock the account out of Windows where the system's threshold is low, and can fill the user's screen with prompts, each of which waits up to 300 seconds. The guard refuses to open a prompt while another prompt of its own is open in the same session, and for 10 seconds after a refusal that followed a prompt (the right to a prompt is kept for that time before the guard returns, and a starter that has exited cuts it short; a prompt that was left open for 300 seconds is refused and the guard exits at once, with no such wait, so that the dialog or the console read is left to end with the process and nothing typed into it is lost to a run that is already refused), which keeps them from stacking and slows them following one another, but does not stop a loop of runs from opening a prompt every 10 seconds or so. The lock that keeps two prompts apart is a named object of the session (`Local\ProcessTreeGuardPrompt`), so a process of the same user that holds that name keeps every run over the cap in that session from asking, and those runs are refused ("another sign-in prompt of the guard is open or was refused less than 10 seconds ago, or another program holds its lock name"); that denies the exception and approves nothing. A guard that an agent starts as a command, under automatic mode or under a guard that is not extendable, was started by a guard and is refused before any prompt, lock or logon ("an exception above the cap is not asked for by a run that another guard started", with `attempt=0`), so in a host whose shell commands are all wrapped, an agent that runs a guard with a cap over the default as a command does not, while the two tests hold, start a prompt or use the console method as a way to guess the password, unless it avoids the two tests as the next sentence says. This depends on the commands of the agent being started by a guard and being seen to be (the two tests are described under In scope): an agent that can open a terminal of its own that is not under a guard job, that sets its own parent, that puts itself in a job of its own and leaves an intermediate process to exit, or that leaves an intermediate process to exit and runs outside a guard job, is a process of the same user, which this document does not defend against. The reason of that refusal names the cause, either the file name of the program found above the guard or the job that kills its processes when it closes, so that a refusal can be traced to the test that made it.
  - The text of the prompt. It puts first what the person must check, in this order: the command line, the program, the account whose password it asks for and the parent process as the system reports it (the nearest one); after them it says what the cap means (the size of each request of the processes of the run, which may renew without a total limit, in hours rounded up to two decimals with the seconds beside the figure when it is not exact), the deadline the run starts with, and how to refuse. A dialog that clips or scrolls long text loses its end first, so the end is the explanation and not a field that a launcher influences. Each field is framed in square brackets, in which no bracket can occur, and is cut to a limit of its own once written out (the command line 140 characters, the program 80, the account 40, the parent 80; the command line keeps its start and the others keep their end, which holds the file name or the user), with a count of what was cut, so that the whole message stays under 1,024 characters, the limit of the dialog; a longer message would refuse the run rather than reach the dialog. Every character that is not printable basic Latin (the letters and digits of other scripts, which can look like Latin ones, such as a Cyrillic o for the Latin o; the blanks and spaces of other scripts; the marks that stack over the text; the control and format characters) is written as `\u{..}`, and the message says so when a field has a character outside basic Latin.
  - Answers that cannot approve. A Personal Identification Number (PIN), a fingerprint, a face or a smart card is not expected to unpack to a password (the manual check records what each does), so an account that signs in with a PIN or a smart card alone, or with no password, is expected not to be able to approve; the guard has no consent path of Windows Hello, and an empty password is never accepted. If a PIN does unpack under the account's own name, it is sent to `LogonUserW` as a password and counts toward the lockout of the account. An answer that cannot be read as a name and a password is an attempt used, with no logon tried; so is an answer whose password the system hands back in a protected form (`CredIsProtectedW`), which is not sent to the logon, where it would fail as a wrong password and count toward the lockout of the account (that the secure prompt returns clear text for each type of account is not asserted by the tests, and the manual check records it).
  - The process that started the guard. It is opened before the first prompt and watched while any wait goes on (the prompt, the check by the system): if it exits, the run is refused, so a prompt is not answered for a run that nobody started. A process is taken as that starter only if it started before the guard did, as a parent must have, so a process that took the identifier of a starter that had gone is not taken for it when the guard opens it; the handle that was watched during the prompt is the one the run is watched against afterwards, and the identifier is not looked up again. A starter that cannot be opened, or that started after the guard, refuses the run with the reason "the process that started the run cannot be watched" and attempt=0.
  - The record. Every attempt and the outcome is a line that names the account the guard runs as (`account=`, as the system writes it), the command line that was shown (`command=`), how the user was asked (`method=`), the deadline the run starts with (`timeout=`) and the nearest process that started the guard as the prompt shows it (`started_by=`), so that an approval can be read afterwards for what it was, for whom and by what; the image of the line is always the guard's own file name, and says nothing of who asked; neither the password nor anything that was typed is in a line. The command line is in the line (the first 140 characters once written out, as the prompt shows them), so a secret passed as an argument is written to the audit file and to standard error, which an agent host may feed back to the agent; pass secrets by environment variable or file, not by argument (CWE-532, insertion of sensitive information into a log file). An approval stands only if its line is recorded: with an audit file the guard waits for the file to write the line, and a file that cannot take it refuses the run; without one it waits for standard error. A refusal line is queued and the guard gives the file 500 milliseconds to take it before it returns, so a file that hangs can lose a refusal line while the run is refused; the refusal itself is also the error on standard error and the exit code 125. A run whose exception was approved and which then fails to start (the job cannot be made, or the command cannot be started) writes a notice line, `the approved run did not start: ` with the reason, so that the record does not show a cap approved for a command that never ran.
- The exception above the cap: the console prompt (`--authenticate console`) is accepted only when standard input is a console input buffer (`GetConsoleMode` and `GetNumberOfConsoleInputEvents` both succeed on it; the second call is what rejects the screen buffer of a console, which also answers `GetConsoleMode`), because the prompt reads the console itself and a pipe is controlled by whoever starts the guard.
  - A process of the same user can create a console of its own (a pseudo console) and start the guard in it. It still has to type the password, which it does not have; if it has it, the exception is no protection against it. The prompt is shown even when a generic credential is stored under the name of the product (`CREDUI_FLAGS_ALWAYS_SHOW_UI`), so a stored credential does not stand in for the person; the manual check confirms it.
  - A program that can start the guard in a console it drives can guess the password, three tries per start (each try a real logon, with a wait of 2 seconds between tries): across starts, the lockout of the guard (the third wrong password within six hours locks the prompt for six hours) and the account lockout policy of the system are the limits. The lockout of the guard counts only the passwords given to the guard. A program that guesses through the guard is held to the wrong passwords the record can take: the guard locks the record from its last look at it until the wrong password is added, has the room for that record allocated before the logon, and refuses the run before the logon when it cannot lock the record, when the volume has no room for a record or when that room cannot be allocated, so a guess is counted before the run ends, unless an administrator removes the record or the disk itself fails (see the item on anyone who can add to the record). Do not use the console method in such a host, and set an account lockout threshold. The console method types the password into whatever hosts the console: a terminal inside an agent application, or a pseudo console that an agent drives, sees the keystrokes, so the console method should not be used there; the desktop method puts its prompt on the secure desktop.
  - The console prompt is not known to have a cancel key. What Esc, Ctrl+C and Ctrl+Z with Enter do has not been tried: Esc and Ctrl+Z with Enter are expected to leave it waiting or to give an empty answer (an attempt used), and Ctrl+C may end the guard, which also refuses the run; step 6 of the manual check records which. The message therefore tells the user to refuse by leaving the prompt unanswered for 300 seconds or by closing the console; three empty answers refuse the run too.
  - The prompt switches the console to no echo while it reads; the guard puts the mode back when the prompt returns or its wait gives up, and while the prompt reads it puts the mode back on a control event that ends the guard (Ctrl+C, Ctrl+Break, closing the console), but it cannot when the guard is ended from outside (Task Manager), and a wait that gives up on a read that goes on cannot be known to leave the console as it was; the manual check looks at both. The line that is typed may reach the command history of the console, which the console host keeps for the executable name and which a process attached to the same console can read (CWE-312 and CWE-316); after every console prompt, on every path, the guard clears the history kept for its own executable name, ignoring the result, and step 6 of the manual check looks at F7 to see that no password line is left. All the calls of the console prompt of a run are made on one thread, because a call made on a new thread after the thread of the first call had ended was cancelled at once, with nothing shown, in the test with a pseudo console. The desktop prompt is the same library and makes all its calls on one thread too, so that the second and third attempt are shown and are not cancelled at once, which the guard would read as the user refusing the run; no automated test can show the desktop prompt, so step 2 of the manual check is where it is seen.
- The exception above the cap: the lockout and its record (see the README, "The lockout").
  - The rule. The third wrong password for an account within any six hours, counted across runs, starts a lockout of six hours from that third wrong password. Only a refusal by `LogonUserW` of a password that was not empty, for the account the guard runs as, counts; at the console prompt so does a password that the system answers with one of the codes it gives only for a correct password (above), which is given the reason of a wrong one there, so that counting does not undo that masking. A logon that was started and that the system did not answer in 60 seconds counts as well, because the password reached it and what became of it is not known (the system may complete it after the guard gives up), and the run ends there. A check that was cut short because the process that started the guard exited counts the same way, because the password had reached the logon. A check that could not be started, or that ended without an answer, tested no password and does not count. A name that is not the account's counts for nothing, because no logon is tried for it. A correct password does not clear earlier failures: a record of a success could be written by anyone who can add to the record, and no record may ever shorten or end a lockout, so the record only grows and the rule is a function of the times in it and the time now. A run over the cap for a locked account is refused before the presence checks, the lock and any prompt or logon, with the count, the local time of the last wrong password, the time left and the time the lockout ends, every time; an attempt while locked adds nothing, so it does not extend the lockout. A run that starts while the account is locked never waits, and a run whose account becomes locked out after its prompt was shown, by its own third wrong password or by another run, is refused at once, with no cool-down: no prompt can be shown to a locked account, so there is no right to a prompt to keep, and the person who typed the third wrong password sees the message at once. The cool-down of 10 seconds that follows every refusal after a prompt remains for the other refusals after a prompt.
  - What the record resists. A program running as the account without administrator rights can read the record and add to it. It can also lock a range of it (a handle that can only read the record can), and set its sparse attribute, which changes no byte of it. It cannot shorten it, rewrite it, rename it, replace it or delete it, change its permissions or its owner, make a file in its folder, or delete or rename the folder. The integrity is the access control of the file system, not encryption: any key the guard held would be in the reach of the account. The folder and the records are owned by the Administrators group, with protected access lists; the account has the rights to read the record (data, extended attributes, attributes and permissions, so that the ordinary ways of reading a file work) and `FILE_APPEND_DATA` without `FILE_WRITE_DATA` on its record, and an owner rights entry takes away what an owner has by being the owner. The guard checks the lists on every run over the cap, against the token of a process of the account without administrator rights, which it makes from its own token (the Administrators group turned to deny only and all privileges but one removed, whether or not the guard is elevated), and fails closed: a record that is missing, cannot be opened for reading and appending, allows more than that, is a link, has a second name, is not owned by the Administrators group, the system or the installer of the system, or cannot be read within ten seconds (all the reads of a run share the ten seconds) refuses every run over the cap, with the step that mends it named. The owner is checked as well as the list because a process without administrator rights can make a folder and a record of its own in the folder of the programs' data with exactly the lists that the guard accepts, and keep a handle that can write to the record, opened before the list was tightened; it cannot make the Administrators group, the system or the installer of the system the owner, so a tree it made is refused. The guard judges the entries of the list as well as what its own token is granted: the list may give something only to the system, the Administrators group, the account the record is named for and the owner rights entry, and an entry for another account or group (or of a kind the step does not make) refuses the run. Each record can therefore be read and added to by its own account alone, so one account cannot lock out another, whatever was done to the record after the step made it (an entry that allowed another account to write would let that account lock this one, and a handle it opened then would outlive a new list).
  - What it does not resist. An account that is a member of the Administrators group is not protected: its programs run with a filtered token, User Account Control (UAC) is not a security boundary, and a program of that account can obtain the elevated token and remove the record, which resets every lockout. The lockout protects an account that is not a member of the Administrators group; use such an account for runs that use the exception. An administrator, or a process with an elevated token, can remove the record, which resets the lockouts, change its permissions, change the system clock, or replace the guard; this document does not defend against them (see Out of scope). An account that holds a privilege that lets a program act as the system or go round the access control of a file is not an administrator by group but can rewrite, shorten or remove the record whatever its list says (CWE-250 and CWE-269; Saltzer and Schroeder, least privilege and fail-safe defaults). The privileges are those to debug programs (`SeDebugPrivilege`), act as part of the operating system (`SeTcbPrivilege`), make a token (`SeCreateTokenPrivilege`), load a driver (`SeLoadDriverPrivilege`), assign a token to a process (`SeAssignPrimaryTokenPrivilege`), impersonate a client (`SeImpersonatePrivilege`), restore files (`SeRestorePrivilege`), back them up (`SeBackupPrivilege`), take ownership of them (`SeTakeOwnershipPrivilege`), manage volumes (`SeManageVolumePrivilege`) or change the system time (`SeSystemtimePrivilege`): members of Backup Operators and Server Operators have some of them, a policy can grant any of them to an ordinary account (`SeDebugPrivilege` is often granted to developers, and the privileges to impersonate a client and to assign a token belong to service accounts), and a program that holds one of the first six can act as the system (the sixth with a token of the system to impersonate, which is usually to be had). The check of the list cannot see them, because the token it asks the system about has every privilege but one removed; the guard therefore reads the privileges of its own token first, and refuses a run over the cap when the token holds one of them, enabled or not, and the guard is not elevated (an elevated token is an administrator's, which is the case above): `this account holds privileges (SeDebugPrivilege) that let a program of the account rewrite the lockout record, so it cannot be protected; do not use the exception for this account`. The standard token of an ordinary account, and the filtered token of a member of the Administrators group, hold none of them, so an ordinary account is not refused. The setup step prints the same sentence as a warning when it is run for its own account and the programs of that account (the other half of a split token, when there is one) hold such a privilege. Do not use the exception for such an account. A change of the clock needs administrator rights or the privilege to change the system time, which a policy can grant to an ordinary account; an account that holds it can step the clock forward six hours and end any lockout, and the guard does not notice. Do not use the exception for such an account. A record dated more than five minutes ahead of the clock is ignored, and one dated less than five minutes ahead is read as now, so a record can neither end a lockout early nor lock for longer than six hours from now. The time named as the end of a lockout is rounded up to the minute so that it is not already past while the run is still refused, for records dated by the clock; a record dated ahead of the clock by less than five minutes is read as now, so the end named for it can move later by up to five minutes as the clock reaches it (a step of the clock backwards by up to five minutes does the same to the guard's own records), and a run retried at the time first named can be refused again for those minutes. The times kept while the record is read are those after twelve hours ago and not later than five minutes past the time of the reading, which are exactly the times the rule reads; a time the rule ignores is never kept in place of a real one, and the scan and the rule use one reading of the clock. A change of the time zone changes only how the times in the message are shown, not when the lockout ends. The clock is trusted: a correction of the clock backwards by more than five minutes (by the time service, or an administrator) puts the earlier failures ahead of it, where they are ignored until the clock has caught up with them, and a step forwards of six hours ends a lockout; the record keeps no clock of its own.
  - Anyone who can add to the record can start a lockout, as wrong passwords would. A program running as the account can append the three lines of a record, which locks the prompt for the account for six hours, and again before they end, which keeps it locked for as long as the program keeps appending (an administrator removes the record to end it), or append more than the guard can read in ten seconds (many gigabytes of anything), which refuses every run over the cap for that account until an administrator removes the record and runs the step again, or hold the record open without sharing it, which refuses the run with a reason that says so and ends when it lets go, or lock a range of the record (a handle that can only read it can), which refuses the run before the logon, or at its first look when the range is one the guard reads, and ends when it lets go; this is a denial of service against the use of exceptions by that account and nothing more, and it cannot be done to another account, whose record it can neither read nor add to. A program of the account can also make the record as large as the volume allows; the account cannot shorten it, so the space stays taken until an administrator removes the record. The size of a file is charged to its owner, which is the Administrators group, so a disk quota set for the account does not limit it; on machines where the exception is used, watch the size of the `ProcessTreeGuard` folder (`Get-ChildItem`) and remove the record if it is large. What it appends cannot push the real failures out of the record: the record is read whole, in blocks, in constant memory, with the times that can matter kept, and not from its end, because reading only the end of a large record would let appended bytes end a lockout. The times kept are those after twelve hours ago and not later than five minutes past the time of the reading, which are exactly the times the rule reads; a time the rule ignores (one dated further ahead) is never kept in place of a real one, and the scan and the rule use one reading of the clock, so a flood of records dated just beyond the five minutes cannot push the real failures out. All the reads of the record in one run share ten seconds, each look being one read, so a record that takes nine seconds to read cannot be read again and again to hold a run for minutes; a run whose reads together take more than ten seconds is refused. The count in the message is of the times kept, at most 4096. A program of the account that fills the volume cannot make a guess go uncounted: the room check (less than 64 kibibytes available to the account on the volume refuses the run) is made with the lock and before the logon, and so is the allocation of the room of the next record. Without that allocation the account could leave the volume with a little more than 64 kibibytes, let the check pass, and fill the rest in the time the logon takes, so that the append of a wrong password needed a new unit of allocation and failed with the disk full: the run is refused ("the wrong password could not be recorded"), which also tells the program that the guess was wrong, and a right password approves, so it has an oracle with no record (CWE-367 and CWE-770; NIST SP 800-63B section 5.2.2). The guard therefore reads the allocated size of the record (`GetFileInformationByHandleEx`) under the lock and, when it is not at least one record of 20 bytes past the end of the record, appends newlines until it is (a record shorter than 4096 bytes is first made that long, because a short file may be kept in the volume's own table and so takes no room of its own; then one byte is written past the end of its allocation, which makes the volume allocate the next unit; at most about 4 kibibytes, once). The reading ignores newlines, so they change no failure and no lockout. The append of the wrong password then lands in room that is already allocated, and what is left is a fault of the disk itself, which the account cannot cause. A record that cannot be given that room refuses the run before the logon.
  - The lockout is read again before every prompt and before the logon of a password that was entered, so that one that starts meanwhile (a run of the same account in another session, or three records appended while a prompt is open) stops the run there: the password that was entered is dropped without a logon, and no guess is made, and a right password does not approve, while the account is locked (CWE-367). Once a password is entered the record is locked (the whole range, exclusive) before that last look and kept until the attempt is over: through the logon (which can take up to a minute), the approval and the line that records it, or the adding of a wrong password and the look at what it came to. While it is held no other program can append to the record or read or lock a range of it, so a lockout cannot start between the look and the approval, and two runs of the account cannot both pass the look at two wrong passwords and both guess; the second is refused before its logon ("the lockout record is locked by another program or another run; try again") after 2 seconds, which is the cost of that, and it can run again. A program of the account that holds a range from the end of the record locked would otherwise let every look pass and make the append fail after the guess (CWE-362 and CWE-307; NIST SP 800-63B section 5.2.2): the guard cannot take its lock then, and the run is refused before the logon. The lock is not held while a prompt is open, so other sessions are not kept waiting for a person who is typing, and it is let go before the wait that follows a refusal. The prompt says how many wrong passwords of the account are on record from the last six hours, so that a person who is one typing error from the lockout knows (the desktop prompt in its text at every attempt; the console prompt shows its text once, so it writes the count on a line of its own before the second and the third attempt as well, and a console that cannot take that line refuses the run); any program of the account can add to that count, as above.
  - Where the record is. The folder `ProcessTreeGuard` in the folder of the programs' data, which the guard reads from the registry value `ProgramData` of the machine (`HKEY_LOCAL_MACHINE`, which only administrators write), with `%SystemDrive%` replaced by the drive of the system folder (`GetSystemWindowsDirectoryW`). It does not use the known folder interface (`SHGetKnownFolderPath`), `GetAllUsersProfileDirectoryW` or any environment variable. The reason was measured: with `SystemDrive` set in the environment of a process to a folder that holds a folder named `ProgramData`, both the known folder interface and the profile directory call returned the folder inside it, and with it set to a drive that is not there the known folder interface failed and the profile directory call returned that drive; `ProgramData`, `ALLUSERSPROFILE`, `PUBLIC`, `SystemRoot` and `windir` were not followed, but nothing promises that for other versions of Windows. A process of the account could therefore have pointed the guard at a folder and a record of its own. The registry value and the system folder do not follow the environment (G102 sets the variables and checks that the guard still looks where the machine keeps its record). A drive letter in a path is resolved through the device map of the logon session, which a process of the account can add to and change (`DefineDosDevice`, `subst`; measured: a process without administrator rights defined a drive letter in its own session). The guard therefore opens nothing through a drive letter. The system volume is found by opening `\SystemRoot`, a link in the root of the object manager that the kernel made, with `NtCreateFile`, and asking for the final name of what it leads to (`\Device\HarddiskVolume3\Windows`, the volume `\Device\HarddiskVolume3`); the registry value, which must be on the system drive (`%SystemDrive%\ProgramData`, or a literal path on that drive; a folder of the programs' data on another drive refuses every run over the cap), is put on that volume, and the folder, the folder of the records and the record are opened by their names from the root of the object manager. A process of the account cannot add to or change the names there. A tree that the account redirects a letter to is therefore never opened, whoever owns it: this is what closes a tree that an administrator owns and the account can reach (a copy kept after an upgrade, as `Windows.old` is, or a restored backup, whose parents an ordinary user may be able to read and whose old record would reset a lockout), which the owner test alone does not close. The owner test closes the other kind, a tree that the account made, and stays as well: the guard requires that the record, its folder, the folder of the programs' data and every folder above it are owned by the Administrators group, the system or the installer of the system (which owns the root of the system drive on a usual machine), and that none is a link, which a process without administrator rights cannot arrange for a tree of its own. `\\?\GLOBALROOT` is not used for this: it is a name that is looked up through the same device map as a drive letter, and `DefineDosDevice` refused to define it here with an access denied, but a name made by another route was not tried, and `NtCreateFile` with a name from the root asks nothing of the map. The decision is made on the object that is used and not on a name (CWE-367, time of check to time of use): after the look at the names the record is opened once, and the owner, the access list, the number of links and the kind of file are judged again on the open handle; it must be the file the look found (the volume serial number and the index of the file), and its final name from `GetFinalPathNameByHandleW` must be the name it was asked for, so a name that led elsewhere the second time (the time between the check and the open) is refused, and a record that was replaced by the account in between is not the file that is used.
  - The folder of the programs' data and squatting. By default any user can make a folder in the folder of the programs' data and owns it with full control, so a user could make `ProcessTreeGuard` before the step is run and keep control of it. The cost is that one user who makes the folder first denies the exception to every account on the machine: every run over the cap is refused, for every account, until an administrator removes the folder and runs the step. Run the step as part of the installation, before users can sign in, and remove and make the folder in one elevated command, so that there is no time in which a user can make it first: `Remove-Item -Recurse -Force "<folder>"; process-tree-guard create-lockout-record ACCOUNT`. The step does not take over a folder that is owned by neither the Administrators group, the system nor the installer of the system, and says so; the guard refuses a folder that the account owns, and one where the account has more than the right to read, because each fails the check, whatever list it was given (the owner is the account that made it, and a handle opened before the list was tightened can still write). The step also does not take over a record whose owner is not one of those: where a folder of the records was made first by an administrator or by a program, without the lists of the step, a user can make files in it (the entry for users on the folder of the programs' data is inherited), so a program of the account could plant `<security identifier>.lockout` there and keep a handle opened for writing before the step runs; setting the list and the owner of that record would leave the handle writing for ever (CWE-283, CWE-732 and CWE-379) and the check would then pass it. The step reads the owner from the handle it then uses to set the permissions, before anything is asked of the record, and refuses; an administrator removes the record and runs the step. The check also requires that the account cannot delete or rename the folder of the programs' data and the folders between it and the root of the drive, nor what is in them, nor change their permissions or owner (the rights that would let it remove, swap or take over the folder of the records); the step cannot change those folders, and where it is so, no record can be protected there and the guard refuses. A data volume gives a user the right to delete the folders it makes in the root (the usual list of a volume that is not the system's), and the right to delete the folder of the programs' data would let it rename that folder and put a tree of its own in its place; the root of the drive itself keeps the judgment it had, because it cannot be deleted or renamed in any case.
  - Compression. A file or folder made in a compressed folder is compressed, and a compressed file is allocated in units that leave no room for the next record, so a record on a volume that keeps it compressed could never be given the room that the guard allocates before the logon, and every password would be refused after it was typed. The step makes the folder and the record uncompressed (it sends nothing to one that is not compressed, and changes how the volume stores the record, no byte of it), and the check refuses a record or a folder that is compressed, with a message that names the step and `compact /u`; the refusal is fail-closed (Saltzer and Schroeder, fail-safe defaults) and no wrong password is guessed without being counted. An administrator, or a process with an elevated token, can compress the record again, which refuses every run over the cap for the account until the step is run again; that is a denial of service by someone this document does not defend against.
  - The step. `process-tree-guard create-lockout-record [ACCOUNT]` (the alias `process-guard` runs the same command) is run from an elevated terminal, and refuses without elevation with exit code 125. Every refusal of the guard that the step mends names the account of the refused run (`process-tree-guard create-lockout-record DOMAIN\user`), because with no argument the step makes the record of the account of the elevated token, which is usually the account that elevates and not the account that is protected. Run from a deployment tool as the system account, or as local service or network service, with no argument it is refused (those accounts have no password to ask for and no record can protect them), so a deployment always names the account. Whoever installs the guard on a machine must run this step once for each account that approves exceptions; nothing in the guard's files runs it, and until it is run every run over the cap is refused. It makes the folder and the record with their access lists in force from the first instant (the lists are the ones they are made with), sets right the list of a folder that is there, and of a record that is there whose list is right (never touching what a record holds), refuses a link, a record with a second name, and a folder or a record owned by someone else, and runs the check that the guard runs before it says that it is done; the line that says so ends with the sentence "An account in the Administrators group is not protected from its own elevated programs; see SECURITY.md.", which it says every time (see "What it does not resist"). It names what it makes by the drive of the system folder, as an administrator reads it; the check that ends it looks at the same objects by their names in the object manager, and fails if they are not the ones it made. For an account other than the elevated one the check compares the owner and the access list of the record with what was set, because a token of the elevated account cannot stand for another. It does not set a record right in place when its list allowed the account more than reading and appending (a deployment tool or an administrator may have made the record, owned by the Administrators group, under the default list of the folder, which lets users write): a program of the account may have opened the record for writing while it did, and that handle stays valid when the list is changed (the access check is made when a handle is opened, not at each write), so it could truncate or rewrite the record for ever and so reset any lockout, and what the record holds cannot be restored (CWE-672, CWE-732; Saltzer and Schroeder, complete mediation). It is the reasoning by which the step does not take over a record owned by someone else, applied to the list: the step names the rights, leaves the record as it was and exits with 125, and the guard refuses such a record with the same remedy. An administrator removes the record and runs the step, which makes a new one. For an account other than the elevated one, whose rights the system cannot be asked about, a record that is not exactly as the step makes it is refused in the same way. An administrator removes the lockouts, or a record that a program of the account has made unreadable in time, by removing the folder or the record (the `Remove-Item -Recurse -Force` of the folder, from an elevated PowerShell); until the step is run again every run over the cap is refused for the missing record, so remove and make in one command: `Remove-Item -Recurse -Force "<folder>"; process-tree-guard create-lockout-record ACCOUNT` (for one record, remove its file and run the step for that account).
  - Cost. One file for each account, and 20 bytes for each wrong password; a program of the account can make its record as large as the volume allows (see above).
- The exception above the cap: the password in memory. The password lives only in buffers that are zeroed with volatile writes when they are dropped. The release profile aborts on a panic without running destructors, so a panic hook zeroes every buffer that holds the password (and the authentication buffer of the prompt) before the abort. Even so, the password can reach a crash dump of the guard taken at another moment (Windows Error Reporting local dumps), the page file or the hibernation file, since the buffers are not locked in memory (CWE-316, CWE-528 and CWE-591). The system's own copies of the credentials are outside the guard: the authentication buffer is zeroed over its whole size and freed, but what Windows keeps inside is not the guard's to wipe.

- When `hook antigravity` sees a line already in the wrapper form of the other family (`process-tree-guard-auto.exe` for `process-guard.exe` and the reverse, or any of the three automatic copies for `process-tree-guard-gate.exe`), it lets the line pass unchanged and does not check that the file exists. This fails closed: if the file is missing, the host cannot start the line and nothing runs. The file would have to be in the guard's own folder, and a person who can write there can already replace the guard.

- `hook powershell-auto` rewrites a PowerShell tool call to the automatic copy beside the program and does not check that the file exists, and a line that already has that wrapper form passes through unchanged without the check. If the file is missing, the rewritten line runs nothing, but PowerShell reports the missing program and the line can end with exit code 0, so a host may read it as success. The command is not run unguarded, but it is not run at all. This is the reverse of `hook antigravity`, which denies the call when the copy is missing. Install the automatic copy before configuring the vendor.
- The program the guard is asked to run is found as the Windows search for a command finds it, as in 1.x: through `PATH`, and in the current folder first unless `NoDefaultCurrentDirectoryInExePath` is set. The caller names that program, so a caller that needs one exact program gives its full path. The shell the guard chooses for `--shell powershell` (`pwsh.exe`, else `powershell.exe`) and for `--shell cmd` (the program named by `COMSPEC`, else `cmd.exe`) is found the same way, as in 1.x. The guard's own files (the automatic copy a hook rewrites to, and `POLICY.md`) are never found this way.
- The library calls `run`, `run_shell` and `run_auto` take the calling process's parent (and, for `run_auto`, its live ancestors) as the owner, and identify it by process identifier when the call starts. Windows can reuse an identifier after its process has exited, so a call made after the parent has exited can watch an unrelated process that has taken the identifier. The README describes the owner rule; a program that can outlive its parent should start `process-tree-guard` as a child instead of calling the library.
