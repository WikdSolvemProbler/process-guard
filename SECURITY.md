# Security policy

## Supported versions

Security fixes are made for the latest release only. Update to the latest release before reporting.

## Reporting a vulnerability

Report vulnerabilities privately through GitHub's private vulnerability reporting: open the repository's **Security** tab and choose **Report a vulnerability**. Do not open a public issue for a vulnerability.

Include the release or commit, the Windows version, the exact command line or hook payload, what you expected, and what happened. A minimal reproduction is the most useful thing you can send.

## In scope

- A process that escapes the job object, or that survives the deadline or the exit of the process that launched the guard. This holds against commands that do not act against the guard on purpose; a hostile process of the same user inside the job can do the things listed under Known behaviour, which are not vulnerabilities.
- A command that passes the hook mode envelope check without being exactly the documented envelope. The envelope may name the executable the hook runs from, or the same executable under its other name (`process-tree-guard.exe` and the 1.x alias `process-guard.exe`) in the same folder; a path in another folder or in another letter case that passes is in scope.
- A hook mode denial that does not exit with code 2 because a standard stream cannot be written (Common Weakness Enumeration, CWE-636, failing to fail securely): the host reads any other status as a non-blocking error and lets the command run.
- A command that passes the envelope check of the hook role (`process-tree-guard-gate`) without naming `process-tree-guard.exe`, `process-guard.exe` or `process-tree-guard-deadline.exe` in the gate's own folder or in the `bin` folder beside a `libexec` folder (the folder name `libexec` is read in any letter case); the gate itself is never a valid envelope, under whatever file name it is installed and in whatever letter case it is started.
- A Google Antigravity `run_command` call that reaches the shell through `hook antigravity` without being wrapped, exactly guarded already (the wrapper form of either name beside the guard, or an envelope of either name), or denied.
- A file used by a program that was found through `PATH` or the current folder instead of relative to the program's own location: the automatic copy a hook rewrites to, or `POLICY.md`.
- Malformed input to the hook's JavaScript Object Notation (JSON) parser or the Base64 decoder that crashes the guard, hangs it, or changes its decision.
- Argument or shell quoting that runs a different command from the one given.
- In an extendable run (`--extendable`, see the README), the channel that the processes in the job use to ask for more time:
  - A request granted to a process that is not alive, is not in the guard's job, or started after it connected; or a hold that outlives its process, or that is kept by a process identifier and so can pass to an unrelated process; or a hold made for a library call (`run`, `run_shell`, `run_auto`) that outlives the call; or a hold that stands for longer than half a second after its client was left without the reply that grants it.
  - A deadline of the run that is later than the latest of its own `--timeout` deadline and the holds of live processes, a hold or a nested guard's start that exceeds `--max-extension` without being refused (exit code 125 for the guard), or a cap that anything but the guard's own launch arguments can change.
  - A change of the deadline, or a hold, that is not in the log; a grant made in a run with no `--extension-log` whose line was not written to standard error, or in a run that started with a standard error that is closed or is the null device; an `--extension-log` that names a device or a pipe and not a file on a disk (the run does not start); a grant made while the audit file named by `--extension-log` cannot take its line (one that cannot be written, or cannot be turned over and has less than 64 kibibytes (KiB) left before twice its limit), other than the lines that were on their way when it became so; a value that can end a log line or start a field of its own (Common Weakness Enumeration, CWE-117); or a log file that grows without the bound of one mebibyte (MiB) and one rotation, or that discards its earlier lines without a line in it saying that its turn over failed.
  - The channel reached by another machine, or by another account on the machine; a second instance of the pipe, or its name predictable.
  - A request that makes the guard hang, crash, or miss its deadline, including a request that is granted after the deadline has passed; a message of a size other than the fixed ones that is not refused; a log destination (a standard error that nobody reads, the audit file) that keeps the tree from being ended or the guard from returning; a client that waits for ever for a reply.
  - A request that reaches the run and is not in its log (other than the refusals the log coalesces and counts), or a flood of refusals, from one process or from processes outside the job, that pushes earlier lines out of the log. (A flood of grants from many short-lived processes in the job is known behaviour; see below.)
  - A client of the channel (`extend`, the start of a nested guard, the library call `extend`) that crashes, hangs, or reports a grant on a reply whose numbers are out of range, in place of refusing it with a reason (Common Weakness Enumeration, CWE-248 and CWE-20).
  - A client outside the job that keeps the channel from serving the processes in the job.
  - A guard started inside an extendable run that is not held to the run's cap; an extendable guard in a job that is not extendable that outlives the outer deadline; the contain role running a command with no extendable run around it.

## Out of scope

- Commands that were never routed through the guard. The guard bounds what runs through it; see the Limits section of the README.
- Work on remote machines, in containers or in Windows Subsystem for Linux (WSL).
- Actions by a user who already has administrative rights on the machine.
- Actions by a hostile process of the same user inside the job, such as suspending the guard or asking a system service to start a process outside the job; see Known behaviour.

## Known behaviour

- Extendable runs: access by another process of the same user is not a security boundary. The name of the channel is in the environment of every process in the run, and a process of the same user can read it, or the memory of a process that has it. What limits such a process is that the guard verifies it before it answers (alive, in the job, started before the connection), the cap on every request, the rate limit (12 requests per process in 10 seconds), the limit on holds (256, and 8 for one process) and the log. A same-user process outside the job is refused and logged for its first 12 connections in a window, and disconnected at once after that. The log is an audit record, not a control.
- Extendable runs: any verified process in the job can hold the deadline up, and can replace the hold of its parent through the `extend` program, which asks for the process that ran it. A chain of requests, each within the cap, keeps a run alive for as long as a process keeps asking: renewal without end is the intended mechanism, and there is no limit on the whole life of a run. Each request is capped, in the log and made by a verified process in the job, at every moment the deadline is no more than the cap ahead, and a run whose processes stop asking, or hang, ends at the latest hold. A launcher that wants a run to end by a given time sets `--max-extension` and `--timeout` to it, and a run that nothing renews ends at its `--timeout`.
- Containment is not a boundary against a hostile process of the same user inside the job (Common Weakness Enumeration, CWE-693, protection mechanism failure). Such a process runs with the rights of the user that started the guard, and can do what that user can do to the guard and to the system: open the guard and suspend it (`SuspendThread`) or write to its memory, so that the deadline is not checked or is changed; duplicate a handle to the job; and ask a service of the system, such as Windows Management Instrumentation (WMI, `Win32_Process.Create`), the Task Scheduler or a Component Object Model (COM) server, to start a process, which belongs to that service and not to the job, and so survives the kill. The guard prevents a process from using `CreateProcess` to leave the job, and ends every process that stays in it. The statements in the README and above, that nothing survives the deadline and that a deadline moves only by a logged request, hold for commands that do not do these things on purpose: tests that hang, servers left running, descendants that outlive their parent, the ordinary commands of an automated agent. A host that must resist a hostile command runs it as another user, in a container or in a virtual machine; the guard is not that. The guard process's own access list is not hardened against the same user.
- Extendable runs: the table of holds has 256 places, and one process can hold at most 8 of them, all its holds together whatever their numbers; a ninth is refused with "this process holds too many deadlines", so a single process cannot take the table from the rest. Processes of the job can still fill it between them, each within its 8 and its 12 requests in 10 seconds (32 processes are enough): every other request, and the start of every nested guard, is then refused with "too many processes hold the deadline" until those holds end, each at most the cap from its grant and at the latest when its process exits. That is a denial of the channel to the processes of the run by processes of the run; it never moves the deadline, and every grant is in the log.
- Extendable runs: the client and the run agree about whether a hold exists. The guard sets a hold, then sends the reply and waits half a second (a quarter of a second for a process over its share) for the client to read it; the pipe has no outgoing buffer, so the write completes only when the client has read the reply. A client that sends a valid request and reads later than that gets an error and no reply, and the guard withdraws the grant: the hold goes back to what it was before the request, the deadline is recalculated and the log has a `decision=withdrawn` line after the `granted` line. A nested guard that did not get its reply exits with 125 and runs nothing, and `extend` exits with 125. A reply to a release that is not taken leaves the hold ended, which is what the client asked for. The window between the grant and the withdrawal (up to half a second) is the only time the run holds a deadline that its client was not told of, and the hold in it is within the cap and in the log.
- Extendable runs: the channel is four instances of a pipe, each served by a thread of its own. The guard settles who a client is before it waits for its message; a client outside the job that has used its allowance (12 connections in 10 seconds, all such clients together) is disconnected at once, with no wait and no reply; any other connection costs an instance at most a quarter of a second to send and half a second to take the reply (a tenth of the first, and a quarter of a second for the second, for a process in the job that is over its share), and a connection that sends nothing is charged to its share and logged. A process in the job can still stall: a handful of processes that connect and send nothing, or do not read the refusal, can keep all four instances busy, and another process's request then waits, up to the five seconds a client waits for the channel, and fails. That is a denial of the channel to the processes of the run by a process of the run; it never moves the deadline. The deadline of the run is never delayed by a client. A client waits at most five seconds for the reply and gives up with a reason if the run does not answer. A standard error that nobody reads blocks neither the answers nor the deadline: the log is written from bounded queues by threads of its own, a full queue drops lines (and a notice counts them), the tree is ended before the guard writes anything to standard error, and the guard's own notice is abandoned after half a second.
- Extendable runs: a process in the job can turn the log file over within minutes. Refusals are coalesced (the first of a process for the rate is a line and opens a window of 10 seconds, the rest of that window one line with a count, written when the window ends, also while the process goes on asking, after which the next refusal opens a window of its own; the count of the window that is open when the guard is killed is lost; all clients outside the job count as one process) and at most 24 refusal lines are written in any 10 seconds, so refusals alone cannot do it. Grants are not budgeted: each is a line of its own, a process is limited to 12 per 10 seconds, but processes are cheap, and one that starts many short-lived processes, each asking once, writes the file and its one rotation full in a few minutes (a fast spawner needs about a minute), and every earlier line, the refusals among them, is gone from both files. The bound of one mebibyte and one rotation is a bound on disk space, not a promise to keep lines. The file is evidence of what happened before such a flood only if it is copied off the machine promptly (read it while the run goes on, or keep the run short). The guard and the processes in the job run as the same account, so they can also open the file, append lines in the form of a grant, and delete or replace it; see the next items.
- Extendable runs: a library call (`run`, `run_shell`, `run_auto`) made inside a run is a nested guard in a process that goes on, so its start asks the run for its `seconds` with a hold on the calling process, and the hold is ended when the call returns, by a release request that is a line of its own in the log (`decision=released`). A call returns only after its release has been answered, so it can wait up to the five seconds a client waits when the run does not answer; a release that does not arrive leaves the hold to run out or to end with the process. A release is let past the rate limit when it ends a hold, and is counted like any other request when it finds none. Each call is one request against the 12 per process in 10 seconds, so a host that makes more than 12 calls in 10 seconds inside a run is refused for the rest, with the reason, and the command does not run; each call has a hold of its own, named by a number in the request and in its release (the hold of `extend` is another), so calls that overlap, from threads of one process, do not replace or release one another's holds, and the run waits for the latest of them, each no more than the cap from its grant. The program (`process-tree-guard`, in any role) is not affected: its hold ends with its process.
- Extendable runs: the audit file is turned over by renaming it to `PATH.1`, and a program that follows the file and holds it open without `FILE_SHARE_DELETE` (PowerShell `Get-Content -Wait` is one) stops the rename. The earlier lines are not discarded for that: the file is copied to `PATH.1` and emptied instead, and when that fails too the file grows past one mebibyte, toward twice that, with a notice in it that the turn over failed; the guard tries again once a second, whether or not a line comes, and standard error has every line. `PATH.1` is not held open by the guard, and any process in the job can stop both ways of turning the file over by opening `PATH.1` for reading and sharing reading only (read access is all it needs, and it is the default of .NET's `File.OpenRead`); no setting of the folder prevents that. The run does not carry on and lose lines for it (Common Weakness Enumeration, CWE-778; National Institute of Standards and Technology (NIST) Special Publication (SP) 800-53 control AU-5, response to audit processing failures): when the file cannot be turned over and has less than 64 KiB left before twice its limit, or when its lines cannot be written, the run grants nothing. Every request that would move a deadline is refused, with the reason that the audit file cannot take lines, until a turn over or a write works; deadlines already granted stand, so the deadline never moves later without a line. A run started with a file that is past its limit, cannot be turned over and has no such room does not start (125). The 64 KiB is room for the lines on their way at that moment; a grant is in the file unless more than that was queued behind it. A collector that follows the file should open it with `FILE_SHARE_WRITE` and `FILE_SHARE_DELETE`. The guard holds the file open for appending for the whole run, so a reader that does not share writing (the default of .NET's `File.OpenRead` and `FileStream` for reading, which share reading only) is refused when it opens the file, and cannot make the guard's appends fail by holding it; a reader that opened the file before the run began stops the guard at its start, with 125. A write that fails all the same (the folder went away, a handle opened by another route) is not silent: the guard tells standard error at once, keeps the lines (up to 256), tries again every half second, writes them in order when the file takes lines, and then puts a notice with the counts in the file and on standard error; lines past the 256 are counted in it, and the end of a run says how many lines the file never got. A process that can only read the file can hold it open, but it cannot erase lines by doing so; with the file held open by the guard it cannot make the appends to it fail, and a write that fails is recorded by those notices and stops the grants as above (standard error has every line either way). The file is evidence only against a process that cannot open it. A process in the job runs as the same account as the guard, opens the file with the guard's own access, and can append a line in the exact form of a grant, or delete or replace the file; a folder that the job cannot write to is one that the guard cannot write to either, so no setting of the folder prevents it. Rely on the file only where a boundary of another kind keeps the command from it (the command runs as another user, in a container or in a virtual machine) or where a collector ships the lines off the machine as they are written; copy it off the machine promptly in either case.
- Extendable runs: the table that tells processes apart for the rate limit holds 1024 live processes. A process that has exited is forgotten when the table is full, so any number of short-lived processes can ask in turn; a new process is refused, with a reason of its own, while 1024 others are live.
- Extendable runs: when there is no audit file, standard error is the only record, and the guard holds its grants to it. A run does not start when standard error is closed or is the null device and `--extension-log` was not given; a grant is made only once its line has been written to standard error (the guard waits at most half a second for the write, and takes the grant back with a `withdrawn` line and the refusal "the audit file (or standard error, when there is no audit file) cannot take lines" when it fails or does not finish); and after a write has failed the run grants nothing until one works. The guard cannot tell a standard error that is a pipe or a file whose reader keeps nothing, or reads and discards, from one that records, so the rule that a deadline moves only by a logged request holds without `--extension-log` only as far as the launcher's standard error is kept. A launcher that needs the log as evidence, and not only a refusal where nothing can be written, passes `--extension-log` and reads the file, on the terms of the item on the audit file above.
- Extendable runs: a process in the job shares the guard's standard error and can print a line in the form of a log line. The copy of the log on standard error is not evidence. The file named by `--extension-log` is better evidence, but only on the terms of the item on the audit file above: a process in the job can write to it too.
- Extendable runs: `process-tree-guard extend` holds the process that ran it. Under Git Bash that is the shell that made a short-lived copy of itself to run the program, found by looking through copies of `bash.exe` or `sh.exe` with the same image path; a launcher that is not recognised, and that runs the program through an intermediate process that ends with it, holds that process, and the hold ends with it. The library call holds the process that makes it.
- Extendable runs: the deadline is measured with `GetTickCount64`, which counts the time the machine is asleep and does not follow changes of the clock.
- Extendable runs: the check that a client started before it connected compares its creation time with the system (wall) clock, and the time it compares with is when the thread that serves the instance of the pipe noticed the connection, taken as soon as its wait returns, not the instant the client connected. A process that took the identifier of a client that had connected, written its request and exited, and was created in the gap between the connection and that moment, is not told apart by the comparison (Common Weakness Enumeration, CWE-367 and CWE-362). The gap is the time the serving thread took to run: short on an idle machine, tens of milliseconds or more under load, and the whole time since the connection when the client connected before the thread was waiting. Windows reuses process identifiers readily. The guard closes that gap with a second check, made after it has read the request and before it decides: it asks the pipe whether the client's end is still open (`PeekNamedPipe`), and a request whose end is closed is refused as not verified. A client waits for its reply with its end open, so a client that wrote and exited has closed its end, and the process that took its identifier is refused whenever it was created. What remains is a client that gave a duplicate of its end to another process before it exited: the end is then still open, the check passes, and a process created inside the job in the gap with the client's identifier can be taken for the client; it would get the client's hold (within the cap, in the log, ending with that process), its share of the rate and the log line. The client would need a second process that stays, and the identifier to be reused inside the gap. A step of the system clock backwards across the start of a client makes its creation time later than the connection time, and the client is refused as not verified, which is logged; the deadline is not affected.
- Extendable runs: a value of `PROCESS_TREE_GUARD_CHANNEL` that is not the name of a channel, or names one that is gone, is read as no run around the guard: the guard keeps its own fixed deadline and runs its command, as before extendable runs, so no setting of that variable (a user or project environment setting, a stale shell) can stop the guards of a host from running commands; `extend` and the contain role refuse it, since they have no run to ask. A value that names a pipe that is there and is not an answering run (one that stalls, or answers with something that is not understood) ends the guard that reads it with 125, which is a denial of that one command to a process that can set the variable in the guard's environment; it cannot give the command more time.
- Extendable runs: a client does not check which process serves the channel. A process that can set `PROCESS_TREE_GUARD_CHANNEL` in the environment of a client can point it at a pipe of its own. The client accepts a reply only when it is well formed and its numbers are in range (finite seconds from 0 to 86400, a time that a clock can show) and refuses anything else with exit code 125. A reply from such a server can make `extend` report a grant that no run made; it cannot move the deadline of any run, which is held in the state of the guard that owns the job, and the process that reported it stays bounded by that job.
- An extendable guard in an extendable run asks the outer run for its own deadline and then serves a channel of its own. Holds granted by the inner channel keep the inner tree alive only while the outer run holds the inner guard, because the outer run ends the whole job at its deadline.

- When `hook antigravity` sees a line already in the wrapper form of the other family (`process-tree-guard-auto.exe` for `process-guard.exe` and the reverse, or any of the three automatic copies for `process-tree-guard-gate.exe`), it lets the line pass unchanged and does not check that the file exists. This fails closed: if the file is missing, the host cannot start the line and nothing runs. The file would have to be in the guard's own folder, and a person who can write there can already replace the guard.

- `hook powershell-auto` rewrites a PowerShell tool call to the automatic copy beside the program and does not check that the file exists, and a line that already has that wrapper form passes through unchanged without the check. If the file is missing, the rewritten line runs nothing, but PowerShell reports the missing program and the line can end with exit code 0, so a host may read it as success. The command is not run unguarded, but it is not run at all. This is the reverse of `hook antigravity`, which denies the call when the copy is missing. Install the automatic copy before configuring the vendor.
- The program the guard is asked to run is found as the Windows search for a command finds it, as in 1.x: through `PATH`, and in the current folder first unless `NoDefaultCurrentDirectoryInExePath` is set. The caller names that program, so a caller that needs one exact program gives its full path. The shell the guard chooses for `--shell powershell` (`pwsh.exe`, else `powershell.exe`) and for `--shell cmd` (the program named by `COMSPEC`, else `cmd.exe`) is found the same way, as in 1.x. The guard's own files (the automatic copy a hook rewrites to, and `POLICY.md`) are never found this way.
- The library calls `run`, `run_shell` and `run_auto` take the calling process's parent (and, for `run_auto`, its live ancestors) as the owner, and identify it by process identifier when the call starts. Windows can reuse an identifier after its process has exited, so a call made after the parent has exited can watch an unrelated process that has taken the identifier. The README describes the owner rule; a program that can outlive its parent should start `process-tree-guard` as a child instead of calling the library.

## Response

Reports are acknowledged within seven days. A fix, or an explanation of why the report is not a vulnerability, follows as soon as the issue is understood. Reporters are credited in the release notes unless they ask not to be.
