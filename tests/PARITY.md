# Check table

This table lists every check (102 guard checks, 11 lockout checks, 26 automatic mode checks, 148 battery checks and 42 Google Antigravity hook checks) and the Rust test that covers it. The suite began as a port of an earlier behaviour suite, item for item. A check in a group prints its identifier (`G`, `L`, `U`, `B` or `A` and a number) with PASS or FAIL, so a run traces back to this table; use `cargo test --release -- --nocapture` to see every line. Some tests assert directly and print no line when they pass: G1, G10, G16 to G18, G21, G25 to G27 and U1 to U9. A failure of one of them names the test, which this table gives for each identifier.

Program names. The guard has two names: `process-tree-guard` (from 2.0.0) and `process-guard`, its 1.x alias kept through all of 2.x. The checks that predate the rename run against the new names: the built guard, and the copies the tests make in temporary folders (`process-tree-guard.exe` and `process-tree-guard-auto.exe`). The checks added with the rename (G29 to G34, U14 to U18, B117 to B122, A26 to A32) cover each alias path under both names, and the file names that are neither. No test depends on the file name cargo gives the built guard; each copies it to the names it needs.

Programs and layouts. The crate builds four programs: the full command `process-tree-guard`, the deadline role `process-tree-guard-deadline`, the hook role `process-tree-guard-gate` and the contain role `process-tree-guard-contain`. The checks added with them (G17, G26 and G27 for the programs, G35 to G41, G45, U19 to U22, B123 to B127, B131, A33 to A38) run each role as cargo built it in this run, in two layouts made in temporary folders: the install layout (the full command in `bin`; the roles and the automatic copy of the deadline role in `libexec`) and the flat layout (every program in one folder, `bin`). Where a role is compared with the full command, the same observations are made of both and the table says which. Checks that need the automatic copy to be named in a rewritten line run in a folder whose path uses only the characters the hook accepts (the A series, as before).

Shell, library and role. G42 checks that the shell the guard chooses is found as in 1.x: by the `PATH` search (current folder first unless `NoDefaultCurrentDirectoryInExePath` is set) and by `COMSPEC`, each against a control in which no helper copy is reachable. G43, G44 and B130 check the library's owner rule: the calling process's parent is the owner. G45 checks the owner rule of the deadline role, as a program. G43 and G46 to G49 check each of the four library calls (`run`, `run_shell`, `run_auto` and `run_hook`) for its results and its errors. B126 (extended), B128, B129 and A39 check that the policy file is found from the program's own location, and that the hook's rules follow the role of the program and not its file name.

Extendable runs. The checks added with them (G50 to G86, U23, B132 to B147, A40, A41) start the guard with `--extendable` and use the helper to ask the run for time, from inside the job and from outside it. The scaled tests use a unit of one second (three seconds for the three cases, G51 to G53) and a grace G of 1.5 seconds: a run planned to end at `n` units must not end before `n` units (always asserted) and ends by `n` units plus G (reported, not asserted, under `PROCESS_TREE_GUARD_TIMING=info`). A structural upper bound is always asserted besides (`bound` in the output), and continuous integration (CI) runs with `PROCESS_TREE_GUARD_TIMING=info`, so it is the bound that CI enforces: one set just under the first wrong answer. A request cannot be made after the boss's deadline, so a run held up by one ends by the boss's deadline plus the hold plus 6 units for the end of the run (the guard waits at most 5 seconds for the tree to go, and half a second for the notice). Where the wrong answer ends a fixed time after a grant (cases 1 and 2), the bound is counted from the time of that grant in the log (read with the start time of the run), so that a helper that is late does not move it: case 1 must end before 6 units after the grant for A (which is when it would end if the child that exited still held the run), and case 2 before 7 units after the grant for A (A's 6 and a unit for the end of the run). Neither case tells a hold of the right length from a hold that is too long when the child that holds the run is a guard, because that guard ends its own command at its own deadline: a hold that was added to the boss's deadline and not compared with it would also end with A's guard at 6 units after its grant. The length of a hold is proved by the checks on a hold that one process makes (`check_hold`: G54, G56, G57, G63, G74 and G84), and by the variant of case 2 in G52 in which the hanging child is a process with no deadline of its own, which ends 6 units after its grant and not at 8 units from the start, where a hold added to the boss's deadline would end it. Case 3 must end before 5 units, a live child's hold, a process that outlives its hold and `extend` before the boss's deadline plus their seconds plus 6 units, and a dead child's or a returned library call's hold before the boss's deadline plus 6 units. These bounds are wide, and say so: counted from the start of the run, 26 units for a hold of 12 under a boss of 8, so a hold that is too long by less than 14 units passes it, and they catch only a gross defect in the length of a hold. What catches a hold of the wrong length, in every run and whatever the timing setting, is a second pair of bounds for a hold that one process makes, counted from the grant that the log records (`check_hold`; G54, G56, G57, G63, G74): the run is not over before the grant plus the seconds granted (less a quarter of a second), and is over before 2 units after that. A late request moves the grant and not the length of the hold, so these hold on any load. For a hold that was released (a dead child's, a returned library call's) nothing is left of it, and the run ends within 2 units of the boss's deadline (G56, G67). A defect smaller than 2 units in a hold, or one that is not in the log, is caught only on a run with the timing setting off. The bounds hold on a machine that is busy but not oversubscribed, not on any load: a helper that is starved of the processor for longer than the boss's deadline asks too late, is refused ("the run has ended"), and the test then fails on a lower bound, and on such a machine a correct run can also end after a structural bound. A defect smaller than the time a helper may take to start (up to the boss's deadline) is caught only on a run with the timing setting off. A test whose helper has to start and ask inside the boss's deadline gives the boss 8 seconds or more (6 in cases 1 and 2, whose boss has 2 units of 3 seconds). The unit tests in `src/extend.rs`, `src/engine.rs` and `src/cli.rs` cover the wire format, the deadline rule, a request after the deadline, the limit of holds (256 in all, 8 for one process), the withdrawal of a grant whose reply the client did not take, the flags the channel is made with (message mode, no remote clients, no outgoing buffer, the first-instance flag on the first instance and no other), the check that a client started before it connected, the poll that releases a holder that has exited (with no message from the job), the interval of that poll, the release of a hold at its process's request and what it costs of the rate limit, the audit file that a follower stops from being renamed (the earlier lines kept, the notices, the file that takes no more lines and resumes), the audit file that cannot be written (a reader that denies write sharing is refused at its open; lines held, told of at once, written late in order with a notice of the counts; lines past the limit of those held counted; a run that ends blind says so; the file copy of the log written again with no further line to wake it; the file that cannot be turned over, which blocks the run before it is full, is retried with no line, and stops a run from starting if it is blocked at the start; a blocked file refuses a request and lets a release through), renewal in time (a run held up for as long as its process renews, each request capped), the client that has closed its end of the pipe, the time a client connected as `accept` stamps it from the clock (compared with a clock read in the test, with the client already there and with the server waiting, and a stop with no client), a hold for each call of one process (renewal, release and the hold of `extend` independent), the order of the environment block, the rate limit and its table (including the forgetting of processes that have exited, and the refusal for a full table), the budget and coalescing of refusal lines, the queues of the log and a destination that stalls, the arguments, the time and log formats, the numbers the log records, the escaping of log values (the format characters among them), the check of the channel name, a channel that stopped serving (closed to grants, not past its deadline), the bounded log file, the windows of refusals of a process that is never idle (one summary for each window while it asks, and every counted refusal in a line), the range of a reply (a client refuses what is out of range) and the verification of a client that was created after the connection or has gone before the reply (`evaluate` driven directly, with the time of the connection given; the time itself is the one `accept` stamps, which has its own test, so the creation-time half of the verification is covered at both ends). The section "The deadline rule and its tests" at the end of this file maps each sentence of the rule in `POLICY.md` to the tests that prove it.

The exception above the cap. The checks added with it (G87 to G102, L1 to L11, U24, U25, B148, A42) and the unit tests in `src/auth.rs`, `src/cli.rs`, `src/engine.rs`, `src/extend.rs` and `src/lockout.rs` cover a `--max-extension` over 21600, which needs the signed-in user's password at the start of the run. No test shows a prompt to the person who runs the suite: the desktop of the machine that runs the suite belongs to whoever is signed in, and a secure desktop prompt would take it over. Every run over the cap in the tests says `--authenticate console` and has a standard input that is null, a pipe or a file, except G95 (the desktop method on a window station that is not visible), G97 and G98 (the console method in a pseudo console that nobody sees); the others are refused with the reason (G87 to G89, G94, U25, A42), a run at or below the cap is shown not to ask (G92), the helpers that start a guard panic on a cap over the default without the console method (G93), and G93 scans the test sources for a run over the cap that does not say so, and the source of the module for a stub in a program that is released.

The desktop method (G95). The one run that uses it does so on a window station that is not visible, which the test helper makes and checks before it starts anything, so the real path of the test for a person being present (the session, the flags of the window station) is run. G95 is the one test whose failure mode is a real prompt: if that test were defective the real secure prompt could appear on the desktop of whoever runs the suite, and where it would appear is not established. G95 therefore runs only when `PROCESS_TREE_GUARD_RUN_DESKTOP_PROMPT_TEST` is set (the continuous integration and release workflows set it; `CI` alone does not, because machines where a person sits set it too) and prints NOT ASSERTED otherwise. The helper waits only ten seconds for the refusal, which is immediate, and step 11 of the manual check runs G95 once with the screen watched. On a host whose test process runs in session 0 (a build agent installed as a service) G95 accepts the reason that the process runs in session 0, which the guard reports before the window station.

The console method, called for real (G97 and G98).
- G97: the console prompt is called once in a pseudo console that the test helper (`pty-guard`) makes. It presses Enter every 300 milliseconds, so every question is answered with an empty line, which is turned away before any logon is tried (no failed logon is written to the audit log of the machine). The check sees the message and the product name as the target of the prompt on the console (the text of the system's own, localized, question is not matched), the three attempts in the log, the third saying that none is left, and neither the error for invalid flags nor any other failure of the call. A defect in the flags of the call, or in the way the second and third prompt are made, shows there and nowhere else.
- G98: the watch on the process that started the guard is run end to end. The helper (`pty-guard-quiet`, which types nothing) runs `cmd.exe` in a pseudo console, `cmd.exe` starts the real guard in the background with the console method and ends after about three seconds, and the check sees one refusal at attempt 1 that says nobody is waiting for the run, the command never run, and the guard ended long before the 300 seconds of the prompt. A defect in the wiring of the starter's handle (opened for the prompt, watched during the wait, kept for the run) shows there and not in the unit tests, which use stubs.
- Where no pseudo console can be made the check says NOT ASSERTED, unless `PROCESS_TREE_GUARD_REQUIRE_PSEUDO_CONSOLE` is set.

Turns and locks. G97 and G98 take turns, because a guard keeps the right to have a prompt open in its session: among their threads, and among the processes of the session through a named mutex of the session that every suite takes (`session_turn` of the test helpers). They also try again, up to six times 12 seconds apart, when the guard is refused the lock by a program that is not a test (a real prompt, a manual check, a guard in its cool-down of 10 seconds), and are then NOT ASSERTED, or fail where `PROCESS_TREE_GUARD_REQUIRE_PSEUDO_CONSOLE` is set. The helper that runs the guard in a pseudo console puts the program in a job and returns only when every process it started has ended, so that a guard left behind by a starter that exited still holds its lock only while its test is running. Do not run two test suites, or a step of the manual check, at the same time in one Windows session: the prompts of the guard share one lock per session.

A guard that another guard started. Whether it is the command of automatic mode (U25, A42) or runs inside a guard that is not extendable (G94, G99), it is refused before anything is shown, for the guard above it by file name, and a chain whose parents have exited is refused by job (G100); a copy of an ordinary program under the name of the desktop shell in another folder does not end the search of the names (G101). The checks that expect the refusal for standard input take the reason from the surroundings of the suite (`nobody_reason` in `tests/common/mod.rs`): where a guard is above the tests (the command that runs them is `process-guard -- cargo test`, or a shell is wrapped by the automatic wrapper) every guard they start is refused for that, and G95, G97 and G98 are NOT ASSERTED, or fail where their variable is set. Cargo puts the tests it runs in a job that kills them when it closes, which the guard takes for the job of a guard, so each test program puts its own process in a job of its own that kills nothing, nested in the job that cargo made (`leave_the_job_of_the_runner` in `tests/common/mod.rs`), before it starts a guard. G100 starts a chain of shells in which a parent has exited before the last one runs the guard, once under a guard (refused as a run that another guard started, which the names above it cannot show) and once with no guard around it (refused for its standard input, or for the lockout record where the account has none that can be used, in any surroundings).

The lockout (L1 to L11, G102, and the unit tests in `src/lockout.rs` and `src/auth.rs`). The record of the machine is made by `process-tree-guard create-lockout-record` from an elevated terminal. - the text of the prompt: the product, then the fields to check in the order command line, program, account and parent process as the system reports it, then what the cap means, the deadline the run starts with and how to refuse for each method, with no cancel on the console; the hours rounded up to two decimals with the seconds beside a figure that is not exact; each field cut at its own limit once written out (command line 140, program 80, account 40, parent 80), the command line keeping its start and a path keeping its end with its file name, with a count of what was left out; the whole message under 1,024 characters, the limit of the dialog, when all four fields are the longest escapes (controls, format characters, blanks, marks and every letter of another script written out, brackets escaped); a note when a field has such a character and none when it has not; paths and quotes not doubled;
- the split of a user name by its form; the comparison of the security identifiers (only the guard's own user approves); the turning away of a name that is not the guard's own account before any logon; the sorting of what the system says to a logon and to a look up (as a pure function; no test calls `LogonUserW`, so none writes a failed logon to the audit log of the machine);
- the test for a person being present (session 0, a missing session or window station, a window station that is not visible, each with its own reason, and what it reads from this process, also in a copy of the test executable on a window station of its own);
- the names above the guard (every program of the guard, any file name ending in `-auto`, and the names that are not taken for one: `a_run_that_another_guard_started_is_refused_before_any_prompt_and_says_so` asserts that `guard_above` gives nothing for them), the end of the walk up the parents (the six programs of the system end it at their system paths, `explorer.exe` in the Windows folder and the other five in `System32`, and a copy of an ordinary program under one of those names in another folder, a folder under the Windows folder that is not the system path, the system path of another of the six, a folder whose name only begins like the Windows folder, a path that cannot be read and a name that is not one of the six do not: `the_walk_ends_at_the_programs_at_their_system_paths_and_goes_past_a_copy_under_the_same_name`) and the job (a copy of the test executable put in a job that kills on close is in a guard job, one put in a job that kills nothing is not, whatever job it was in before);
- the bounded waits (the prompt and the check of the credentials, both ended early by the exit of the process that started the guard), the right to open one prompt at a time, the zeroing of the buffers on the path of every verdict and of the authentication buffer, the zeroing of the live buffers by the panic hook (a panic on a thread under `catch_unwind`, with the buffer listed while it is alive and no longer listed once dropped);
- the test for a console input buffer (the null device, an anonymous pipe and a file give false; where the run has a console, its screen buffer, which answers `GetConsoleMode`, gives false and its input buffer true), and the console prompt itself, begun in a copy of the test executable whose standard input is the null device (`the_console_prompt_is_refused_before_anything_is_written_when_standard_input_is_not_a_console`), which is refused before the lock is taken or anything is written, whatever guard is above the tests;
- a prompt left open at its limit, which is refused at once with no cool-down (and a failure of the system after a prompt was shown, which keeps it), and the text shown being the same for an argument that holds the written-out form of a character as for the character itself: a backslash before `u{` is written as `\u{5c}`, any other backslash is shown as it is;
- the sizes the prompt fills, the user of a token read as the process's own, the log opened before the job, and the refusal of a cap over the default that nobody approved.

Not asserted anywhere:
- the desktop prompt in any form: that the system accepts the flags of the call, shows the dialog, reports a cancel and a wrong password as the code expects, and returns the password (the manual check, steps 1 to 5, is the only evidence);
- that a process which puts itself in a job of its own is refused by job (it is not: the job test reads the innermost job);
- what Esc, Ctrl+C and Ctrl+Z with Enter do at the console prompt (the manual check, step 6, records it);
- the form of the user name for a Microsoft account and for an Azure Active Directory (Azure AD) account;
- that the secure prompt returns the password in clear text for each type of account;
- that the dialog shows the whole command line, and how it shows an ampersand or a percent sign;
- an approval with the domain controller out of reach;
- that the shell echoes again after a console prompt that ended by timeout;
- that the functions of `credui.dll` are found on every supported Windows (nothing links the library, so the build cannot show it);
- that a scheduled task or a remote shell is refused;
- that the dialog goes when the process exits.

These are the manual check in `CONTRIBUTING.md`.

The helper executable `src/bin/testkit.rs` stands in for every child process: sleepers, exit codes, standard stream relays, argument reporters, markers that record their process identifier, wide and deep process trees, bulk output, children started with given creation flags, requests to an extendable run (by the library call, by raw messages, and with the channel's access list read back) and groups of children started together.

## Differences from the earlier suite

- Children are the helper executable, not an interpreter. Where the earlier suite read an interpreter's output (a list of arguments, the length of the argument list), the helper prints a JSON array of the arguments and the test compares it exactly. B73 therefore checks that the child receives exactly `--timeout`, in place of an exit code equal to the argument count.
- G26 asserts the operating system error text `WinError 5`, which the helper prints when the breakaway creation flag is refused.
- B33 and B34 start helper sleepers rather than `ping.exe`; B54 names the copied executable `kit copy` followed by a u with diaeresis.
- B55 asserts the exit code only, as the earlier check did in effect; the output bytes are printed for inspection.
- B76 compares with an earlier guard only when `PROCESS_GUARD_PREVIOUS` names its executable, and then only reports the ratio.
- U9 copies the guard into a private folder as `process-tree-guard.exe` and `process-tree-guard-auto.exe`, so nothing is written beside the build output. U18 does the same under each of the two names.
- Fixed delays that gave a child time to start (G19, G20, G21, G25, B36 to B41) became waits for the child's marker, with generous limits, so a slow process start cannot fail a run. The deadlines of G19 and G21 were raised to match.
- B47 and B50 count output bytes without keeping them.
- B79 to B84 keep the earlier duplication: the three PreToolUse checks run twice under the same names.
- Bounds on time and load (B15 to B18 elapsed, B43 elapsed, B75, B77, G18 elapsed, U6 elapsed, U6b elapsed and the A16 to A18, A24, A30 and A37 bounds) are asserted unless the environment variable `PROCESS_TREE_GUARD_TIMING` (else its 1.x name `PROCESS_GUARD_TIMING`) is `info`, which reports them without failing. Exit codes and process cleanup checks are always asserted.
- U6 uses `PROCESS_TREE_GUARD_AUTO_TIMEOUT`, U6b the legacy `HARNESS_AUTO_TIMEOUT`, and the end to end Google Antigravity checks `PROCESS_TREE_GUARD_AUTO_TIMEOUT`; the 1.x name `PROCESS_GUARD_AUTO_TIMEOUT` is covered by U17 and A30. The tests that set a deadline variable first remove all three from the child's environment, so the settings of the machine running the tests cannot change a result.
- Battery tests share one lock, so they run one at a time whatever the test thread count.
- G39 is asserted only when the tests are built for the MSVC target, the only supported one, because the version resource is linked only there; on another target it writes a `NOTICE` line to standard error (not captured by the test harness) and asserts nothing, unless `CI` or `PROCESS_TREE_GUARD_REQUIRE_RESOURCES` is set, when it fails instead, so a build on the wrong toolchain cannot pass. G40 checks the same resource bytes on every target, by placing them in a scratch executable with the system update calls and reading them back with `GetFileVersionInfoW` and `VerQueryValueW`. Those two functions are loaded from `version.dll` in the system folder when first used, so the tests link on toolchains that ship no import library for it.
- B130 shares the battery lock, so no other test starts processes while it waits for the parent's process identifier to stay unused. The first case keeps a handle to the exited parent, which keeps its record and its identifier; the second closes it.
- G59 runs `--timeout 21600` with `--max-extension 21600`, the largest cap that needs no password; the larger caps are G87 to G102 and L1 to L11, and no integration check runs a cap over 21600 to its end because none can be approved without a person (the unit test in `src/engine.rs` does, with a stub answer that exists only under `cfg(test)`).
- The role checks (G17, G26 and G27 for the programs, G35 to G38, G45, U19 to U22, B123 to B127, A33 to A38) compare a role with the full command by making the same observations of both and expecting the same answers; B125 compares the answers themselves, in one folder, after reading the deadline role's automatic copy as the full command's.
