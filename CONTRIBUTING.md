# Contributing

Issues and pull requests are welcome.

## Requirements

- Windows 10 or 11, 64-bit.
- A stable Rust toolchain for the Microsoft Visual C++ (MSVC) target, with the Visual Studio Build Tools. Make it the default toolchain of the machine that runs the tests: the version resources of the programs are linked only for that target, so on a GNU's Not Unix (GNU) toolchain the check G39 cannot run. It prints a `NOTICE` line to standard error when it is skipped, which shows on a plain `cargo test`, and it fails instead when `CI` or `PROCESS_TREE_GUARD_REQUIRE_RESOURCES` is set; set the second one on your machine to make sure the suite covers the resources.
- Git Bash, Windows PowerShell and `cmd.exe`, which the tests use.

The library and the programs build with the Rust version that `rust-version` in `Cargo.toml` declares (1.78), and the continuous integration job `minimum-rust` checks that on every change; the tests are run with the current stable toolchain only. A change that needs a newer Rust raises `rust-version` in the same commit, and says so in the changelog.

## Rules for changes

- `cargo test --release` passes. On a busy machine, `PROCESS_TREE_GUARD_TIMING=info` reports the timing bounds instead of asserting them; say so in the pull request if you used it.
- No new dependencies. The guard uses only the Rust standard library and direct Windows system calls, so that the whole program can be reviewed in one sitting.
- A change in behaviour comes with a test, and a new check gets the next identifier in its series (`G`, `L`, `U`, `B` or `A`) and a row in `tests/PARITY.md`.
- Tests take every program from the binaries cargo built in the run (`CARGO_BIN_EXE_*`), never by a file name in the build folder, so a stale file left there is never picked up.
- Tests do not depend on the file name of the built guard. They copy it to the names they need (`process-tree-guard` and the 1.x alias `process-guard`, each with an `-auto` copy where the check needs one) in a temporary folder.
- The README is updated when a flag, exit code, guarantee or limit changes.
- No test shows a prompt to the person who runs the suite.
  - A run over the default cap (`--max-extension` over 21600) in a test says `--authenticate console` on the same line and has a standard input that is null, a pipe or a file. Check G93 scans the test sources for one that does not, and the helpers that start a guard refuse a cap that a test builds when it runs.
  - G95 is the one test that uses the desktop method. It does so on a window station that is not visible, which the test helper makes and checks first. It is also the one test whose failure mode is a real prompt: if the guard's test for a window station that is not visible were defective, the secure prompt could appear on the desktop of whoever runs the suite, and where it would appear is not established.
  - G95 therefore runs only when `PROCESS_TREE_GUARD_RUN_DESKTOP_PROMPT_TEST` is set (the continuous integration and release workflows set it; `CI` alone does not, because it is also set on machines where a person sits), and reports NOT ASSERTED otherwise. Its helper waits only ten seconds for a refusal that is immediate, and step 11 of the manual check runs G95 once with the screen watched.
  - No test writes to the lockout record of the machine it runs on unless `PROCESS_TREE_GUARD_RUN_LOCKOUT_RECORD_TEST` is set, in an elevated process (the continuous integration and release workflows set it, after they run `process-tree-guard create-lockout-record` once). L3 to L11 are the tests that do; they leave the machine with a fresh record, and print NOT ASSERTED where the variable is not set. They remove the whole `ProcessTreeGuard` folder, which holds the record of every account of the machine, so they reset every account's lockout there: set the variable on runners that are used for the tests alone (the workflows), not on a machine where people use exceptions. A guard that a test starts over the cap is refused for a record that is missing, cannot be used or is locked out before it reaches a prompt, so on a machine where the step has not been run G95, G97 and G98 print NOT ASSERTED too (or fail, where their variable is set), and G87, G89 and G100 assert the refusal with the reason of the record; run the step from an elevated terminal to assert the rest.
  - G95, G97 and G98 also report NOT ASSERTED where the host cannot make a window station or a pseudo console, unless `PROCESS_TREE_GUARD_REQUIRE_WINDOW_STATION` or `PROCESS_TREE_GUARD_REQUIRE_PSEUDO_CONSOLE` is set, which the continuous integration and release workflows set.
  - The unit test that reads the access lists and owners of the real folder of the programs' data and the folders above it reports NOT ASSERTED, with what is not met, on a machine that does not meet the requirements of the check (a hardened or customised machine), unless `PROCESS_TREE_GUARD_REQUIRE_PROGRAM_DATA_CHECK` is set, which the continuous integration and release workflows set. The desktop part of L2 reports NOT ASSERTED where `PROCESS_TREE_GUARD_RUN_DESKTOP_PROMPT_TEST` is not set or no window station can be made.
  - G97 and G98 are the two tests that use the console method for real. They do it in a pseudo console that the test helper makes, in which no logon is ever tried: G97 answers every question with an empty line, and G98 types nothing while the process that started the guard exits.
  - Both take the lock that the prompts of a Windows session share, and wait for it: they take a turn that every suite of the session shares, try again for a minute when a real prompt, or a guard that was refused less than 10 seconds before, holds the lock, and are then reported NOT ASSERTED (or fail, where `PROCESS_TREE_GUARD_REQUIRE_PSEUDO_CONSOLE` is set). Do not run two test suites, or a step of the manual check, at the same time in one Windows session: the prompts of the guard share one lock per session.
  - A guard that another guard started is refused before its window station or its console is looked at, by the file names above it or by the job it is in. When the suite is run under a guard (`process-guard -- cargo test`, or a shell wrapped by the automatic wrapper), G95, G97 and G98 report NOT ASSERTED (or fail, where their variable is set) and the other runs over the cap are refused for the guard above them instead of for their standard input. G94, G99, G100, U25 and A42 assert that refusal in any surroundings.
  - Cargo puts the tests it runs in a job that kills them when it closes, which a guard takes for the job of a guard. Each test program therefore puts its own process in a job of its own that kills nothing, nested in the job that cargo made, before it starts a guard (`leave_the_job_of_the_runner` in `tests/common/mod.rs`).
  - Two unit tests in `src/auth.rs` make checks that need no prompt and hold under any guard: one checks the detection of a window station that is not visible on one of its own, and one begins the console prompt with a standard input that is not a console and sees it refused before anything is written.
  - Run the suite from a terminal that is not under a guard to assert the rest.

## Manual check of the prompts

The sign-in prompts for a cap over the default are not exercised by the tests with a real password, except for the refusal on a window station that is not visible (G95), the console prompt in a pseudo console with empty answers (G97) and the same prompt left unanswered in a pseudo console while its starter exits (G98).

Before a release that changes `src/auth.rs`, `src/lockout.rs` or `src/sys.rs`, run these steps on a machine where someone is present, signed in with an account that has a password, from the interactive desktop (steps 9 and 10 are the exceptions). Run them in a terminal that is not under a guard and not in a job that kills its processes when it closes: a guard that another guard started is refused before anything is shown.

Use a short command, for example `cmd /c echo ran`, and a deadline under 30 seconds. Write down what you see where a step says so; the documents say what is expected, and the steps are what confirm it. Steps 2, 4 and 7 can put wrong passwords on the record; run them after the other steps.

1. Desktop prompt, right password: `process-tree-guard --extendable --max-extension 86400 --timeout 20 -- cmd /c echo ran`. A secure desktop prompt appears, captioned Process Tree Guard.
   - It names first the command line, the program, the account whose password it asks for and the parent process as the system reports it (the nearest one), each in square brackets. Then it says that the processes of the run may each ask to keep it alive for up to 24 hours at a time and may renew without a total limit and that the run starts with a deadline of 20 seconds, and it lists only your account.
   - The pass criterion for the text is that the Command line field is fully visible in the dialog; if the dialog clips the text, write down where it is clipped and which field is the last one shown.
   - Enter the password. The command prints `ran`, and the log has one `decision=exception-approved` line with `attempt=1`.
   - Record the result for each type of account you can try (a local account, a Microsoft account, a domain account): the password that the secure prompt returns must be accepted. If the run is refused with the reason that the answer holds a protected form of the password, the desktop method cannot approve for that type of account, and the documents must say so before a release.
   - Run it a second time with `--shell cmd --command-b64 TEXT`, where TEXT is the Base64 of `echo a && b %PATH% ` followed by 300 letters x (in PowerShell: `[Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes("echo a && b %PATH% " + ("x" * 300)))`).
     - The text is given as Base64 because a shell changes `&&` and `%PATH%` on the command line before the guard sees them.
     - Write down what the dialog shows: whether `&&` and `%PATH%` appear as typed (if the dialog consumes an ampersand, the display must be fixed by doubling it for the dialog only), and that the command line ends with how many characters were left out.
   - Run it a third time with a copy of `cmd.exe` whose name begins with the Cyrillic letter U+0441 (so that it looks like `cmd.exe`) and confirm that the dialog shows that letter written as `\u{441}`, with the note about characters outside basic Latin, and not as a letter.
   - Where you have a host that puts its terminal in a job that kills its processes when it closes (some editor terminals and continuous integration runners), run the command from that terminal too and confirm that it is refused with 125 and the reason that another guard started it, with no prompt.
2. Wrong password three times: repeat, and enter a wrong password each time.
   - After the second and third the prompt shows that the user name or password is incorrect; the second and third prompt are shown and are not cancelled at once (all the calls of the prompt are made on one thread, and this is the only step that shows it for the desktop method).
   - After the first wrong password confirm that the text of the prompt ends with "1 wrong password on record within six hours; the third stops this prompt for six hours." and is not clipped (it is the last sentence of a message of up to 1024 characters, so a dialog that clips loses it first); after the second, that it ends with "2 wrong passwords on record within six hours; the third stops this prompt for six hours." Write down any dialog that clips it.
   - The run exits with 125 after the third, the command never runs, and the log has `decision=exception-refused` with `attempt=1`, `attempt=2` and `attempt=3`, the last saying no attempts are left.
   - Do this last of steps 1 to 11, or on a local account made for the check, and once only: each failure counts toward the lockout of the system for the account, and the third within six hours also starts the lockout of the guard for it, in which no prompt is shown for that account for six hours (the run prints "locked out after 3 wrong passwords"), so every later step that needs a prompt would be refused. To end it early an administrator removes the record as in step 12 and runs the step again.
3. Cancel: repeat and cancel. The run exits with 125 and the log has one refusal with `attempt=1` that says the prompt was cancelled.
4. Personal Identification Number (PIN): if the account has a PIN, repeat, choose the PIN tile and enter the PIN.
   - Either the answer unpacks to a name and a password, and the logon is tried (it is sent to `LogonUserW` as a password if the name is the account's own, and counts toward the lockout; a wrong password also counts toward the lockout of the guard, see step 2), or it does not, and the log has an attempt with the reason that the answer could not be read as a user name and a password; both count as an attempt and the prompt is shown again.
   - Write down which one happens; the documents say only that a PIN is not expected to unpack to a password.
   - If the account has a smart card, choose it and record that it counts as a failed attempt in the same way.
5. No answer, and a starter that goes: repeat and leave the prompt alone.
   - After 300 seconds the run exits with 125 ("no answer within 300 seconds"). Look at the screen and write down whether the dialog is gone or still there once the guard has exited; the documents do not claim that it goes until this step has been run. The guard exits as soon as the 300 seconds are over, without the 10 seconds of waiting that follow another refusal, so the dialog must not stay open for any time after the error is printed; if a password can still be typed into it, record that.
   - Then start the guard from a `cmd.exe` window, and while the prompt is open end that `cmd.exe` in Task Manager. Within a second the run is refused ("the process that started the run exited"), with `attempt=1` in the log, and the prompt should go; write down what happens to the dialog.
6. Console prompt: from a real terminal, run the same command with `--authenticate console`.
   - The message is written to the console once, then the prompt asks for the password alone and names your account (write down the form of the name); confirm that no question for a user name is asked. The right password runs the command.
   - Run it again and press Esc, then Ctrl+C, then Ctrl+Z and Enter, and write down what happens (the documents do not claim a result for these keys until this step has been run): Esc and Ctrl+Z with Enter may leave the prompt waiting or give an empty answer that uses an attempt, and Ctrl+C may end the guard, which also refuses the run; the message tells the user to leave the prompt unanswered for 300 seconds, or to close the console, to refuse the run.
   - Store a generic credential with `cmdkey /generic:"Process Tree Guard" /user:x /pass:y`, run the console method again, confirm that the prompt is still shown and does not return the stored credential, and delete it with `cmdkey /delete:"Process Tree Guard"`.
   - Run it again with standard input piped (`echo x | process-tree-guard ...`) and confirm that it is refused with 125 and a reason that names standard input, with no prompt.
   - Command history: the guard clears the command history that the console keeps for its own executable name after every console prompt. After a console prompt answered with a known test password, in the same console press F7 and run `doskey /history`, and read the history kept for `process-tree-guard.exe` (for example with `GetConsoleCommandHistoryW`, or by running the guard again and reading the F7 popup). Record whether any password line is present; a line that is present means the call is missing or does not clear it, and is a defect to be fixed.
   - Ctrl+C: run the console method again, press Ctrl+C while the prompt waits for the password, and confirm that the shell echoes the characters you type afterwards. The guard puts the console mode back on a control event while the prompt reads, so an echo-off shell is a defect; ending the guard from Task Manager is outside this and may leave the mode as it was set.
   - Finally let the console prompt time out (leave it alone for 300 seconds), or end the process that started the guard while it is open, and confirm that the shell echoes the characters you type afterwards; if it does not, the console mode was not restored (type `cmd /c echo on` or open a new window, and report it).
7. Microsoft account and Azure Active Directory (Azure AD) work or school account: on a machine signed in with a Microsoft account, and on one signed in with an Azure AD account, repeat step 1.
   - Confirm that the user name the prompt returns (`MicrosoftAccount\name@example.com` or the local account name for a Microsoft account; `AzureAD\Name` for an Azure AD account) is accepted by `LogonUserW`. Write down the form of the name that came back in each case.
   - If it is not accepted, the run is refused after three attempts (each counting toward lockout; a wrong password also counts toward the lockout of the guard, see step 2), and the form of the name must be changed: for an Azure AD account, pass the user principal name with a null domain.
8. Nothing at or below the cap prompts: run `process-tree-guard --extendable --max-extension 21600 --timeout 20 -- cmd /c echo ran` and confirm that no prompt appears and the command prints `ran`.
9. Nobody present: run the step 1 command with `--authenticate desktop` and a deadline under 30 seconds (a) from a scheduled task that is set to run whether or not the user is logged on, and (b) over a Secure Shell (SSH) or Windows Remote Management (WinRM) session.
   - Record that each exits 125 at once with "session 0" or "no interactive window station" in the reason, that no dialog appears on the desktop and that the command does not run. The README names only what this step confirms.
   - If the reason is instead that another guard started the run, the host put the shell in a job that kills on close and the step has not exercised the test for a person being present.
   - Record that, and try a host whose shell is not in such a job (or rely on the unit tests of the test for a person being present and G95).
10. Domain controller out of reach: on a machine that is joined to a domain and signed in with a domain account, disconnect it from its domain controller (the network off), repeat step 1, and write down whether the name that the prompt returns is accepted by the look up and by `LogonUserW`; if the run is refused with a look up error, the documents' statement about the form of the name must be changed.
11. The test on a window station that is not visible (G95), watched: with the screen in view, set `PROCESS_TREE_GUARD_RUN_DESKTOP_PROMPT_TEST=1` (in a Command Prompt, `set PROCESS_TREE_GUARD_RUN_DESKTOP_PROMPT_TEST=1`), then run `cargo test --release --test guard g95 -- --nocapture` once, on a machine where someone is present and the desktop is unlocked.
   - Record that nothing appears on the desktop and that the test passes (a line NOT ASSERTED means the variable was not seen).
   - The test asserts the reason that the process has no interactive window station or, on a host whose test process runs in session 0 (a build agent installed as a service), that it runs in session 0, which the guard reports first.
   - If a prompt appears, record where (on the desktop, on the secure desktop, or nowhere), end the test, and treat the guard's test for a window station that is not visible as defective: G95 is the one test whose failure mode is a real prompt, and where such a prompt would appear is not established until this step has been run.
12. The record of wrong passwords and its setup (done once, by one person, on a machine where the person is an administrator). Steps 1 to 11 need the record: run this step first on a machine that does not have one.
   - From a terminal that is not elevated, run `process-tree-guard create-lockout-record`. It exits with 125 and says that it needs administrator rights.
   - Run the step 1 command and confirm that it is refused with 125 and "no lockout record exists for this account; an administrator must run: process-tree-guard create-lockout-record" followed by the name of your account as the system writes it (`DOMAIN\user`), with no prompt.
   - From an elevated terminal run `process-tree-guard create-lockout-record` (the alias `process-guard create-lockout-record` is the same command; name the account, as the refusal does, when the person who elevates is not the person who asks); when it is run from a deployment tool as the system account, or as local service or network service, always name the account (`process-tree-guard create-lockout-record ACCOUNT`), because with no argument the step is refused for those accounts. It prints three lines: `created folder`, `created record ... for ...` with the security identifier of the account, and `verified:` (a line that ends with the sentence "An account in the Administrators group is not protected from its own elevated programs; see SECURITY.md."). Run it again: it prints `folder ...: permissions set`, `record ...: permissions set` and `verified:`, and makes nothing.
   - Run the step 1 command again and confirm that the prompt is shown (the record is in place), then cancel the prompt (a cancel adds nothing to the record).
   - Compression: from an elevated terminal run `compact /c` on the record, then the step 1 command, and confirm that it is refused with 125 and "is compressed, so the room for the next record cannot be allocated", with no prompt. Run the step and confirm that the record is uncompressed (`compact` lists it without a `C`), and that the step 1 command shows the prompt again; cancel it.
   - Look at the permissions on the folder `ProcessTreeGuard` in the folder of the programs' data (`C:\ProgramData` on a usual machine) and on the record. Run `icacls RECORD` and `Get-Acl RECORD | Format-List Owner` (`icacls` does not print the owner): the owner is `BUILTIN\Administrators`, inheritance is removed, the account has `(R,AD)` (`icacls` writes the read rights `Rc` (read control), `S` (synchronize), `RD` (read data), `REA` (read extended attributes) and `RA` (read attributes) together as `R` (read), and `AD` is append data; `(Get-Acl RECORD).Access` names the rights apart) and `OWNER RIGHTS` has `(Rc)` only (no `WD` (write data), `DE` (delete), `WDAC` (write the access list) or `WO` (write the owner) for either).
   - From a terminal that is not elevated, as the signed-in user, in Windows PowerShell 5.1 (`powershell.exe`), add a line to the record with only the right to append (in PowerShell 7 the `FileStream` constructor that takes `FileSystemRights` is not available, and `[IO.File]::Open($path, 'Open', 'Write', 'ReadWrite')` is not usable either, because it asks for the right to write data; do this check in Windows PowerShell 5.1): `$s = New-Object IO.FileStream($path, [IO.FileMode]::Open, [Security.AccessControl.FileSystemRights]::AppendData, [IO.FileShare]::ReadWrite, 8, [IO.FileOptions]::None); $b = [Text.Encoding]::ASCII.GetBytes(([string][char]10) + 'junk' + ([string][char]10)); $s.Write($b, 0, $b.Length); $s.Close()`, with `$path` the file of the record. It works, and the line is ignored by the guard as it is no record; `Get-Content $path` shows it. Then try `Add-Content` (it asks for the right to write, which the account does not have), `Set-Content`, `Remove-Item`, `Rename-Item`, taking its permissions (`icacls RECORD /grant "*S-1-1-0:(F)"`) and making a file in its folder. Each of those must fail with access denied. Write down any that does not.
   - From an elevated terminal give everyone the right to write to the record (`icacls RECORD /grant "*S-1-1-0:(W)"`), run the step 1 command, and confirm that it is refused with 125, "allows more than read and append" and the rights named. Run the step and confirm that it exits with 125, names the rights the record allowed, says "it is not set right in place" and to remove the record, and leaves the record as it was (the step 1 command is still refused). Then remove the record and make it again in one elevated command (`Remove-Item RECORD; process-tree-guard create-lockout-record ACCOUNT`, with the file of the account as RECORD), and confirm that it prints `created record ...` and that the step 1 command shows the prompt again; then cancel the prompt (a cancel adds nothing to the record).
   - Removal: from an elevated PowerShell, `Remove-Item -Recurse -Force` on the `ProcessTreeGuard` folder. Run the step 1 command and confirm the refusal for the missing record, then run the step again. In practice remove and make in one elevated command, so that there is no time in which a user can make the folder first (a user who does denies the exception to every account on the machine until an administrator removes the folder): `Remove-Item -Recurse -Force "<folder>"; process-tree-guard create-lockout-record ACCOUNT`.
   - A folder made first by the user: with the folder removed, from a terminal that is not elevated, make `ProcessTreeGuard` in the folder of the programs' data (`New-Item -ItemType Directory`; any user may). Run the step 1 command and confirm that it is refused with 125 and "the folder of the lockout records is owned by" your security identifier, "so it cannot be trusted" and the step named, with no prompt. From an elevated terminal run the step and confirm that it refuses to take the folder over ("is not taken over"); remove the folder and make it again in one elevated command (`Remove-Item -Recurse -Force "<folder>"; process-tree-guard create-lockout-record ACCOUNT`), and confirm that the prompt is shown; then cancel the prompt (a cancel adds nothing to the record).
   - A record planted by the user in a folder an administrator made first: with the folder removed, from an elevated terminal make the folder with `New-Item -ItemType Directory`, then from a terminal that is not elevated make a file named after your security identifier and ending in `.lockout` in it (`New-Item -ItemType File`; a user may make files there). From the elevated terminal run the step and confirm that it sets the folder right and then refuses the record ("the record ... is owned by" your security identifier, "is not taken over"), and that the step 1 command is refused with 125 and "the lockout record for this account is owned by" your security identifier. Remove the folder and make it again in one elevated command, as above.
   - Another account in the list: from an elevated terminal give the Users group the right to read the record (`icacls RECORD /grant "*S-1-5-32-545:(R)"`; every ordinary account is a member, so the entry gives this account nothing more than it has), run the step 1 command, and confirm that it is refused with 125 and "has an entry for another account or group (S-1-5-32-545)", with no prompt. Run the step and confirm that it exits with 125, says "it is not set right in place" and leaves the record as it was. Then remove the record and make it again in one elevated command, as above.
   - The guard does not follow `SystemDrive` or a drive letter that leads elsewhere (this shows that, and no more): from a terminal that is not elevated, make a folder tree of your own that holds `ProgramData\ProcessTreeGuard` with a file named after your security identifier and ending in `.lockout`, map a drive letter to it with `subst X: PATH` and set `SystemDrive` to `X:` for a shell. Before the mapping is used, remove the `ProcessTreeGuard` folder from an elevated terminal, so that the real place holds no record. In the shell with the mapping and `SystemDrive` set to `X:`, run the step 1 command and confirm that it is refused with 125 and "no lockout record exists for this account", never a prompt and never a lockout or an approval taken from the tree you made (which holds a record for your security identifier); the guard does not follow `SystemDrive`, and opens nothing through a drive letter or the environment. End the mapping with `subst X: /d`, and run the step again from an elevated terminal. This does not try a redirected `C:` itself, which is what a program of the account could do in the device map of its own logon session; that cannot be tried safely on a desktop, because it would break the session. The property that nothing is opened through a drive letter rests on the unit tests that open by the names of the object manager (`the_record_is_found_by_its_name_in_the_object_manager_and_the_file_that_is_opened_must_have_that_name`) and on G93, and no test or step asserts it end to end; do not record a pass for it.
13. A lockout (done once, by one person). Use a local account made for the check and never your own: wrong passwords are real, they count toward the lockout of Windows for the account, and the lockout of the guard is for six hours.
   - From an elevated terminal make the account (`net user ptgcheck * /add`, which asks for the password, so that it is not on a command line) and run `process-tree-guard create-lockout-record ptgcheck`; the last line it prints says that the record of that account has the permissions that were set. Copy the programs to a folder that the account may read and run (one made for the check; a build folder under another account's profile is not), and run them from there. Start a console as that account (`runas /user:ptgcheck cmd.exe`, in a real console window).
   - The lock, first: start a second console as that account and hold a range of the record locked from it (`$s = [IO.File]::Open($path, 'Open', 'Read', 'ReadWrite'); $s.Lock($s.Length, 1000000)`, with `$path` the file of the record of that account; a handle that can only read it can lock it). In the first console run the command of the next item and enter a wrong password: the run is refused with 125 after about 12 seconds (2 seconds to try the lock, then the cool-down of 10 seconds that follows every refusal after a prompt) and "the lockout record is locked by another program or another run; try again", before the check of the password (the Security log has no failed logon, event 4625, for it), and the size of the record is unchanged. Let go of the lock in the second console (`$s.Dispose()`).
   - In that console run `process-tree-guard --extendable --max-extension 86400 --authenticate console --timeout 20 -- cmd /c echo ran` and enter a wrong password at each of the three questions. Before the second and the third question the console writes a line of its own with the sentence about the wrong passwords on record ("1 wrong password on record within six hours; the third stops this prompt for six hours." and "2 wrong passwords on record ..."). The run exits with 125, and the last error says "no attempts are left; locked out after 3 wrong passwords, the last at" the time on your clock, "the password can be asked again in 6h 0m, at" the time six hours later. Write down the two times and check them against the clock.
   - Run the command again at once, and again a few minutes later, with the right password ready: no prompt appears; each run prints the lockout at once and exits with 125; the count and the two times are the same each time and the time left is shorter. The size of the record (`(Get-Item RECORD).Length`) is the same each time and does not change: after the first run it is a little over 4 kibibytes, which is the 60 bytes of the three wrong passwords and the newlines that the guard adds under its lock to have the room for the next record allocated; a run that is refused while the account is locked adds nothing.
   - Remove the lockout: from an elevated terminal remove the record of the account (`Remove-Item` on the file named after the security identifier of the account, ending in `.lockout`, in the `ProcessTreeGuard` folder), run `process-tree-guard create-lockout-record ptgcheck` (both in one elevated command: `Remove-Item RECORD; process-tree-guard create-lockout-record ptgcheck`), and confirm that the prompt is shown again and the right password runs the command.
   - A privilege: on the check account only, grant it the right to debug programs (Local Security Policy, Local Policies, User Rights Assignment, "Debug programs"), sign in as it again, run the command of the lockout from a console, and confirm that it is refused with 125 and "this account holds privileges (SeDebugPrivilege)", with no prompt. Take the right away again and sign in once more; the prompt is shown.
   - Then delete the account (`net user ptgcheck /delete`).
