# process-tree-guard

A Windows command-line tool that runs one command under a job object with an explicit, finite wall-clock deadline. When the deadline passes, the whole process tree is terminated: the command and every process it started.

It is a Rust library and four small programs built on it, with no third-party dependencies, licensed under the Apache License, Version 2.0. The programs are the full command `process-tree-guard`, the deadline role `process-tree-guard-deadline`, the hook role `process-tree-guard-gate` and the contain role `process-tree-guard-contain`, described in [Programs](#programs). A run can also be started so that the processes in it hold its deadline up, within a cap and with every request logged; see [Extendable runs](#extendable-runs). Through version 1.5.1 the project and program were named process-guard; that name still works as an alias, described in [Names and compatibility aliases](#names-and-compatibility-aliases).

## Why

Automation and AI coding agents start shell commands that can outlive their purpose: a test runner that hangs, a development server left in the background, a search over a whole drive, a child process that keeps running after its parent is killed. A per-call timeout in the calling tool usually stops waiting for the command; it does not reliably end the command's descendants. process-tree-guard closes that gap at the operating system level. Every process the command starts is inside one job object, and the job is closed at the deadline or when the caller goes away, so nothing in the tree survives.

## Guarantees

- The child is created suspended and assigned to the job before it runs, so it cannot use `CreateProcess` to start a process outside the job. A process that asks another program of the system to start one is a different matter; see Limits.
- The job is created with kill on close and without breakaway, so a child that asks to leave the job is refused.
- Standard input, output and error are passed through unchanged, and so is the exit code.
- If the process that launched the guard exits, the guard stops waiting and the tree is terminated.
- When the command finishes normally, any processes it left running are terminated with the job.
- The guard waits, up to 5 seconds, until every process in the job has exited before it returns, so no descendant outlives it.

## Limits

process-tree-guard bounds the commands that are run through it. It is not an operating-system-wide interception mechanism.

- Commands that are not routed through the guard are not bounded. Automatic mode and hook mode, below, are how a host routes its commands through it; anything a host runs by another path is outside the guard.
- Work on a remote machine, in a container, or in Windows Subsystem for Linux (WSL) needs an equivalent deadline and cleanup inside that environment. The guard ends the local process that started the remote work, not the remote processes.
- A run without `--extendable` ends by its fixed `--timeout`, at most 86400 seconds (24 hours); long-running services are out of scope for it by design. It never moves its deadline, so the policy's test of a deadline that moves by other means does not arise for it; the cap that `--max-extension` sets belongs to extendable runs. An extendable run has no limit on its total life, only on how far ahead its deadline is at any moment. In an [extendable run](#extendable-runs) the processes in the job can hold the deadline up by explicit, logged requests, each no more than the cap of the run (`--max-extension`, at most 86400 seconds): at every moment the deadline is a fixed time no more than that cap ahead, and a process that keeps the run alive does so by renewing it, request by request, in the log. A run whose processes go on renewing in time has no end by design: what bounds it is that every renewal is capped, logged and made by a verified process in the job, and that the deadline is a fixed time ahead at every moment. A run whose processes stop renewing, or hang, ends at the latest hold.
- Containment is not a boundary against a hostile process of the same user inside the job. Such a process can open the guard as the same user and suspend it, so that it never checks the deadline; it can duplicate a handle to the job; and it can ask a service of the system, such as Windows Management Instrumentation (WMI), the Task Scheduler or a Component Object Model (COM) server, to start a process, which is then outside the job and survives the kill. The guarantees above, that nothing outlives the deadline and that a deadline does not move by other means, hold for commands that do not do this on purpose: tests that hang, servers left running, descendants that outlive their parent, the ordinary commands of an automated agent. See [SECURITY.md](SECURITY.md).

## Programs

The crate builds one library and four programs. Each program is a thin `main` over the library, and each carries its own Windows version resource, so Task Manager and File Explorer show a description for it.

| Program | Description shown | Role |
|---|---|---|
| `process-tree-guard.exe` | Process Tree Guard | The full command: every mode runs in this process, with no extra process hop. |
| `process-tree-guard-deadline.exe` | Process Tree Guard: Deadline | The deadline role: the `--timeout` form and automatic mode (the `auto` subcommand, or a file name ending in `-auto`). It has no hook mode; `hook` is read as a program name and refused with exit code 125 for want of a deadline. |
| `process-tree-guard-contain.exe` | Process Tree Guard: Contain | The contain role: `process-tree-guard-contain --timeout SECONDS [--] COMMAND [ARGS...]` runs the command in a job of its own as a child of an [extendable run](#extendable-runs), and its `--timeout` is a request to that run. With no extendable run around it, it exits with 125 and runs nothing, because it never runs a command without a deadline that something finite holds. It takes no extension options and has no automatic or hook mode, whatever its file name. |
| `process-tree-guard-gate.exe` | Process Tree Guard: Gate | The hook role: `process-tree-guard-gate VENDOR` takes the same vendors and formats as `process-tree-guard hook VENDOR` (`pretooluse`, `cursor`, `cursor-context`, `antigravity`, `antigravity-context` and `powershell-auto`), and reads `pretooluse` when no vendor is given. It differs in the envelope set it accepts, the automatic copy it rewrites to, and `-h` and `--help` (see Where the programs go). It never runs a command. It takes no options: as its first argument only, `-h` or `--help` prints its usage and exits 0 without reading standard input. |

A person who wants one program uses `process-tree-guard.exe`, which does everything the roles do. The roles are for installers and for programs that start the guard themselves: a host that only needs a deadline can name the deadline role, and a host that only needs the hook can name the gate. The deadline role runs a command as the full command does; the hook role answers as the full command's hook does, within the differences named above.

Write the gate as `process-tree-guard-gate VENDOR`, never as `process-tree-guard-gate hook VENDOR`: the gate takes the vendor directly, so a leading `hook` is read as the vendor name, which is not one and is treated as `pretooluse`, and the vendor that follows it is ignored. Only the full command has the `hook` subcommand.

The version resource is written by `build.rs` with no resource compiler and no crates. It holds the description above, the product name `Process Tree Guard`, the file and product version (the package version), the copyright notice and the original file name of the program; no company name is set. It is linked only for the Microsoft Visual C++ (MSVC) target, which is the supported one. The GNU's Not Unix (GNU) target is unsupported: its linker does not take the resource, so a GNU build has none. On such a build the test of the resources (G39) asserts nothing: it writes a `NOTICE` line to standard error, which shows on a plain `cargo test`, and it fails instead when the environment variable `CI` or `PROCESS_TREE_GUARD_REQUIRE_RESOURCES` is set.

## Install

From version 2.0.0, each [release](https://github.com/WikdSolvemProbler/process-guard/releases) attaches prebuilt programs for 64-bit Windows, with a `SHA256SUMS` file that lists every executable: `process-tree-guard.exe`, `process-tree-guard-deadline.exe`, `process-tree-guard-gate.exe` and `process-tree-guard-contain.exe`, and, through all of 2.x, `process-guard.exe`, an identical copy of `process-tree-guard.exe` under the 1.x name (earlier releases attach `process-guard.exe` alone). A release also attaches `LICENSE`, `NOTICE`, `README.md` and `POLICY.md`; the test helper executable is not part of it. A source install (`cargo build`, `cargo install --path .` or `cargo install --git`) builds and installs the four programs and not the test helper `testkit`, which is built only for a test run (see [Build and test](#build-and-test)). Verify the checksums before use:

```powershell
(Get-FileHash .\process-tree-guard.exe -Algorithm SHA256).Hash
```

To build from source, install a stable Rust toolchain for the MSVC target and run:

```
cargo build --release
```

The programs are `target\release\process-tree-guard.exe`, `process-tree-guard-deadline.exe`, `process-tree-guard-gate.exe` and `process-tree-guard-contain.exe`. They need no installer; see [Where the programs go](#where-the-programs-go).

## Where the programs go

A program finds its own files (the automatic copy a hook rewrites to, and `POLICY.md`) relative to its own location, taken from `std::env::current_exe`. It never looks for them through `PATH` or in the current folder, so a file planted in either is never used (Common Weakness Enumeration, CWE-427, uncontrolled search path element).

The guard's own files are the only ones found relative to the program. The program the guard is asked to run is found as the Windows search for a command finds it, which looks in the current folder first unless the setting `NoDefaultCurrentDirectoryInExePath` is set, as in 1.x. The shell the guard chooses for `--shell` is found the same way, as in 1.x: `bash` is Git Bash at its fixed path, `cmd` is the program named by `COMSPEC` (else `cmd.exe`), and `powershell` is `pwsh.exe` when that search finds one (else `powershell.exe`). A caller that needs one exact shell names it with a full path in `COMSPEC`, runs it as the command itself, or sets `NoDefaultCurrentDirectoryInExePath`.

Two layouts work, and both are tested. In the install layout the full command is in `bin` and the roles are in `libexec`:

```
<root>/bin/process-tree-guard.exe
<root>/bin/process-tree-guard-auto.exe             a copy of process-tree-guard.exe
<root>/libexec/process-tree-guard-deadline.exe
<root>/libexec/process-tree-guard-deadline-auto.exe   a copy of process-tree-guard-deadline.exe
<root>/libexec/process-tree-guard-gate.exe
<root>/libexec/process-tree-guard-contain.exe
<root>/POLICY.md
```

In the flat layout every program is in one folder, here `bin`:

```
<root>/bin/process-tree-guard.exe
<root>/bin/process-tree-guard-auto.exe
<root>/bin/process-tree-guard-deadline.exe
<root>/bin/process-tree-guard-deadline-auto.exe
<root>/bin/process-tree-guard-gate.exe
<root>/bin/process-tree-guard-contain.exe
<root>/POLICY.md
```

In both, a program looks for `POLICY.md` one folder above its own folder, and for its automatic copy in its own folder:

- The full command uses the automatic copy of its own name: `process-tree-guard-auto.exe` (`process-guard-auto.exe` for the alias).
- The gate uses `process-tree-guard-deadline-auto.exe`, the automatic copy of the deadline role, in its own folder. In the install layout that is `libexec`. The full command's own automatic copy beside the gate (flat layout) is recognised as already guarded but does not stand in for it.
- The envelope check of the full command accepts an envelope that names the full command or its other name in the same folder. The envelope check of the gate accepts an envelope that names a program that enforces a deadline (`process-tree-guard.exe`, `process-guard.exe` or `process-tree-guard-deadline.exe`) in the gate's own folder and, when that folder is named `libexec` (in any letter case, as Windows folder names are not case sensitive), in the `bin` folder beside it, which must be spelled `bin` like every other part of the path in an envelope. It never accepts the gate itself, because the gate would not run the command.
- The role of a program decides its rules, not its file name. The gate keeps the gate's rules if it is copied to another name, and still never accepts an envelope that names its own path, in whatever letter case it was started; the full command keeps the rules of its own name even if it is copied to `process-tree-guard-gate.exe`.

An automatic copy is the program copied to a name ending in `-auto`; make it when installing.

The policy file names its programs through the placeholder `{{BIN}}` (see [The policy file](#the-policy-file)). In the install layout `{{BIN}}` is the `bin` folder: it holds `process-tree-guard.exe` and `process-tree-guard-auto.exe`, the two files the policy tells agents to run, and the gate accepts an envelope that names `process-tree-guard.exe` there. It is not `libexec`, which holds the roles. For `hook antigravity` the gate rewrites commands to `process-tree-guard-deadline-auto.exe` in its own folder; the agent never writes that name, but an installation whose hook is the gate and that has no full command in `bin` fills `{{BIN}}` with the `libexec` folder and writes `process-tree-guard-deadline.exe` and `process-tree-guard-deadline-auto.exe` in place of the two names, as the policy file allows. In the flat layout there is one folder, and it is `{{BIN}}`.

## Library

The programs are thin mains over the library crate `process_tree_guard`, which has no dependencies. It is not published to crates.io; use it as a path or git dependency. Its public interface is small:

- `run(command, seconds)` runs a program and its arguments under a deadline. Inside an [extendable run](#extendable-runs) the call asks the run for `seconds` first, as a nested guard does, and the hold it makes on the calling process is ended when the call returns (see Nested guards under that heading). The same holds for `run_shell` and `run_auto`, and the calls share the process's limit of 12 requests in any 10 seconds. Each call has a hold of its own, so calls that overlap, from threads of one process, do not replace or release one another's holds.
- `run_shell(shell, command_b64, seconds)` runs Base64 encoded UTF-8 command text in PowerShell, Git Bash or `cmd`.
- `run_auto(args)` is automatic mode, and `run_hook(vendor)` is a hook mode of the full command: the files it looks for and the envelope it accepts follow the file name of the running program.
- `extend(seconds)` asks the enclosing [extendable run](#extendable-runs) to hold the deadline of the calling process for that many seconds from now, and returns a `Grant` (the seconds and the time the hold ends) or a `GuardError` with the reason.
- `main_full()`, `main_deadline()`, `main_gate()` and `main_contain()` are the entry points of the four programs; each returns the exit code.
- `GuardError` is the error type, `Shell` names the shells (the type is `#[non_exhaustive]`, so a later version may add one), `MAX_SECONDS` is 86400, `CHANNEL_VARIABLE` is `PROCESS_TREE_GUARD_CHANNEL` and `DEFAULT_MAX_EXTENSION` is 21600.

```rust
use process_tree_guard::{run, GuardError};

fn main() -> Result<(), GuardError> {
    let command = ["rg".to_string(), "--files".to_string(), "C:\\src\\project".to_string()];
    let code = run(&command, 60.0)?; // the command's own code; 124 at the deadline
    std::process::exit(code as i32);
}
```

The command inherits the caller's standard input, output and error handles, and runs in the caller's console when it has one, so its output appears where the caller's own output does. The notices `PROCESS_TIMEOUT` and `PROCESS_OWNER_EXITED` are written to the caller's standard error, as the programs write them.

The command inherits more than those three. It is created with handle inheritance on and without a list of handles, so every handle of the caller that is marked inheritable passes into the command and its descendants, and an unrelated pipe or file held that way stays open until the whole tree has exited. An embedder should mark its own handles non-inheritable before the call (files opened through the Rust standard library already are), or start the `process-tree-guard` program as a child, so that it chooses what that child inherits.

The owner. The guard ends the tree when the process that launched it exits. In a library call that process is the caller's parent, not the caller: `run` and `run_shell` watch the parent of the calling process, and `run_auto` watches every live ancestor of it.

- If the parent has already exited and Windows no longer has a record of it, the call returns a `GuardError` with the Windows error 87 text, as the program does in 1.x. If another process still holds that record, the command is started and ended at once, and the call returns `Ok(125)`.
- If the parent exits during the call, the guard ends the command tree and the call returns `Ok(125)`.
- The parent is identified by its process identifier when the call starts. Windows can reuse an identifier after its process has exited, so a call made after the parent exited can end up watching an unrelated process that has taken the identifier.

A program that can outlive its parent should not call the library directly. It can start `process-tree-guard` as a child, which then watches that program itself.

## Names and compatibility aliases

Version 2.0.0 renames the project and the program from process-guard to process-tree-guard. To let installations move over without a flag day, the old names are kept as aliases through all of 2.x and are removed in 3.0 (Semantic Versioning 2.0.0: removing them is a breaking change).

Each program reads only its own file name. Copying the full command to any of these names gives identical behaviour:

| Name | Role |
|---|---|
| `process-tree-guard.exe` | The program. |
| `process-tree-guard-auto.exe` | Automatic mode: any name ending in `-auto` selects it. |
| `process-guard.exe` | Alias of `process-tree-guard.exe`, through 2.x. |
| `process-guard-auto.exe` | Alias of `process-tree-guard-auto.exe`, through 2.x. |

The deadline role, `process-tree-guard-deadline.exe`, selects automatic mode by a name ending in `-auto` in the same way (`process-tree-guard-deadline-auto.exe`). The roles are new in 2.0.0 and have no 1.x names. The hook role does not read its file name, either for a mode or for its rules (see [Where the programs go](#where-the-programs-go)).

What the aliases cover:

- Every `hook` subcommand and the `auto` subcommand work under both program names.
- The hook envelope check accepts an envelope that names the executable it runs from, or the same executable under its other name in the same folder. A path in another folder, in another letter case, or with anything added is refused, as before.
- `hook antigravity` wraps commands with the automatic copy of its own name family: `process-tree-guard.exe` uses `process-tree-guard-auto.exe` beside it, and `process-guard.exe` uses `process-guard-auto.exe`. A line already in the wrapper form of either family, or already a valid envelope of either name, passes through unchanged. An executable under any other file name behaves as in 1.x: it uses `process-guard-auto.exe` beside it and recognises only that wrapper form.
- The automatic deadline is read from `PROCESS_TREE_GUARD_AUTO_TIMEOUT`, else `PROCESS_GUARD_AUTO_TIMEOUT`, else `HARNESS_AUTO_TIMEOUT`: the first of the three that is set is used. A variable set to the empty string counts as set, so an empty `PROCESS_TREE_GUARD_AUTO_TIMEOUT` shadows the older names; the empty text is not a number, so the wrapper then fails with exit code 125.

Apart from the program name in the `--help` usage line, which reads `process-tree-guard` whichever name the program runs under, version 2.0.0 changes one thing from 1.5.1. It is a deliberate correction, and the [changelog](CHANGELOG.md) records it:

- The denial text of the hook names the policy file one folder above the program's own folder, the file that `cursor-context` and `antigravity-context` read. In 1.5.1 it named the text before the last `/bin/` of the program's path, which is a different file when `/bin/` occurs earlier in the path, and the bare name `POLICY.md` when the folder is not called `bin`.

Everything else is as it was: the deadlines, the 86400 second maximum, exit codes 124 and 125, containment, and the messages on standard error `PROCESS_TIMEOUT` and `PROCESS_OWNER_EXITED` and the `PROCESS_GUARD_ERROR` prefix. To move over, install the executable under the new names, change hook configurations to the new paths, and remove the old files when nothing refers to them.

## Usage

```
process-tree-guard --timeout SECONDS [--] COMMAND [ARGS...]
process-tree-guard --timeout SECONDS --shell powershell|bash|cmd --command-b64 BASE64
process-tree-guard --extendable [--max-extension SECONDS] [--extension-log PATH] --timeout SECONDS ...
process-tree-guard extend SECONDS
```

- `--timeout` is required: a number greater than zero and at most 86400 seconds; decimals such as `.3` are accepted. There is no default in this form; a missing or invalid deadline is refused.
- `--shell` runs the Base64 encoded UTF-8 command text in PowerShell (`pwsh.exe` when present, otherwise `powershell.exe`), Git Bash, or `cmd.exe`. The command must be nonempty and contain no NUL character.
- Without `--shell`, the command and its arguments follow the options, optionally after `--`. A `.cmd` or `.bat` file is refused; run it through `cmd.exe /d /s /c` instead.
- `--extendable`, `--max-extension` and `--extension-log` start an extendable run, and `extend` asks one for more time; see [Extendable runs](#extendable-runs). The deadline role takes them as the full command does; the contain role takes none.
- With `PROCESS_GUARD_TRACE` set to any text in the guard's environment, the guard writes the milliseconds since it started at each stage (`PROCESS_GUARD_TRACE` lines) to standard error. The lines are kept while the run goes on and written once the tree has ended, together with the notice, so a standard error that nobody reads does not hold the tree past its deadline with this variable set either; a standard error that has been closed does not change the exit code.

Examples:

```
process-tree-guard --timeout 60 -- rg --files C:\src\project
process-tree-guard --timeout 900 -- cargo test --release
```

## Exit codes

| Code | Meaning |
|---|---|
| The command's own code | The command finished before the deadline. |
| 124 | The deadline passed; the process tree was terminated. |
| 125 | Guard error (invalid arguments, executable not found, a system call failed), the process that launched the guard exited first, or an extension was refused (`extend`, a guard started inside an extendable run whose deadline the run would not hold, or an extendable run with no `--extension-log` whose standard error is closed or is the null device). |

Outside hook mode the guard never exits with 2 for its own errors, because agent hosts treat exit code 2 from a hook as a block. In hook mode a denial exits with 2 whether or not the guard can write its output and its reason: a host that blocks a tool call only on exit code 2 reads any other status as a non-blocking error, so a denial that ended in a crash because a stream had no reader would let the command run. `--help` prints usage and exits 0, in the full command and the deadline role; the gate prints its own usage text for `-h` or `--help` as its first argument, and exits 0 (see [Programs](#programs)).

## Extendable runs

A deadline can be held up by the processes it runs, within limits the launcher sets, with every request in a log. The rule is the one in [POLICY.md](POLICY.md): a deadline is finite when, at every moment, it is a fixed time no more than `--max-extension` ahead, set or moved only by an explicit, logged request from a verified process in the guard's job. A process that runs past its deadline, or whose deadline moves by any other means, is unlimited, and the guard does not allow it. A process that renews before each hold ends keeps a run alive by requests that each satisfy the rule: renewal is the mechanism, and the rule is what it is held to. There is no limit on the whole life of a run, so a supervisor made of processes that renew in time can be permanent; every renewal is capped, logged and made by a verified process in the job, and a run whose processes stop renewing ends at the latest hold.

```
process-tree-guard --extendable [--max-extension SECONDS] [--extension-log PATH] --timeout SECONDS [--] COMMAND [ARGS...]
process-tree-guard extend SECONDS
process-tree-guard-contain --timeout SECONDS [--] COMMAND [ARGS...]
```

**Opt in.** A top-level guard started with `--extendable` (the full command or the deadline role) runs an extendable run. It is never automatic mode and never the hook envelope: automatic mode refuses the extension options, and a command line with `--extendable` is not an envelope, so the hooks deny it or, for the Google Antigravity hooks, wrap it again whole. Without the flag a run has a fixed deadline, no channel of its own, no environment variable set for its command, no new log and the clock of 2.0.0-alpha.2. `--max-extension` and `--extension-log` need `--extendable`. The following differ from 2.0.0-alpha.2 in every run, whether or not it is extendable, and the [changelog](CHANGELOG.md) records each under "Changes that reach every run": (1) the guard ends the tree before it writes `PROCESS_TIMEOUT` or `PROCESS_OWNER_EXITED`, and gives that write half a second on a thread of its own, so a standard error that nobody reads can no longer keep the tree alive, which it could; with `PROCESS_GUARD_TRACE` set, the trace lines are kept while the run goes on and are written with the notice once the tree has ended, where 2.0.0-alpha.2 wrote each as it was made; (2) each line on standard error is written with one call, and a standard error or standard output whose reader has gone no longer ends the guard with a crash in any mode, the hook modes included, so the exit code is kept (124, 125, the command's own, 0 for a request that was granted, for `--help` and for the usage of the gate, and 2 for a denial by a hook); (3) a guard that finds `PROCESS_TREE_GUARD_CHANNEL` set in its environment to the name of a live channel asks that run for its deadline (a value that is not the name of a channel, or the name of one that is gone, is read as no run around the guard, which then keeps its own fixed deadline as before, so no value of that variable can stop a guard from running its command); (4) `--max-extension` and `--extension-log` without `--extendable` are refused with a message of their own; and (5) the usage text that `--help` prints has a second line for `process-tree-guard extend SECONDS` and names the extension options.

**The cap.** `--max-extension SECONDS` is the most a single request can ask for: a number greater than zero and at most 86400, 21600 (six hours) when it is not given. It is read from the guard's own launch arguments and from nowhere else, so nothing a child sets in its environment can raise it. The run's own `--timeout` is held to the same cap, so that the rule above holds from the first moment: `--extendable --timeout 86400` needs `--max-extension 86400`.

**The channel.** The guard serves a named pipe in message mode. Its name is random, 128 bits from the system random generator, made with `FILE_FLAG_FIRST_PIPE_INSTANCE` on the first of four instances, which is the most the pipe allows and all of which the guard makes before the command starts (so nobody else can make another), each served by a thread of its own, `PIPE_REJECT_REMOTE_CLIENTS` and an access list for the current user alone (read, write and read attributes; not the right to make another instance, which the list has only while the guard makes the four). The name is passed to the command, and so to everything it starts, in `PROCESS_TREE_GUARD_CHANNEL`. Requests and replies are fixed-size messages (24 and 40 bytes); a message of any other size is refused. What a connection can cost is bounded: the guard settles who the client is before it waits for a byte of its message, a client that is let in has a quarter of a second to send its request and half a second to take the reply, and a client that sends nothing is dropped, charged a request of its share of the rate limit, and logged. The pipe has no outgoing buffer, so the guard's write of a reply completes only when the client reads it, and the guard knows whether the reply was taken.

**Verification.** For each connection, before it replies, the guard takes the client's process identifier from the pipe (`GetNamedPipeClientProcessId`), opens that process, and checks that it is alive, that it is in this guard's job (`IsProcessInJob`, which counts the jobs nested inside it, so a process under a nested guard is in) and that it was created before the guard learned of the connection, which a process that took over a reused identifier later than that was not. The client stays connected until the reply, and the guard checks that it is: after it has read the request and before it decides, it asks the pipe whether the client's end is still open (`PeekNamedPipe`), and a request whose end is closed is refused as not verified. A client waits for its reply with its end open, so only a client that has gone has closed it, and whatever process now has its identifier is not the client. The creation time check is not exact by itself. The guard takes the time when the thread that serves the instance of the pipe notices the connection, so a process that took over the identifier of a client that had connected, written and exited, between the connection and that moment, would pass it: the gap is the time the thread took to run, short on an idle machine and tens of milliseconds or more on a busy one, and the whole time since the connection when the client was there before the thread was waiting. The check on the client's end closes that gap for a client that closed its end by exiting; it does not close it for a client that gave a duplicate of its end to another process before it exited, because the end is then still open. The comparison reads the system (wall) clock, as a creation time is a wall clock time, so a step of the clock backwards across the start of a client can make the guard refuse it as not verified; the deadline is unaffected, as it is measured by `GetTickCount64`. See [SECURITY.md](SECURITY.md). Requests are rate limited, before any of that is believed and before the guard waits for the message: at most 12 per process in any 10 seconds, counting a connection that sends nothing as a request. All the clients outside the job draw on one such allowance; the first 12 in a window are read, answered with a refusal and logged, and after that a client outside the job is disconnected at once, without its message being waited for and without a reply (they are counted, and the log says how many), so they cannot crowd out the processes in the job. The table of processes holds 1024 live ones: a process that has exited is forgotten when the table is full, so a run may start any number of short-lived processes, but a new process is refused (with a reason of its own, "too many processes are asking at once") while 1024 others are live, and a live one is never forgotten to make room. At most 256 holds at once, and at most 8 for one process (all its holds together, whatever their numbers): a ninth is refused with "this process holds too many deadlines", so one process cannot take the table from the rest, which takes 32 processes of the job. A process in the job over its share is still answered, with a refusal, but with a tenth of the waiting for its message. A client waits at most five seconds for the reply, and gives up with a reason if the run does not answer.

What remains is the cost of a process in the job. It can connect and stall: each such connection holds one of the four instances for at most a quarter of a second (a tenth of that for the message once the process is over its share, and up to a quarter of a second for it to read the refusal), and the guard counts it against the process's share. A handful of such processes can keep all four instances busy, so that another process's request waits, up to the five seconds a client waits, and then fails. A client outside the job costs the channel nothing beyond its first 12 connections in a window. None of this moves the deadline, and the stalls are logged, within the budget of refusal lines below.

**Holds and the deadline.** A granted request sets a hold on the verified process, by its handle and never by its identifier: now plus the granted seconds. A hold ends when its process exits or its seconds run out, whichever is first. The deadline of the run at every moment is the latest of its own `--timeout` deadline and the holds of the live processes. It is recalculated, under one lock, on every grant and every exit; exits are learned from the job's completion port, and every 100 milliseconds the guard also polls each holder (alive, in the job) and the job's list of processes, so a lost message delays nothing for longer than that. A request that arrives after the deadline is refused (the run has ended), even if the guard has not yet noticed that the deadline passed: the deadline is checked under the same lock, before anything is granted. When the deadline passes, the guard ends the whole tree first and only then writes `PROCESS_TIMEOUT`, and exits with 124, as it does without `--extendable`; the command's own exit code passes through when it ends first. The notice differs in one number. A run without `--extendable` names its `--timeout` as it was given (`PROCESS_TIMEOUT: exceeded 2 seconds; terminating process tree`, or `exceeded 0.5 seconds`), and an extendable run names the seconds it lasted, to the millisecond (`exceeded 10.19 seconds`), because its deadline moves and its `--timeout` is not what it ran for. Both are plain decimal numbers, but a consumer that reads the number as a whole number must read the second form as a decimal. Any verified process in the job may ask, and the hold is on the process that asked.

The client and the run agree about whether a hold exists. The guard sets the hold, then sends the reply and waits half a second for the client to read it. A client that sends its request and reads the reply later than that gets an error (the guard has closed the connection; the system error reads that no process is on the other end of the pipe) and no hold: the guard withdraws the grant, putting the hold back to what it was before the request (none, or the earlier one), recalculates the deadline, and writes a second line for it, `decision=withdrawn`, after the `granted` line. A nested guard that did not get its reply exits with 125 and runs nothing; `extend` exits with 125. The standard clients read the reply at once, so this is the behaviour of a client that stalls or has been stopped between its request and its read. A release whose reply is not taken still ends the hold, since that is what the client asked for.

**Asking.** `process-tree-guard extend SECONDS` asks for the process that ran it, its parent, because the `extend` program ends at once and a hold on it would end with it. The guard reads the parent from the verified client's own process record, and checks the parent as it checks any process (alive, older than the client, in the job). It prints `PROCESS_TREE_GUARD_GRANTED: seconds=N deadline=TIME held=ID image="NAME"` (universal time, and the process the hold is on) and exits 0; when the request is refused, or there is no run to ask, it exits 125 with the reason on standard error. The number is sent as it is: a value that is not greater than zero, not finite or over the cap reaches the run, which refuses it and logs it; only text that is not a number is refused before it is sent. The library call `extend(seconds)` asks for the calling process itself.

Under Git Bash the parent of the `extend` program is a copy of the shell that Git Bash makes to run it, and that copy ends as soon as the program does, which would end the hold with it. When the parent is a `bash.exe` or `sh.exe` whose own parent is the same program, older, alive and in the job, the hold goes to the outermost such shell (up to eight levels), the one that goes on to run the rest of the script, and the `held=` and `image=` fields of the line say which process it is. Under PowerShell, `cmd.exe` and a direct call from a program the parent is the shell or program that ran `extend`, and the hold lasts only for as long as that process stays: `extend 20; Start-Sleep 60` in PowerShell, or `extend 20 & ping -n 60 127.0.0.1` in `cmd.exe`, holds a shell that goes on to run more commands. When `extend` is the last command of a one-liner (`cmd /c`, `powershell -Command` or `bash -c`, the form that `system()` and `shell=True` make), the shell that is held exits as the program returns, and the hold ends with it: `extend` still prints `PROCESS_TREE_GUARD_GRANTED` and exits 0, and the log still records the grant for the full seconds, but the deadline of the run does not move. A hold that ends with its process is not a line of its own in the log, so the line that names the process held (`held=` and `image=`) is the place to see it: a shell there that is about to exit holds nothing. For a one-liner, and for any other launcher that runs the program through a short-lived intermediate process (it holds that process), the reliable routes are the library call `extend(seconds)` made by the process that stays, and a script that goes on running after the call. A process that wants to stay alive renews before its hold ends; each renewal is a request, with the same cap, rate limit and log line. A client accepts a reply only if it is well formed and its numbers are in range (the seconds, and the cap in a refusal, finite and from 0 to 86400; a time that a clock can show); anything else is an error with exit code 125 and the reason "the extendable run sent a reply that is not understood". A client does not check who serves the channel; see [SECURITY.md](SECURITY.md).

**Nested guards.** A guard started inside an extendable run, whatever its role or mode, asks the run for its own `--timeout` as it starts, and the hold is on the guard's process and ends with it, so a run lives while the guards in it do. A library call (`run`, `run_shell` or `run_auto`) made by a process in the run is the same request, made by the calling process, which goes on after the call; so its hold is ended when the call returns, with a release request that is a line of its own in the log (`decision=released`) and does not use up the process's share of the rate limit. Each call has a hold of its own, and so has `extend`: the request carries a number that names the hold, one for each call, and a release names the same number, so calls that overlap, from threads of one process, neither replace nor release one another's holds, nor the hold of `extend`; the run waits for the latest of them, each no more than the cap from its grant. Each call is one request against the 12 per process in any 10 seconds: a host that makes a 13th call inside a run within the window has it refused, with "too many requests from this process; try again later", and its command does not run. If the run refuses (the deadline is over its cap, a rate limit, no verified place in the job) the guard exits with 125 and its command never starts; the refusal is in the run's log. A variable that names a channel that is there, and a run that does not answer or answers with something that is not understood, stop a guard the same way, with 125; a variable that does not name a channel, or names one that is gone, is no run around the guard, and the guard keeps its own deadline (the contain role is the exception: it refuses, since it never runs without a run around it). An extendable guard in an extendable run asks the outer run for its deadline and then serves a channel of its own; its tree is also ended when the outer run ends it, so it lives no longer than the outer run holds it. An extendable guard inside a job that is not extendable has no one to ask, and ends at the outer deadline.

**The contain role.** `process-tree-guard-contain` is a nested guard that insists on being one: its `--timeout` is the request, and with no extendable run around it, it exits with 125 without running the command. The command runs in a job of its own and is ended at its own deadline with 124.

**The log.** Every request and every grant is a line on standard error that starts with `PROCESS_TREE_GUARD_EXTENSION:` and, with `--extension-log PATH`, in that file too. Refusals are lines as well, within the limits stated below: the first refusal of a window is a line of its own, and the later ones are counted and written as one line with their count, so that a flood of refusals cannot push the grants out of a file of limited size. This is a decision, and a departure from a line for every single refusal: a refusal past the first of its window is recorded as a number in a count line (apart from the count of the window that is open when the guard is killed, below). A line has the time (universal, to the millisecond), the process identifier, the image name (the file name of the program), the seconds requested and granted, the decision (`granted`, `refused`, `released` for the end of a hold at its process's request, or `withdrawn` for a grant taken back because its reply was not taken) and the reason, for example `time=2026-10-20T15:04:05.123Z pid=4242 image="worker.exe" requested=60 granted=60 decision=granted reason="within the cap"`. Quotes, backslashes, control characters and line separators in a value are escaped, so no value that a process chooses (its image name) can end a line the guard writes or start a field of its own (Common Weakness Enumeration, CWE-117). The file is bounded at one mebibyte (MiB) with one rotation, `PATH.1`. It must be a file on a disk: a path that names a device (the null device, a console) or a pipe takes every write and keeps none of it, so the run does not start (exit code 125, "the extension log must be a regular file"). The seconds are written exactly as they were asked for, in a bounded number of characters: a value of 10^15 or more, or below a millionth, is written in scientific form (`1e300`, `5e-324`), and a value that is not a finite number as `invalid`. Besides the controls, the line separators and the characters that change how text is shown (the bidirectional controls, such as a right-to-left override, the zero width characters and the byte order mark; the category Cf) are escaped too, so what an operator reads is what the bytes say (Common Weakness Enumeration, CWE-451).

**Without an audit file.** When there is no audit file, standard error is the only record, and the guard holds its grants to it, so that the rule in [POLICY.md](POLICY.md), a deadline moved only by a logged request, holds without `--extension-log` too. A run does not start (exit code 125) when standard error is closed or is the null device, which takes every write and keeps none of it, and `--extension-log` was not given. A grant is made only once its line has been written to standard error: the guard waits for the line for at most half a second, and when the write fails or does not finish in that time (the reader has gone, the pipe is full, the queue of lines is full) it takes the grant back, replies with the refusal "the audit file (or standard error, when there is no audit file) cannot take lines, so nothing is granted until it can", and logs a `withdrawn` line. After a write to standard error has failed the run grants nothing until a write works. Releases and refusals are not held to this. With `--extension-log` the file is the record and standard error is a copy, so none of this applies and the file's own rule (below) is the one that stops the grants. What the guard cannot tell is a standard error that is a pipe or a file whose reader keeps nothing, or a reader that reads and discards: a launcher that needs the log as evidence passes `--extension-log` and reads the file.

Every grant is a line of its own. Refusals are limited so that a flood of them cannot push the earlier lines out of the log: the first refusal of a process for the rate is a line and opens a window of 10 seconds, and the rest of that window are one line with their count (`12 more refused within 10 seconds of the first`), written when the window ends, whether the process has stopped asking or goes on; the next refusal opens a window of its own and is a line again, so a process that asks all the time has a first line and a count line in every window, and the log is at most 10 seconds behind what the guard has counted (the counts of the window that is open when the guard is killed, with `taskkill /F` or a power loss, are lost; the end of a run writes them); the clients outside the job count as one process; and at most 24 refusal lines are written in any 10 seconds over all processes, the rest being one line with their count. The copies on standard error and in the file are written by threads of their own from queues of 256 lines, so nothing the log is written to is waited for: a standard error that nobody reads costs lines (a full queue drops them and a notice says how many), never the answers or the deadline. The tree is ended before the guard writes anything to standard error, and the notice that it did so is given half a second to be written and is then left, so an unread standard error cannot keep the guard from returning either. At the end of a run the last lines are given half a second to be written.

The log is an audit record, not a control: the cap, the verification and the rate limit are the controls. The command shares the guard's standard error, so a process in the job can print a line that looks like a log line there; the copy on standard error is not evidence. The file named by `--extension-log` is evidence only against a process that cannot open it. The guard and the processes in the job run as the same account, so a process in the job can open the file and append a line in the exact form of a grant, or delete or replace the file; no setting of the folder prevents that, because a folder that those processes cannot write to is one that the guard cannot write to either. Rely on the file only where a boundary of another kind keeps the command from it (the command runs as another user, in a container or in a virtual machine), or where a collector ships the lines off the machine as they are written; copy the file off the machine promptly in either case. The limit stated below for `PATH.1` applies: a process that can read the folder can stop the file from being turned over, and the run then stops granting rather than lose a line.

The bound on the file is a bound on disk space, not a promise to keep the lines. Grants are not budgeted, so a process in the job that starts many short-lived processes, each asking once, can turn the log file over, and its one rotation, in a few minutes (in about a minute with a fast spawner), and push every earlier line out, the refusals among them. The file is evidence of what happened before such a flood only if it is copied off the machine promptly: read it while the run goes on, or keep the run short. A collector that follows the file must open it so that others may write and delete it (`FILE_SHARE_WRITE` and `FILE_SHARE_DELETE`; many do not, PowerShell `Get-Content -Wait` among them, and the default of .NET's `File.OpenRead` and `FileStream` for reading shares reading only): the guard appends to the file, which a reader that does not share writing refuses, and turns it over by renaming it to `PATH.1`, which a program that holds it open without sharing delete stops. The guard holds the file open for appending for the whole run, so a reader that does not share writing is refused when it opens the file (a sharing violation, Windows error 32) and cannot make the guard's appends fail without a word; a reader that opened the file before the run began stops the guard, which exits with 125 ("cannot open the extension log") and runs nothing. If an append fails all the same (the folder went away, a handle opened by another route), the guard tells standard error at once, keeps the lines that could not be written (up to 256), tries again every half second, writes them in order as soon as the file takes lines, and then writes a notice into the file and to standard error with the number written late and the number that were not written; the end of a run says how many lines the file never got. Standard error has every line either way. The guard does not discard the earlier lines for that. It copies the file to `PATH.1` and empties it instead, and if that cannot be done either (`PATH.1` is held open too) the file could not be turned over, so it grows past one mebibyte, with a notice line in it, toward twice that (it tries again once a second). The guard does not hold `PATH.1` open, and a program in the job can hold it so as to stop both ways of turning the file over: opening it for reading and sharing reading only (read access is all it needs, and the default of .NET's `File.OpenRead` is such an open) refuses the rename and the copy alike. No setting of the folder prevents that, because reading needs no write access. So the run does not carry on and lose lines: when the file cannot be turned over and has less than 64 kibibytes (KiB) left before twice its limit, or when its lines cannot be written, the run grants nothing. Every request that would move a deadline is refused, with the reason "the audit file cannot take lines, so nothing is granted until it can", the logged refusals and the deadlines already granted stand, and the file is tried again every half second, whether or not a line comes, until a turn over or a write works, when the run grants again. A run started with a file that is past its limit, cannot be turned over and has no such room refuses to start, with 125. The 64 KiB is room for the lines that are on their way when the file becomes blocked, so a grant is in the file unless more than that was queued behind it (standard error has every line either way). The number of lines in a window is bounded for refusals only.

**The clock.** An extendable run measures its deadlines with `GetTickCount64`, a count of milliseconds since the system started that includes the time the machine spends asleep and does not follow changes of the clock. The deadline of a run started without `--extendable` keeps the clock of 2.0.0-alpha.2: its wait is a Windows wait timeout, which on Windows 8 and later does not count time asleep.

**Same-user access is not a boundary.** The channel name is in the environment of every process in the run, and the access list keeps out other accounts and other machines, not another process of the same user, which can read the variable, or the memory of a process that has it. What limits that process is the cap, the verification that it is in the job, the rate limit and the log; a process of the same user that is outside the job is refused and logged (within the limits on refusal lines above) for its first 12 connections in a window, and is disconnected at once after that. See [SECURITY.md](SECURITY.md).

## Automatic mode

```
process-tree-guard-auto.exe [--timeout SECONDS] [--shell powershell|bash|cmd] [--] COMMAND...
process-tree-guard.exe auto [--timeout SECONDS] [--shell powershell|bash|cmd] [--] COMMAND...
```

The wrapper a host puts in front of every shell command, so individual commands need no envelope. Copy `process-tree-guard.exe` to `process-tree-guard-auto.exe` in the same folder; a file name ending in `-auto` alone selects this mode, so a host can name it as a single program path. The 1.x name `process-guard-auto.exe` selects it the same way (see the aliases above). The deadline role works the same way: `process-tree-guard-deadline.exe auto ...`, or a copy named `process-tree-guard-deadline-auto.exe`, which is the automatic copy that the gate rewrites to (see [Where the programs go](#where-the-programs-go)).

- One remaining argument is a command line for a shell: the one named by `--shell`, otherwise the same kind of shell that launched the wrapper (PowerShell, `cmd`, or Git Bash when unknown). Several remaining arguments are a program and its arguments.
- The deadline is `--timeout`, else the `PROCESS_TREE_GUARD_AUTO_TIMEOUT` environment variable, else `PROCESS_GUARD_AUTO_TIMEOUT`, else `HARNESS_AUTO_TIMEOUT`, else two hours. The first variable that is set is used, even when it is empty: an empty value is refused with exit code 125 and the older names are not consulted.
- The wrapper watches every live ancestor up to the desktop shell, not only its parent. A host that ends a call by killing the outer launcher of a shell (Git Bash runs as a launcher and a separate shell process) therefore still ends the whole tree. Each ancestor must have started before its child, so a reused process identifier is never mistaken for one.
- Standard input, output and error, and the exit code, pass through, so hook commands keep working.
- Automatic mode is never extendable: `--extendable`, `--max-extension` and `--extension-log` are refused with 125. Started inside an extendable run, it asks the run for its deadline like any guard.

## Hook mode

```
process-tree-guard hook pretooluse|cursor|cursor-context|antigravity|antigravity-context|powershell-auto
process-tree-guard-gate pretooluse|cursor|cursor-context|antigravity|antigravity-context|powershell-auto
```

The second line is the hook role and is the same as the first for each vendor; the rest of this section describes both, and says where the gate differs. An envelope check for agent hosts whose pre-execution hooks can only allow or deny a shell command. It reads the host's hook payload, written in JavaScript Object Notation (JSON), on standard input and allows the command only when it is exactly

```
<installed process-tree-guard.exe, forward slashes> --timeout SECONDS --shell powershell|bash|cmd --command-b64 BASE64
```

with an optional leading `& `, a timeout above zero and at most 86400 written as digits with an optional decimal part, and a payload that decodes to nonempty UTF-8 with no NUL character. The envelope has no `--extendable` option, so a command line that carries it is not an envelope. The executable may be spelled as the one the hook runs from, or as its other name in the same folder (see the aliases above). For the gate, which does not run commands, the envelope names a program that enforces a deadline instead: see [Where the programs go](#where-the-programs-go). Anything else is denied in the host's format with exit code 2; hook mode is the only place the guard exits 2 on purpose.

- `pretooluse` reads `tool_input.command` (or `tool_input.cmd`) and answers in the PreToolUse hook format.
- `cursor` reads `command` and answers in Cursor's `beforeShellExecution` format.
- `cursor-context` prints `POLICY.md` from the folder above the guard's own folder as session context.
- `antigravity` is different: it rewrites instead of only checking. It reads a Google Antigravity PreToolUse payload and, for the `run_command` tool, replaces `CommandLine` with a call to the automatic copy of the guard's own name (`process-tree-guard-auto.exe`, or `process-guard-auto.exe` for the alias) in the guard's own folder, so the command runs under the guard. Every failure it detects, denials included, is a JSON decision on standard output and the exit code is always 0. See [Google Antigravity](#google-antigravity-integrated-development-environment-app-and-command-line-interface).
- `antigravity-context` prints `POLICY.md` from the folder above the guard's own folder as a Google Antigravity SessionStart system message.
- `powershell-auto` rewrites too. It reads a PreToolUse payload for a PowerShell tool and replaces `tool_input.command` with a call to the automatic copy of the guard's own name in the guard's own folder (for the gate, the automatic copy of the deadline role), so the command runs under the guard. A command that is already in that wrapper form, or is a valid envelope, passes through unchanged. The decision on a rewrite is `ask`, or `allow` when the host is in `bypassPermissions` mode. It exits with 0 and never denies; a payload it cannot read leaves the command as it was. It does not test that the automatic copy exists: a rewrite names the wrapper path whether or not the file is there, and when it is missing the rewritten line runs nothing, although the host may read that as success (PowerShell reports the missing program and the line exits with 0). Install the automatic copy before configuring this vendor. A line that already has the wrapper form passes through unchanged for the same reason, without a check of the file.

The exit code 2 on a denial belongs to `pretooluse` and `cursor`. The `antigravity` vendors and `powershell-auto` always exit with 0.

Run the `pretooluse` and `cursor` hooks under the guard itself, for example `process-tree-guard.exe --timeout 10 -- process-tree-guard.exe hook pretooluse`. Do not wrap the `antigravity` vendors this way: a guard timeout would end the hook with exit code 124 and no JSON decision. Vendor names must be spelled exactly; any other name is treated as `pretooluse`.

## Integrating with agent hosts

Pick the strongest mechanism the host offers:

1. **A shell prefix setting.** Hosts that let you name a program to run in front of every shell command should name `process-tree-guard-auto.exe`. Every command is then bounded with no change to how commands are written.
2. **A hook that can rewrite the command.** Hosts whose pre-execution hook can replace the command can wrap it in `process-tree-guard-auto.exe`; `hook antigravity` does this for Google Antigravity, below.
3. **A hook that can only allow or deny.** Use hook mode. The agent must then write every shell command in the envelope form, and the policy file tells it how.

Pair any of these with the policy file below, so the agent knows the rule it is working under.

### Google Antigravity (integrated development environment, App and command-line interface)

The Google Antigravity integrated development environment, the App and the command-line interface (CLI) share one hook system. A PreToolUse hook can replace the arguments of a tool call, so `process-tree-guard hook antigravity` wraps every `run_command` call in `process-tree-guard-auto.exe` instead of only checking it. The agent keeps writing commands as usual, and each one runs with an automatic deadline and process tree cleanup.

Hooks are read from these files:

- `.agents/hooks.json` in the workspace.
- `~/.gemini/config/hooks.json` for every workspace.
- The CLI also reads hooks inside `~/.gemini/antigravity-cli/settings.json`.

A complete example is in [examples/antigravity/hooks.json](examples/antigravity/hooks.json):

```json
{
  "process-tree-guard": {
    "PreToolUse": [
      {
        "matcher": "run_command",
        "hooks": [
          {
            "type": "command",
            "command": "C:/Tools/process-tree-guard/bin/process-tree-guard.exe hook antigravity",
            "timeout": 10
          }
        ]
      }
    ]
  },
  "process-tree-guard-policy": {
    "SessionStart": [
      {
        "type": "command",
        "command": "C:/Tools/process-tree-guard/bin/process-tree-guard.exe hook antigravity-context"
      }
    ]
  }
}
```

Replace `C:/Tools/process-tree-guard/bin` with the folder that holds `process-tree-guard.exe` and `process-tree-guard-auto.exe`, written with forward slashes. `process-tree-guard-auto.exe` is a copy of `process-tree-guard.exe` under that name (see Automatic mode); a release attaches no automatic copy, so make the copy when installing. An installation that still uses the alias names works the same with `process-guard.exe` and `process-guard-auto.exe` in that folder. An installation that uses the hook role puts `process-tree-guard-gate.exe` and a copy of the deadline role named `process-tree-guard-deadline-auto.exe` in one folder (`libexec` in the install layout) and runs `process-tree-guard-gate.exe antigravity`; see [examples/antigravity/hooks-gate.json](examples/antigravity/hooks-gate.json). The `process-tree-guard-policy` hook injects `POLICY.md` from the folder above that one as a system message when a session starts, so the agent knows the rule it is working under.

How the hook behaves:

- It rewrites rather than only allowing. The new `CommandLine` is `<folder>/process-tree-guard-auto.exe --command-b64 BASE64` (with `process-guard-auto.exe` when the hook runs as `process-guard.exe`), where `BASE64` encodes the original text exactly as received. The wrapper detects the kind of shell from the process that starts it: PowerShell and `cmd` are recognised, and any other parent, including an unknown one, runs the command in Git Bash, which must then be installed at `C:/Program Files/Git`. When the host starts the line from PowerShell or `cmd`, the original command keeps its shell syntax; otherwise it is read as a Git Bash command. This was verified with each of the three shells as the direct parent. Google does not document which shell `run_command` uses on Windows, so check that a PowerShell command still behaves as written on your installation. Nothing else in the tool call changes.
- Its decision is `allow`, never `auto_approve`, so the hook does not bypass the review settings of the person using Antigravity. What those settings see is a separate matter, and it limits what this hook can promise. The rewritten command is `process-tree-guard-auto.exe --command-b64 BASE64`, so an approval prompt, a command allow list or a command deny list may see that Base64 form instead of the original text. A person approving a prompt then cannot read the command, and a pattern such as `rm -rf` or `npm test` may fail to match. Google does not document whether the host evaluates its policy before or after the `overwrite` is applied, or against which text. Do not rely on command-text deny lists together with this hook unless you have verified on your installation which text they evaluate. The `reason` in the decision is a fixed sentence and does not quote the command, so it adds no readable copy of it.
- Commands run in a fresh child shell under the wrapper. The `run_command` arguments `RunPersistent` and `RequestedTerminalID` can send a command to a long-lived shell; when the hook wraps such a command, state it changes in that shell (`cd`, `export` or `$env:` assignments, virtual environment activation) does not carry to later calls. A server or other long-running process started this way is ended when the wrapper's default deadline, two hours or `PROCESS_TREE_GUARD_AUTO_TIMEOUT`, expires. The hook leaves those arguments as the host sent them.
- A command that already has exactly the wrapper form of either name, or is a valid guard envelope naming either name, passes through unchanged. Anything else, including a wrapper path followed by more commands or spelled in another case, is wrapped again; a second guard is harmless.
- A tool whose name is a string other than `run_command` is allowed without change. Only `run_command` is guarded: input sent to an already running terminal or background task through another tool is outside the hook's matcher.
- It fails closed. Unreadable or invalid input, a payload that does not have a `toolCall` object with a string `name` (an unrecognised shape, for example after a schema change), a missing or empty `CommandLine`, a `CommandLine` containing a NUL (null) character, more than one `run_command` argument whose name is `CommandLine` in any letter case (or a repeated `CommandLine` key), the same ambiguity in the `toolCall`, `name` or `args` keys whatever the tool, or a missing automatic copy of the guard's own name beside the guard (`process-tree-guard-auto.exe`, or `process-guard-auto.exe` for the alias; the other name's copy does not stand in for it) is a `deny` with an explanation. The hook reads only the exact keys `toolCall`, `name`, `args` and `CommandLine`; Google does not document how the host chooses between spellings or repeats of a key, so the hook refuses to guess and denies the ambiguous call.
- The guard must be installed in a path made only of the characters `A-Z`, `a-z`, `0-9`, colon, slash, period, underscore and hyphen. The rewritten command writes the wrapper path without quotes, and only such a path parses the same in PowerShell, `cmd` and Git Bash. Any other path, a space included, is denied.
- It always exits with 0 and prints exactly one JSON object and a newline on standard output, so every failure the hook detects is reported as a decision. A hook that cannot start (for example, a missing or unlaunchable `process-tree-guard.exe`), that exceeds its `timeout`, or that crashes is handled by the host in a way Google does not document. Verify the installation by running a command in a session and confirming that it was wrapped.
- Wrapping makes a command longer: Base64 adds about a third, plus the wrapper path. `cmd.exe` cannot run a line of more than 8191 characters, and a PowerShell command fails above roughly 12,000 characters, because the wrapper encodes it a second time to start PowerShell. The hook cannot know which shell the host uses, so it denies a command whose rewritten line would exceed 8000 characters, about 6,000 bytes of the original with the example path, and the reason tells the agent to write the long content to a file and run the file. A line already in the wrapper form is not measured; it passes through unchanged.
- The hook does not change how the host reads the exit code. A host that runs the rewritten line with `powershell -Command LINE` and no explicit `exit` sees exit code 1 for any non-zero exit of the wrapper, the deadline code 124 included, where an unwrapped `exit 9` would read 9; the deadline is still reported as `PROCESS_TIMEOUT` on standard error. Appending `; exit $LASTEXITCODE` to the line, as a host would for any native program, restores the exact code. Git Bash and `cmd` report the exact code as they stand.

## The policy file

`POLICY.md` is an organization policy template written for the agents and people working under the guard. `{{BIN}}` stands for the folder that holds the programs the policy names (`process-tree-guard.exe` and `process-tree-guard-auto.exe`: the `bin` folder in the install layout, see [Where the programs go](#where-the-programs-go)) and `{{POLICY}}` for the installed policy file, both written with forward slashes. Fill them in when copying the file into place; it goes in the root, one folder above the programs (see [Where the programs go](#where-the-programs-go)), which is where `hook cursor-context`, `hook antigravity-context` and the hook's denial message look for it. Adapt the search limits and examples to your environment.

## Build and test

```
cargo build --release
cargo test --release
```

Git Bash, Windows PowerShell and `cmd.exe` must be present. The Google Antigravity tests install the guard under a folder whose path uses only the characters `A-Z`, `a-z`, `0-9`, colon, slash, period, underscore and hyphen, because the hook denies any other install path; they use the build's scratch folder under `target` or, if that does not qualify, the system temporary folder, and stop with a message when neither does (set `TEMP` and `TMP` to such a folder). `cargo test --release` builds the four programs and a small helper executable, `testkit`, that stands in for every child process the tests need (sleepers, exit codes, standard stream relays, argument reporters, markers, process trees and bulk output). The helper is built only for a test run: its `[[bin]]` entry in `Cargo.toml` requires the feature `testkit`, which the crate's development dependency on itself turns on for `cargo test` alone, so `cargo build` and `cargo install` never build or install it (G75). It then runs the unit tests and four integration test crates. The tests take every program from the binaries cargo built in that run (the paths cargo records in `CARGO_BIN_EXE_*`), never by a file name in the build folder, so a stale file left there by an earlier version is never picked up; that holds by construction, and G41 only checks that the recorded files are the ones in use and that no test source contains the literal path of the build folder. They never depend on the file name of the built guard: they copy it into temporary folders under each of its names, the 2.0 name and the alias, as the check needs, and build the install layout and the flat layout of the roles in temporary folders.

Build and test on the MSVC toolchain, so that G39 runs.

A check in a group prints its identifier (`G`, `U`, `B` or `A` and a number) with PASS or FAIL; run `cargo test --release -- --nocapture` to see one line per check. A few tests assert directly and print no line when they pass (G1, G10, G16 to G18, G21, G25 to G27 and U1 to U9); a failure names the test. `tests/PARITY.md` lists every check and the test that covers it, and maps each sentence of the deadline rule in [POLICY.md](POLICY.md) to the test that proves it.

The scaled tests of extendable runs use a unit of one second, except the three cases, which use three seconds, and a grace G of 1.5 seconds. Case 1: a boss with a deadline of 2 units starts A (6 units) and C (4 units) at 0, and A exits at 1; the run ends at 4 units plus G, not at 6. Case 2: A hangs; it ends at 6 units plus G. Case 3: an extendable guard inside a job that is not extendable ends at the outer deadline. The lower bounds are always asserted. So is a structural upper bound for each case, set just under the first wrong answer. A request cannot be made after the boss's deadline, so a run held up by one ends by the boss's deadline plus the hold plus 6 units for the end of the run (the guard waits at most 5 seconds for the tree to go, and half a second for the notice). Where the wrong answer ends a fixed time after a grant, the bound is counted from the time of that grant in the log, not from the start of the run, so that a helper that is late does not move it: case 1 must end before 6 units after the grant for A (which is when it would end if the child that exited still held the run), and case 2 before 7 units after the grant for A (a hold of 6 and a unit for the end of the run; the wrong answer, in which the hold is added to the boss's own deadline and not compared with it, ends at 8 units from the start, and the check tells it from the right one when A asked within the first unit). Case 3 must end before 5 units. A live child's hold, a process that outlives its hold and `extend` must end before the boss's deadline plus their seconds plus 6 units, and a hold that should have been released (a dead child's, the one a library call made) before the boss's deadline plus 6 units, far short of the hold that the wrong answer would keep. The tight upper bounds, the planned end plus the grace G, are reported, not asserted, under `PROCESS_TREE_GUARD_TIMING=info`, which the continuous integration workflows set; there the structural bounds are what is enforced, and they are wide. A bound counted from the start of the run is 26 units for a hold of 12 units under a boss of 8, so a hold that is too long by less than 14 units passes it; by itself it catches only a gross defect, and a defect smaller than the time a helper may take to start (up to the boss's deadline) is caught only on a run with the setting off. Two further bounds are always asserted, for a hold that one process makes, and are the ones that catch a hold of the wrong length. The first is counted from the grant that the log records: the run is not over before the grant plus the seconds granted, and is over before 2 units after that. A late request moves the grant and not the length of the hold, so it holds on any load, and it catches a hold that is too long or too short by about 2 units or more (G54, G56, G57, G63, G74). The second is for a hold that was released (a dead child's, a library call's): nothing is left of it, so the run ends within 2 units of the boss's deadline (G56, G67). A defect smaller than 2 units is caught only on a run with the setting off, and the cases of the deadline held up by children (G51, G52) keep their own bounds, counted from the grant for A.

These bounds hold on a machine that is busy but not oversubscribed. They are not proof against any load. A helper that is starved of the processor for longer than the boss's deadline asks too late and is refused as late ("the run has ended"), the run then ends at the boss's deadline, and the test fails on a lower bound; on such a machine a correct run can also end after a structural bound. A test whose helper has to start and ask inside the boss's deadline gives the boss 8 seconds or more (6 in cases 1 and 2, whose boss has 2 units of 3 seconds), where an idle machine needs a fraction of one; a runner that is oversubscribed beyond that can still fail them, and the failure is then about the load, not about the guard.

Environment variables for the tests:

- `PROCESS_TREE_GUARD_EXE`: test the guard at another path instead of the one just built. The 1.x name `PROCESS_GUARD_EXE` is read when it is not set.
- `PROCESS_TREE_GUARD_TIMING=info`: report the bounds on time and load without failing the run, for a busy machine or a shared continuous integration runner. By default they are asserted. The 1.x name `PROCESS_GUARD_TIMING` is read when it is not set; if both are set, the first decides.
- `PROCESS_TREE_GUARD_REQUIRE_RESOURCES`: set to any text to make G39 fail, rather than print its `NOTICE` line, when the programs carry no version resource. It is also required when `CI` is set.
- `PROCESS_GUARD_PREVIOUS`: path of an earlier guard executable; the battery then reports how its launch time compares.

Test executables compiled on another machine can be copied to a Windows machine and run there: when the binary path recorded at compile time does not exist, the programs and `testkit` are taken, under the same file names, from the folder above the test executable. The GNU target is unsupported (see [Programs](#programs)).
