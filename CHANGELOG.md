# Changelog

## 2.0.0-alpha.5

Windows Hello for the exception above the cap. The default method, `--authenticate desktop`, now asks for the consent of Windows Hello (`UserConsentVerifier`: the Personal Identification Number (PIN), fingerprint or face of the signed-in user) and shows the Windows credential dialog only where Windows Hello is not available. On a machine whose user signs in with a PIN the credential dialog returned the password in a protected form, which the guard refused; Windows Hello is the way Windows confirms that the signed-in user is present, and the Trusted Platform Module (TPM) limits the guessing of a PIN where the machine has one. `--authenticate console` and every refusal that comes before a prompt are unchanged.

Added:

- The consent of Windows Hello. The order is: the starter is looked at; somebody must be present and no other prompt of the guard may be open (one right, held for the rest of the run); Windows Hello is asked whether it is available (`CheckAvailabilityAsync`, which shows nothing, with a limit of 5 seconds); if it is, the guard must run as the user signed in to its session; the starter is looked at once more; one request is made (`IUserConsentVerifierInterop::RequestVerificationForWindowAsync`) and only `Verified` approves. `Canceled`, `RetriesExhausted`, `DeviceBusy`, `DeviceNotPresent`, `NotConfiguredForUser`, `DisabledByPolicy`, an error of the system and no answer each refuse the run with exit code 125 and a reason that names the result, and a consent that was asked for and not given is never answered by the password dialog. The log line of a run that Windows Hello decided has `method="hello"`, `attempt=1` (0 when it was refused before the request) and, when it approves, the reason `a cap of N hours was approved: Windows Hello verified the signed-in user`.
- The user that is verified. Windows Hello verifies the user who is signed in to the session, not necessarily the account the guard runs as, so the guard approves only when it runs as that user: the domain and user name of the session (`WTSQuerySessionInformationW`) are compared with the name of the account the guard runs as, and by security identifier when the names are not written alike. A guard started as another account (for example with `runas`) is refused before any request, with a reason that names both accounts and `attempt=0` (where the system says that Windows Hello is not available to that account, the credential dialog asks for the password of that account instead).
- Where the request is read. A face can be matched with no act by the user, so the guard asks Windows Hello only on the desktop that receives the input of the user (`OpenInputDesktop`, compared with the desktop of the guard by name). A guard started on another desktop of the window station, while the screen is locked or while the screen saver runs, is refused before any request, with `attempt=0`, the method `hello` and a reason that says to start the run on the desktop that the user is looking at; the password is not asked for instead.
- What a result shows. A face, and on some devices a fingerprint, can be matched as soon as the prompt appears, with no deliberate act by the user, so `Verified` shows that the signed-in user was present and not that the user read the message; the message begins with how to refuse, and step 12 of the manual check records what each kind of device does. A result is read into a value that is none of the results of Windows Hello before the system fills it, so a call that leaves it alone cannot read as `Verified`.
- The wait. The request waits at most 300 seconds and the process that started the guard is watched meanwhile. When the time is up, or the starter exits, the guard cancels the operation (`IAsyncInfo::Cancel`), waits up to 3 seconds for the system to report it, and exits at once with 125. What the system does with a prompt that is still open at that point is not claimed; steps 5 and 12 of the manual check record it. The request is owned by a window of the guard that is never shown (a tool window of zero size), because a desktop program needs one. The window drops the timer messages that a program of the same user posts to it or to its thread, and serves at most 256 posted messages between two looks at the request (a message that another process sends to it is handled by the system and is not counted).
- The message of Windows Hello begins with how to refuse and names the command line (100 characters once written out), the program (40), the account (30) and the process that started the guard (40), then the cap and the deadline the run starts with, with the escaping, the cuts and the note of the credential dialog, and ends with how to refuse again (`Cancel to refuse it.`), as the credential dialog does. It is kept to 512 16-bit units: a text that is longer is made again with a smaller share of each field, and one that would still be longer is refused before it reaches the system. How the system clips it is not established; the limits are defaults, and step 12 of the manual check reads the whole text in the prompt.
- Windows Runtime and window calls bound at run time from the system folder (`combase.dll`, `user32.dll`, `wtsapi32.dll`), written in Rust over the v-tables of the interfaces: no new crates, no helper program and no PowerShell. The contain role and the automatic copies import none of them (G96). The identifiers of the generic interfaces that are used are recomputed from their signatures by a unit test.
- Tests: 3 new checks and 34 new unit tests. The unit tests are of the decision with a scripted consent (including a starter that exits before the request and a verification that no record holds), the check of the user of the session, the message, the record of a run that Windows Hello decided, the loop that waits for an operation and its cancel, the wait of the owner window when the system cannot make it, the reading of an operation through the slots of its interfaces (an operation made in the test, which shows that a result the system leaves unwritten is not a verification, and the question whether Windows Hello is available, cancelled at once for real, which shows that the cancel reaches an operation of the system), the unprotecting of a password, the identifiers of the interfaces, the hook that zeroes the buffers of a secret on a panic (installed by the making of any such buffer, shown in a copy of the test executable that nothing else has set up), and the refusal of the seat and the length check of the credential dialog. G96 also checks that every library is loaded by one call that names the system folder. The checks are G102 (the request is made in one place, after the presence, the lock, the question and the check of the user), G103 (the record of the desktop method on a window station that is not visible, with nothing asked of Windows Hello) and B149 (what the documents say). No test makes a request for Windows Hello or shows the credential dialog.

Changed:

- Where Windows Hello is not available (it is not set up, a policy disables it, there is no device or the device is busy, the Windows Runtime is missing, or the question is not answered within 5 seconds) the credential dialog asks for the password as before, listing only the accounts of the current user, and the reason of every line of the log on that path ends with `(Windows Hello was not available: NAME)`. The 3 attempts, the check with `LogonUserW` and the match of the account apply to the credential dialog and the console prompt only.
- A password that the credential dialog returns in a protected form (`CredIsProtectedW`) is now unprotected with `CredUnprotectW` into a buffer that is wiped like the other secrets, and checked like a typed one, where it was refused. The dialog's answer is read with a buffer of up to 4096 characters when the system asks for a larger one. The clear password is therefore in memory for a short time, as at the console prompt. A form that cannot be unprotected, or whose clear text is longer than a password can be, uses an attempt and no logon is tried for it.
- `method=` in the log is `desktop`, `hello` or `console`. For a run that Windows Hello decided, `command=` and `started_by=` are cut as the message of Windows Hello cuts them (100 and 40 characters once written out, fewer where that message had to be cut further), so a line never shows more than the user was shown. A run may wait up to 1100 seconds when it falls back to the dialog (the question about Windows Hello adds up to 5 seconds to the 1095 of alpha.4), and under 319 seconds when Windows Hello decides.
- `POLICY.md` says that a `--max-extension` above six hours needs the signed-in user's approval, by Windows Hello or by password.
- The message of Windows Hello names the parent process as `Parent process, as reported`, which keeps the caveat of the credential dialog in a shorter form: the launcher chooses the parent, so the field is information and not proof of who started the run.
- The scan of the test sources for a run over the default cap (G93) now accepts only `--authenticate console` beside it; the desktop method, which shows a window, no longer covers a cap.
- The error of a run that is built with a cap over the default and no means of asking (a caller of the library) now says that the cap needs the approval of the signed-in user, where it said the password of the account the guard runs as.
- The manual check of the prompts has a step 12 for Windows Hello (approve, cancel, a wrong PIN until `RetriesExhausted`, no answer for 300 seconds, the guard ended from outside while the prompt is open, Windows Hello not set up, `runas` as another account, a long command, the placement of the prompt, a PIN-only account in the fallback and a Remote Desktop session).

Not asserted by the tests: Windows Hello in any form (that the system accepts the request, shows its prompt with the message of the guard and how it clips it, puts it in front of the other windows of the user with an owner that is never shown, asks again for every request and does not reuse a recent verification, reports a cancel and a wrong PIN as the code expects, and closes the prompt when the request is cancelled or the guard ends; the manual check, step 12, is the only evidence), that the desktop that receives the input of the user cannot be opened while the screen is locked and can be opened on every desktop that the user is looking at (step 12 again), and that the protected form of the password unprotects for each type of account.

## 2.0.0-alpha.4

The exception above the cap. A top-level `--extendable` run whose `--max-extension` is over the default cap of 21600 seconds (six hours), up to the largest of 86400, is a per-run exception: before the job is made and before the command starts, the guard asks for the password of the account it runs as (the signed-in user in the usual case), and the run starts only if it is given. Apart from the changes listed under Changed, nothing else changes: a cap at or below 21600, a run without `--extendable`, the contain role, automatic mode and the hook envelope never prompt (automatic mode refuses the options itself, and the envelope check does not accept a line that carries them as an envelope), a guard started inside an extendable run (a nested guard) is refused before anyone is asked, and every deadline stays finite and logged. A guard that another guard started, the automatic wrapper that a host puts in front of every command included, is not asked either: a line that carries the options is not an envelope, so the hooks that only allow or deny refuse it and the rewriting hooks wrap it whole as the command text of the automatic wrapper, and the guard that this starts is refused before any prompt, lock or logon, because a command that an agent runs is such a run and an agent must not be able to summon a prompt or guess a password by one. The exception only raises the cap of one run.

Added:

- `--authenticate {desktop,console}`, with `--extendable`; `desktop` is the default and any other value is an error (exit code 125). It is read and ignored at or below the default cap. The usage text names it.
- The desktop prompt: `CredUIPromptForWindowsCredentialsW` on the secure desktop, showing only the accounts of the current user, then `CredUnPackAuthenticationBufferW`, through system calls bound at run time from the system folder (no new crates and no start-up dependency). Its caption is the product name.
  - The message names, first and each in square brackets, the command line, the program as the search found it, the account whose password it asks for and the parent process as the system reports it (the nearest one, as the system gives its path; the parent is chosen by the launcher, so it is information and not proof of who started the run). Then it says what is being allowed (the processes of the run may each ask to keep it alive for up to the cap at a time, in hours rounded up to two decimals with the seconds beside a figure that is not exact, and may renew without a total limit), the deadline the run starts with, and how to refuse.
  - Each field has a limit in characters once written out (the command line 140, the program 80, the account 40, the parent 80), and a count of what was cut: the command line keeps its start, and the program, the account and the parent keep their end, which holds the file name or the user. The whole message stays under 1,024 characters, the limit of the dialog. Every character that is not printable basic Latin, the letters and digits of other scripts that can look like Latin ones (a Cyrillic o for the Latin o), the blanks and spaces of other scripts and the marks that stack over the text among them, and the square brackets, is written as `\u{..}`, with a note in the message when a field has a character outside basic Latin. A command that is run with `--shell` is shown decoded, and the arguments of a program are quoted as they will be started.
  - The approval is of the text shown, not of the content of the program.
  - A run that sits inside a job with a shorter deadline that the guard did not recognise as a guard (see the two tests under "a run that another guard started" below) ends with that deadline, whatever cap was approved.
  - Both prompts make all their calls on one thread, so that the second and third attempt of the desktop prompt are shown and are not cancelled at once (the console prompt needed this; the desktop prompt is the same library); only the manual check shows the desktop prompt.
  - There is no consent path of Windows Hello: a Personal Identification Number (PIN), a fingerprint, a face or a smart card is not expected to unpack to a password (the manual check records what each does), so an account that signs in with a PIN or a smart card alone is expected not to be able to approve, and an empty password never approves. If a PIN does unpack under the account's own name, it is sent to `LogonUserW` as a password and counts toward the lockout of the account. An answer that cannot be read as a name and a password is an attempt used, with no logon tried, and so is an answer whose password comes back in a protected form (`CredIsProtectedW`), which is not sent to the logon where it would fail as a wrong password and count toward the lockout; the manual check records what a PIN and a smart card do, and for which types of account the prompt returns the password in clear text.
- The console prompt: `CredUICmdLinePromptForCredentialsW`, accepted only when standard input is a real interactive console (`GetConsoleMode` and `GetNumberOfConsoleInputEvents` both succeed on it, the second call being what rejects the screen buffer of a console), never a pipe, a file or the null device. A pseudo console, which a process of the same user can create, also passes this test (see `SECURITY.md`).
  - The message is written to the console once (the write has a limit of 5 seconds), and the user name field is filled with the account the guard runs as, so that the prompt asks for the password alone; the name cannot be changed there. Only if the guard cannot read its own account name does the prompt also ask for a name, and that name is looked up before any logon is tried (another account's, or no account's, makes no logon and uses an attempt).
  - The console prompt is not known to have a cancel key. What Esc, Ctrl+C and Ctrl+Z with Enter do has not been tried: Esc and Ctrl+Z with Enter are expected to leave it waiting or to give an empty answer (an attempt used), and Ctrl+C may end the guard, which also refuses the run; step 6 of the manual check records which. The message therefore tells the user to refuse by leaving the prompt unanswered for 300 seconds or by closing the console; three empty answers refuse the run too.
  - The call needs `CREDUI_FLAGS_EXCLUDE_CERTIFICATES` (without it the system answers with the error for invalid flags), is made with `CREDUI_FLAGS_ALWAYS_SHOW_UI` (so that a generic credential stored under the name of the product does not stand in for the person) and with nothing saved, and all its calls in a run are made on one thread of their own (a call made on a new thread after the first thread had ended was cancelled at once). The prompt reads with echo off; the guard puts the console mode back when the prompt returns or its wait gives up, and on a control event that ends the guard while it reads (Ctrl+C, Ctrl+Break, closing the console), but not when the guard is ended from outside (Task Manager). After every console prompt it clears the command history that the console keeps for its own executable name.
  - A program that can start the guard in a console it drives can guess the password, three tries per start, with a wait of 2 seconds between tries: the account lockout policy of the system is the only limit across starts (see `SECURITY.md`).
- Nobody present: the desktop prompt is refused without showing anything when the process has no interactive window station or runs in session 0; the console prompt as above. These are refused too, each with exit code 125 and the reason, and the command never runs:
  - a cancel of the desktop prompt, and no answer within 300 seconds (the guard exits at once, without the wait that follows another refusal, and leaves the dialog or the console read to end with the process);
  - the process that started the guard exiting while a prompt is open;
  - another prompt of the guard open in the same session or refused less than 10 seconds ago (a refusal after a prompt was shown keeps the right to a prompt for 10 seconds before the guard returns, so that guards started in a loop do not put one prompt after another on the screen), or another program holding the name of the lock that keeps prompts apart, which denies the exception to every run in the session and approves nothing;
  - a run inside an extendable run (refused as nested, before anyone is asked);
  - the process that started the guard cannot be opened and watched (it has already exited, it cannot be opened, or its identifier was taken by a process that started after the guard): the reason begins "the process that started the run cannot be watched", before any prompt;
  - a run that another guard started (the automatic wrapper, or the guard that a hook's rewritten line starts): refused before any prompt, lock or logon, with the reason "an exception above the cap is not asked for by a run that another guard started" and `attempt=0`; the reason ends with the cause, the file name of the program found above the guard or the job that kills its processes when it closes. Two tests make the refusal:
    - by file name: the live processes above the guard that the search reaches are looked at, nearest first, for the programs of the guard (`process-tree-guard.exe`, `process-guard.exe`, the deadline and contain roles and the `-auto` copies) and for any file name ending in `-auto`, which selects automatic mode; a copy under any other name is not recognised, which only a process of the same user can make. The search follows the parent chain while each parent is alive, started before its child and is not one of `explorer.exe`, `services.exe`, `wininit.exe`, `winlogon.exe`, `svchost.exe` or `smss.exe` at its system path (`explorer.exe` in the Windows folder, the other five in `System32`; a program of one of those names in any other folder, one under the Windows folder included, is a copy that a process of the user may be able to make, and is walked past like any other process), for at most 32 levels; a parent that has already exited ends it, so a command started through a launcher that exits before the guard runs is not seen to be under a guard by this test, and a launcher can name a parent of its choice;
    - by job: every job a guard makes kills its processes when it closes, so a process whose innermost job does so is refused, however its chain of parents looks, unless the process has put itself in a job of its own, which any process of the user can do with three calls (nested jobs are allowed, and the test programs of this repository do it); the test refuses commands that were not written to avoid it. This also refuses a guard started from inside a host that puts its terminal in a job of that kind (continuous integration runners, some editor terminals), which must start the guard from an ordinary terminal.

    An agent that runs as the same user outside a guard job, that puts its own process in a job of its own (a nested job replaces the innermost job that the job test reads) and starts the guard from a process whose parent has exited, or that can set its own parent, can still summon a prompt; the password is still required.

  The process that started the guard is opened before the first prompt, taken only if it started before the guard did (a reused identifier is refused), and watched during every wait, so a prompt is not answered for a run that nobody started; the handle that was watched is the one the run is watched against afterwards.
- The check: `LogonUserW` with the user name, domain and password as an interactive logon, and the security identifier of the token's user must equal that of the guard's own token. The check runs on a thread and is given 60 seconds.
  - The logon is the check Windows sign-in makes and works with cached domain credentials. The look up of the name before it is local when the name is the guard's own account name as the system writes it, and otherwise may contact a domain controller, in which case a run is refused with the error of the system where none answers; an approval with the domain controller out of reach is not asserted. It makes a logon session, event 4624 type 2, which closing the token ends, and caches the logon information as a sign-in does. Each wrong password writes a failed-logon event (4625) on the machine, or on the domain controller for a domain account, and counts toward the lockout threshold, which writes a lockout event (4740); monitoring will see them, at most three per run. Three attempts per run can equal the lockout threshold of a hardened machine: where the threshold is 3 or fewer (the setting of the Defense Information Systems Agency (DISA) Windows Security Technical Implementation Guide (STIG)), one run in which three wrong passwords are typed locks the account out of Windows, and for a domain account the failures also count toward the threshold of the domain; set the threshold to at least 5 on the machines that use an exception, or enter the password with care.
  - An account without the right to log on locally fails with 1385 (or 1380, which has the same text) and cannot approve. At the console prompt those errors, and the other errors that Windows gives only for a correct password (1327, 1328, 1329, 1330, 1331, 1380, 1385, 1793 and 1907), are given the reason of a password that is not accepted and use an attempt, so that a program that types cannot learn from the refusal that a guess was right.
  - At most 3 attempts per run, each failed `LogonUserW` counting toward account lockout, with a wait of 2 seconds before the next prompt after a name or password that was not accepted (it slows a loop of guesses and does not stop it); a cancel, a prompt that cannot be shown and a failure that more attempts cannot mend end the run at once.
  - A name that is unknown, a password that is wrong and an account that is not the guard's own are given the same reason; an empty password has a reason of its own, since it is not a secret and no logon is tried for it.
- The run's own deadline starts when the command starts, after the approval; the wait for the prompt is bounded at 300 seconds for each of at most 3 attempts, so a run may wait up to 1095 seconds, a little over 18 minutes (3 prompts of 300 seconds, 3 checks of at most 60 seconds, 2 waits of 2 seconds, 5 seconds each for the name of the account and, with the console method, for the write of the message, and half a second for the record of the approval on standard error), before it starts.
- The log: every attempt and the outcome is a line with `account=` (the account the guard runs as) and `command=` (the command line as the prompt shows it), so that the record says what was approved and for whom, `method=` (`desktop` or `console`), `timeout=` (the deadline the run starts with, in seconds) and `started_by=` (the nearest process that started the guard, as the prompt shows it), `decision=exception-approved` or `decision=exception-refused`, `requested=` (the cap in seconds), `hours=` (the same cap in hours, rounded up to two decimals), `attempt=` (0 when the prompt was refused before one was shown) and a `reason=`. Neither the password nor anything that was typed is in a line. The command line is in the line (the first 140 characters once written out, as the prompt shows them), so a secret passed as an argument is written to the audit file and to standard error; pass secrets by environment variable or file, not by argument. An approval stands only if its line is recorded: with an audit file the guard waits for the file to write it, and a file that cannot take it refuses the run. A refusal line is queued and the guard gives the file 500 milliseconds to take it before it returns; the refusal itself is also the error on standard error and the exit code 125. A run whose exception was approved and which then fails to start (the job cannot be made, or the command cannot be started) writes a notice line, `the approved run did not start: ` with the reason, so that the record does not show a cap approved for a command that never ran.
- The password lives only in buffers zeroed with volatile writes when they are dropped, on every path (the authentication buffer from the prompt is zeroed over its whole size and freed), never in a `String`, never logged, never echoed. The release profile aborts on a panic without running destructors, so a panic hook zeroes every buffer that holds the password before the abort; the buffers are not locked in memory, so a crash dump, the page file or the hibernation file can hold the password (`SECURITY.md`).
- Seam for tests: the attempt loop is driven through two traits, with stubs that exist only under `cfg(test)`. No argument, environment variable, file or feature selects a stub, so a release program has none; the only items compiled for a build that is not a test are the wait between attempts and the choice of the thread whose buffers the panic hook zeroes (all of them in a program), and neither decides anything.
- `POLICY.md` gains one sentence: a `--max-extension` above six hours needs the signed-in user's password at the start of the run, and a run where nobody can give it is refused, and so is a run that another guard started, so the person starts such a run from a terminal that is not under a guard. `SECURITY.md` adds the exception to the scope and states that it resists accidents and agents without the password, not a process of the same user that can tamper with the guard (National Institute of Standards and Technology (NIST) Special Publication (SP) 800-63B, verifier impersonation resistance), and that a deadline without `--extendable` and renewal at the default cap need no password. `README.md` describes both prompts and the refusals, and `CONTRIBUTING.md` lists the eleven steps of the manual check of the prompts.

## 2.0.0-alpha.3

Deadlines held up by the processes they run. A run started with `--extendable` lets the processes in its job ask for more time, within a cap and with every request logged. A run started without it has a fixed deadline, no channel, no new environment variable and no log, and keeps the clock of 2.0.0-alpha.2. A few changes reach every run, extendable or not; they are listed together at the end of the section.

Added:

- Extendable runs: `process-tree-guard --extendable [--max-extension SECONDS] [--extension-log PATH] --timeout SECONDS COMMAND...`, in the full command and the deadline role. It is never automatic mode and never the hook envelope. The command is given a private channel, a message-mode named pipe with a random 128-bit name, named in `PROCESS_TREE_GUARD_CHANNEL`. The pipe is made with `FILE_FLAG_FIRST_PIPE_INSTANCE` on the first of four instances (the most the pipe allows, all made by the guard before the command starts, each served by a thread of its own), `PIPE_REJECT_REMOTE_CLIENTS`, no outgoing buffer and an access list for the current user alone.
- The cap: `--max-extension SECONDS`, 21600 by default and at most 86400, read only from the launch arguments. The run's own `--timeout` is held to the cap, so that the rule in `POLICY.md` holds from the first moment.
- Renewal: a process that asks again before its hold ends keeps the run up, and there is no limit on the whole life of a run. Each request is within the cap, in the log and made by a verified process in the job, and a run whose processes stop asking, or hang, ends at the latest hold.
- Holds: a granted request holds the deadline for the process that asked, by its handle and never by its identifier, for the granted seconds from now. A hold ends when its process exits. The deadline of a run is the latest of its own deadline and the holds of live processes, recalculated under one lock on every grant and every exit, with the job's completion port and, as a backstop, a poll every 100 milliseconds of each holder and of the job's list of processes. When it passes the tree is ended and the exit code is 124. A request that arrives after the deadline is refused, even if the supervisor has not yet noticed that it passed.
- Limits on holds: 256 at once, and 8 for one process (all its holds together, whatever their numbers), so that one process cannot take the table from the rest. A ninth hold of a process is refused with "this process holds too many deadlines"; a full table is refused with "too many processes hold the deadline". Processes of the job can still fill the table between them (32 are enough), which denies the channel to the rest of the run until those holds end and never moves the deadline.
- Verification: before it replies, the guard checks that the client is alive, is in its job (the jobs nested inside it count) and started before the connection, and, after it has read the request, that the client's end of the pipe is still open: a client waits for its reply with its end open, so a request whose end is closed is refused as not verified, which closes the window in which a process that took the identifier of a client that had written and exited could be taken for it. Messages are fixed-size (24 and 40 bytes). Requests are rate limited to 12 per process in 10 seconds; the table that tells processes apart holds 1024 live ones, and a process that has exited is forgotten when it is full.
- A reply and its hold agree: the guard sets the hold, sends the reply and waits half a second (a quarter of a second for a process over its share) for the client to read it. A client that sends a valid request and reads later gets an error and no reply, and the guard withdraws the grant: the hold goes back to what it was before the request, the deadline is recalculated and the log has a `decision=withdrawn` line after the `granted` line. A nested guard that did not get its reply exits with 125 and runs nothing, and `extend` exits with 125. A reply to a release that is not taken leaves the hold ended.
- `process-tree-guard extend SECONDS` (and the library call `extend`) asks the enclosing run. The program asks for the process that ran it, because it ends at once; under Git Bash that is the shell that goes on, not the short-lived copy of `bash.exe` that Git Bash makes to run the program, and the `PROCESS_TREE_GUARD_GRANTED` line ends with `held=ID image="NAME"`. The library call asks for the calling process. Exit code 0 and the granted deadline on success; 125 and the reason when refused (no run, not in the job, over the cap, a limit, a run that has ended). The number is sent as it is and the run refuses a value that is not finite, not above zero or over the cap; text that is not a number is refused before it is sent. A client waits at most five seconds for the reply, and accepts a reply only when it is well formed and its numbers are in range; anything else is an error with exit code 125. The hold lasts only as long as the process held stays: `extend` as the last command of a `cmd /c`, `powershell -Command` or `bash -c` one-liner holds a shell that exits as the program returns, and the deadline does not move although the grant is printed and logged. The README says so and points to the library call `extend(seconds)` and to a script that goes on after the call.
- Nested guards: a guard started inside an extendable run, in any role or mode, asks the run for its own `--timeout` as it starts. If that is over the cap, or the run refuses, it exits with 125 and the refusal is logged. An extendable guard inside a job that is not extendable ends at the outer deadline.
- Library calls inside a run: `run`, `run_shell` and `run_auto` made by a process inside an extendable run ask the run for their `seconds` as a nested guard does, and the hold is ended when the call returns, by a release request that is a line of its own in the log (`decision=released`) and is let past the rate limit when it ends a hold. Each call is one request against the 12 per process in any 10 seconds, so a host that makes a 13th call inside the window has it refused with the reason, and its command does not run. Each call has a hold of its own (the request and its release carry a 56-bit number that names the hold; `extend` and the programs use 0), so calls that overlap, from threads of one process, do not replace or release one another's holds or the hold of `extend`, and the run waits for the latest of them. The programs are not affected: their hold ends with their process.
- `process-tree-guard-contain` (installed in `libexec`, file description "Process Tree Guard: Contain"): runs a command in a job of its own as a child of an extendable run; its `--timeout` is the request. With no run around it, it exits with 125 and runs nothing. It takes no extension options and has no automatic or hook mode. Releases attach it.
- The log: every request and every grant is a line on standard error that starts with `PROCESS_TREE_GUARD_EXTENSION:` and, with `--extension-log PATH`, in that file, bounded at one mebibyte (MiB) with one rotation. A line has the time, process identifier, image name, seconds requested and granted, decision and reason. Refusals are lines too, within limits that are a stated decision, a departure from a line for every single refusal: the first refusal of a process for the rate is a line and opens a window of 10 seconds, and the rest of that window are one line with their count (`N more refused within 10 seconds of the first`), written when the window ends; all clients outside the job share one allowance of 12 requests in 10 seconds, and one outside the job over its allowance is disconnected at once, counted and not logged one by one; at most 24 refusal lines are written in any 10 seconds, the rest being one line with a count. Grants are always lines of their own. The seconds are written exactly as asked, in a bounded number of characters (scientific form from 10^15 or below a millionth, `invalid` for a value that is not a finite number). Control characters, line separators and format characters (the bidirectional controls, the zero width characters and the byte order mark) are escaped (Common Weakness Enumeration, CWE-117 and CWE-451). The log is an audit record, not a control.
- Log destinations: the copies of the log are written by threads of their own from bounded queues of 256 lines, one for standard error and one for the file, so nothing the log is written to is waited for; a full queue drops lines and says how many. The last lines get half a second to be written when the run ends. The audit file is held open for appending for the whole run, so a reader that does not share writing (the default of .NET's `File.OpenRead` and `FileStream` for reading) is refused when it opens the file, and a reader that opened the file before the run began stops the guard at its start, with 125. A turn over of the file renames it to `PATH.1`; a program that follows the file and holds it open without `FILE_SHARE_DELETE` (PowerShell `Get-Content -Wait` does) stops the rename, and the guard then copies the file to `PATH.1` and empties it. When that fails too the file could not be turned over, so it grows toward twice the limit with a notice line, and tries again once a second, whether or not a line comes; standard error has every line. `PATH.1` is not held open by the guard, and any program in the job can stop both ways of turning the file over by opening it for reading and sharing reading only (no setting of the folder prevents that), so the run does not carry on and lose lines (CWE-778; National Institute of Standards and Technology (NIST) Special Publication (SP) 800-53 control AU-5): when the file cannot be turned over and has less than 64 kibibytes (KiB) left before twice its limit, or when its lines cannot be written, the run grants nothing, every request that would move a deadline is refused with the reason, and the run grants again once a turn over or a write works. A run started with a file that is past its limit, cannot be turned over and has no such room does not start (125). A write that fails is not silent: the guard tells standard error at once, keeps the lines (up to 256), tries again every half second, writes them in order when the file takes lines, and then puts a notice with the counts in the file and on standard error; the end of a run says how many lines the file never got. A collector should open the file with `FILE_SHARE_WRITE` and `FILE_SHARE_DELETE`.
- The log file is a bound on disk space, not a promise to keep lines. Grants are not budgeted, so a process in the job that starts many short-lived processes, each asking once, can turn the log file over, and its one rotation, in a few minutes and push every earlier line out, the refusals among them. The file is evidence of what happened before such a flood only if it is copied off the machine promptly. The copy of the log on standard error is not evidence, since the command shares that stream; the file named by `--extension-log` is evidence only against a process that cannot open it. The guard and the processes in the job run as the same account, so a process in the job can append a line in the form of a grant to the file, or delete or replace it, and no setting of the folder prevents that. The file is a record to rely on only where the command is kept from it by a boundary of another kind (another user, a container or a virtual machine), or where a collector ships the lines off the machine as they are written. The README and `SECURITY.md` say so.
- Standard error as the only record: without `--extension-log`, standard error is the only record of the grants, and the run holds its grants to it, so that the rule in `POLICY.md` (a deadline moved only by a logged request) holds without the file. A run does not start (exit code 125) when standard error is closed or is the null device and `--extension-log` was not given. A grant is made only once its line has been written to standard error: the run waits for the line for at most half a second, and when the write fails or does not finish in that time it takes the grant back (the hold goes back to what it was, the log has a `decision=withdrawn` line and the process gets the refusal "the audit file (or standard error, when there is no audit file) cannot take lines, so nothing is granted until it can"). After a write to standard error has failed the run grants nothing until a write works. Releases and refusals are not held to this, and with `--extension-log` standard error is a copy and none of it applies. The run cannot tell a standard error that is a pipe or a file whose reader keeps nothing from one that records: a launcher that needs the log as evidence passes `--extension-log` and reads the file. The README and `SECURITY.md` say so.
- Audit file: `--extension-log` must name a file on a disk. A device (the null device, a console) or a pipe takes every write and keeps none of it, so the run does not start (exit code 125, "the extension log must be a regular file").
- Clock: an extendable run measures its deadlines with `GetTickCount64`, which counts the time the machine is asleep. A run without `--extendable` keeps the clock of 2.0.0-alpha.2, whose wait does not count time asleep on Windows 8 and later. The README states both, and that a run without `--extendable` never moves its fixed `--timeout`, at most 86400 seconds.
- The notice `PROCESS_TIMEOUT: exceeded N seconds; terminating process tree` names the `--timeout` as it was given in a run without `--extendable` (`exceeded 2 seconds`, `exceeded 0.5 seconds`), and the seconds the run lasted, to the millisecond, in an extendable run (`exceeded 10.19 seconds`), whose deadline moves. Both are plain decimal numbers; a consumer that reads the number as a whole number must read the second as a decimal.
- `POLICY.md` defines a finite deadline directly after its first sentence: at every moment a fixed time no more than `--max-extension` ahead, set or moved only by an explicit, logged request from a verified process in the guard's job. The sentence after it says that a server or process is unlimited when it runs past its deadline, or when its deadline moves by any other means. `tests/PARITY.md` maps each sentence of the rule to the test that proves it (a move that nobody requested is refused; a process past its deadline is killed).
- `SECURITY.md` adds the channel, the holds, the replies and nested guards to the scope, and states that access by a process of the same user is not a security boundary: the cap, the verification, the limits and the log are the controls. It also states what a process in the job can still do (stall the four instances, fill the table of holds with the help of others, turn the log file over), and what a client does not check (which process serves the channel). `README.md` and `SECURITY.md` state that containment is not a boundary against a hostile process of the same user inside the job: such a process can suspend or write to the guard, duplicate a handle to the job, or ask a service of the system (Windows Management Instrumentation, the Task Scheduler, a Component Object Model server) to start a process outside the job. The guarantees that nothing outlives the deadline hold for commands that do not do this on purpose.
- Library: `extend`, `Grant`, `CHANNEL_VARIABLE`, `DEFAULT_MAX_EXTENSION` and `main_contain`.

In 2.0.0-alpha.2 the notice was written first. The same holds with `PROCESS_GUARD_TRACE` set: the trace lines are kept while the run goes on and written, with the notice, once the tree has ended, where in 2.0.0-alpha.2 each was written as it was made, so that a full standard error held the guard at that line past the deadline; a closed standard error no longer ends the guard with a crash.
- Whole lines: each line the guard puts on standard error (the log lines, `PROCESS_TIMEOUT`, `PROCESS_OWNER_EXITED` and `PROCESS_GUARD_ERROR`) is written with one call, so a line written at the same moment cannot land inside another (CWE-362). A standard error or standard output whose reader has gone does not end the guard with a crash (0xC0000409), in any mode: the exit code (124, 125, or the command's own) is kept, a request that was granted exits 0, and `--help` and the usage text of the gate exit 0. - Every guard reads `PROCESS_TREE_GUARD_CHANNEL`: when it names a live channel, the guard asks that run for its deadline (this is how a guard is a nested guard). A value that is not the name of a channel, or names one that is gone, is read as no run around the guard, which keeps its own fixed deadline and runs its command as in 2.0.0-alpha.2, so no setting of the variable can stop the guards of a host from running commands; `extend` and the contain role refuse it, since they have no run to ask. A value that names a pipe that is there and does not answer as a run ends the guard that reads it with 125.
- `--max-extension` and `--extension-log` without `--extendable` are refused with "need --extendable" in place of "unrecognized arguments".
- The usage text that `--help` prints, and the usage printed for a command line that is not understood, has a second line, `process-tree-guard extend SECONDS`, and names the extension options.
- The test helper `testkit` is no longer a program that `cargo build`, `cargo install --path .` or `cargo install --git` builds or installs: its `[[bin]]` entry requires the feature `testkit`, which only the test run turns on (a development dependency of the crate on itself), and `autobins = false` makes the four programs explicit. The helper can suspend the threads of a process of the user and flood a channel, so a source install does not carry it.

The tests read `PROCESS_TREE_GUARD_TIMING`, then `PROCESS_GUARD_TIMING`, and `PROCESS_TREE_GUARD_EXE`, then `PROCESS_GUARD_EXE`, in the same way.

## 1.5.0

Google Antigravity support (integrated development environment, App and command-line interface).

- `hook antigravity` is a PreToolUse hook for the `run_command` tool. It rewrites `CommandLine` to a call to `process-guard-auto.exe` in the guard's own folder, so every shell command runs under an automatic deadline and process tree cleanup. A command that already has exactly that form, or is a valid guard envelope, passes through unchanged.
- The hook answers with `allow`, never `auto_approve`, so it does not bypass the user's own review settings. Limit: review prompts and command-text allow or deny lists may see the Base64 form (`process-guard-auto.exe --command-b64 BASE64`) instead of the original command, so an approver cannot read it and a pattern such as `rm -rf` may not match. Google does not document whether policy is evaluated before or after the rewrite, so command-pattern deny lists should not be relied on together with this hook unless verified on the installation. The `reason` is a fixed sentence and does not quote the command.
- Limit: commands run in a fresh child shell under the wrapper. A command sent to a persistent terminal (`RunPersistent`, `RequestedTerminalID`) no longer changes that shell's state (`cd`, environment variables, virtual environment activation), and a long-running process started this way ends at the wrapper's default deadline of two hours (`PROCESS_GUARD_AUTO_TIMEOUT`).
- A tool whose name is a string other than `run_command` is allowed without change. A payload without a `toolCall` object that has a string `name` is an unrecognised shape and is denied. Only the plain space, tab, carriage return and line feed characters around a line count as separators when the hook decides whether it is already in the wrapper form; a line with any other whitespace around it (for example a no-break space) is wrapped again.
- The hook fails closed with `deny` for unreadable or invalid input, an unrecognised payload, a missing `CommandLine`, more than one key that is `CommandLine` in any letter case or a repeated `CommandLine` key (the host's choice between them is not documented), a missing `process-guard-auto.exe`, or an install path with characters outside `A-Z`, `a-z`, `0-9`, colon, slash, period, underscore and hyphen. It always exits with 0 and prints one JavaScript Object Notation (JSON) object, so every failure the hook detects is a decision. A hook that cannot start, exceeds its timeout or crashes is handled by the host in a way Google does not document; verify the installation.
- Limit: wrapping grows a command by about a third plus the wrapper path, and `cmd.exe` cannot run a line of more than 8191 characters. The hook denies a command whose rewritten line would exceed 8000 characters, about 6,000 bytes of the original, with a reason that tells the agent to write the long content to a file and run the file. A PowerShell command fails above roughly 12,000 characters in any case, because the wrapper encodes it a second time to start PowerShell.
- Limit: a host that runs the rewritten line with `powershell -Command LINE` and no explicit `exit` reads exit code 1 for any non-zero exit of the wrapper, the deadline code 124 included; the deadline is still reported as `PROCESS_TIMEOUT` on standard error. Appending `; exit $LASTEXITCODE` restores the exact code. Git Bash and `cmd` report it exactly.
- Limit: the wrapper detects the shell from the process that starts it. PowerShell and `cmd` are recognised; any other parent runs the command in Git Bash, which must be installed at `C:/Program Files/Git`. The behaviour was verified with each shell as the direct parent; Google does not document which shell `run_command` uses on Windows.
- `hook antigravity-context` prints `POLICY.md` as a SessionStart system message.
- `examples/antigravity/hooks.json` is a complete hook configuration.
- 24 new checks (A1 to A24) in `tests/antigravity.rs`, including the rewritten command run in PowerShell, Git Bash and `cmd`. These tests need a temporary or build scratch folder whose path uses only `A-Z`, `a-z`, `0-9`, colon, slash, period, underscore and hyphen, and stop with a message otherwise.
