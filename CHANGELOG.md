# Changelog

## 2.0.0-alpha.2

The engine moves into a library and the crate builds three programs. The behaviour of the full command is unchanged, apart from the correction named under Layouts below (the policy file named in the denial text), and so is every alias path. The shell the guard chooses for `--shell` is found as in 1.x.

- Library: the engine is the crate `process_tree_guard`, in `src/lib.rs` with modules for the system calls, the Base64 codec, the command line forms, the engine and the hook (`src/hook.rs`). The public interface is small: `run`, `run_shell`, `run_auto` and `run_hook`; the entry points `main_full`, `main_deadline` and `main_gate`; `GuardError`; `Shell`; and `MAX_SECONDS`.
- Programs: `process-tree-guard` is the full command and runs every mode in its own process, with no extra process hop. `process-tree-guard-deadline` is the deadline role (the `--timeout` form and automatic mode, with no hook mode). `process-tree-guard-gate` is the hook role: it takes the same vendors and formats as `process-tree-guard hook VENDOR`, and reads `pretooluse` when no vendor is given; it differs in the envelope set it accepts, the automatic copy it rewrites to, and `-h` and `--help` (see Layouts below). Each is a thin `main` over the library.
- Dispatch by program name stays: any name ending in `-auto` selects automatic mode in the full command and in the deadline role, and `process-guard.exe` and `process-guard-auto.exe` remain identical aliases of `process-tree-guard.exe` and `process-tree-guard-auto.exe`.
- Library owner rule, documented: a library call watches the calling process's parent (every live ancestor, for `run_auto`), so a call whose parent has already exited is an error (the Windows error 87 text, as in 1.x), or returns 125 at once. The behaviour is as before.
- Layouts: files found beside a program (the automatic copy a hook rewrites to, `POLICY.md` one folder up) are found relative to `std::env::current_exe` only, never through `PATH` or the current folder (Common Weakness Enumeration, CWE-427). The install layout (`bin` and `libexec`) and the flat layout (every program in one folder) both work. The gate rewrites to `process-tree-guard-deadline-auto.exe` in its own folder and accepts an envelope that names a program that enforces a deadline in its own folder or in the `bin` folder beside `libexec` (a folder named `libexec` in any letter case, as Windows folder names are not case sensitive); it never accepts an envelope that names itself, in whatever letter case it was started. The role of a program decides these rules, not its file name: the gate keeps them under any file name, and the full command keeps the rules of its own name under the gate's. The denial text names the policy file one folder above the program's folder, the file that the session context reads, whatever the folders are called.
- Shell hosts, unchanged: `--shell powershell` runs the `pwsh.exe` that the `PATH` search finds, otherwise `powershell.exe`; `--shell cmd` runs the program named by `COMSPEC`, otherwise `cmd.exe`; both are found as the program the guard is asked to run is, with the current folder first unless `NoDefaultCurrentDirectoryInExePath` is set. The README and `SECURITY.md` say so.
- Version resources: `build.rs` writes a version resource for each program with no new crates (file description "Process Tree Guard", "Process Tree Guard: Deadline" or "Process Tree Guard: Gate"; product name; file and product version; copyright; original file name; no company name) and links it with `cargo:rustc-link-arg-bin`. Only the Microsoft Visual C++ (MSVC) target is supported; the GNU's Not Unix (GNU) target is unsupported and builds without them. The check G39 prints a `NOTICE` line to standard error, which a plain `cargo test` shows, on a build without them, and fails instead when `CI` or `PROCESS_TREE_GUARD_REQUIRE_RESOURCES` is set, and the continuous integration and release workflows print the description of each built program.
- Releases attach `process-tree-guard.exe`, `process-tree-guard-deadline.exe` and `process-tree-guard-gate.exe`, and through all of 2.x also `process-guard.exe` as an alias asset, all listed in `SHA256SUMS`. The release asset check is an allow-list of exactly these files and the documentation files.
- Documentation: `SECURITY.md` states that pass-through of the other family's wrapper form does not check that the file exists, and that this fails closed. The README states that an empty `PROCESS_TREE_GUARD_AUTO_TIMEOUT` shadows the older names and fails with exit code 125.
- Documentation, library: a library call runs the command with the caller's standard input, output and error handles, and its `PROCESS_TIMEOUT` and `PROCESS_OWNER_EXITED` notices go to the caller's standard error; the library documentation and the README now say so. The gate's usage text and the README list the `powershell-auto` vendor. The library documentation and the README also say that the command inherits every inheritable handle of the caller, not only the three standard ones, and what an embedder should do about it.
- Hook `powershell-auto`, documented: it names the automatic copy in its rewrite without testing that the file exists, so with the copy missing the rewritten line runs nothing and the host may read that as success. The README and `SECURITY.md` say so, and U22 checks it for the full command and the gate in both layouts. The behaviour is as before.
- Gate usage: `process-tree-guard-gate -h` and `--help`, as the first argument, print the gate's usage and exit 0 without reading standard input. Any other first argument is a vendor name, as in `process-tree-guard hook`; read as one, the help flag would make the gate wait for a payload. The gate has no other options.
- Tests: the tests take every program from the binaries cargo built in the run (the paths cargo records in `CARGO_BIN_EXE_*`), never by a file name in the build folder, so a stale `process-guard.exe` left there is never picked up; G41 checks that the recorded files are the ones in use and that no test source contains the literal path of the build folder. 35 new checks: G35 to G49 (the deadline role in both layouts, including its owner rule; the version resources; the programs under test; the library's four calls, their errors and their owner rule), U19 to U22 (the deadline role in automatic mode, its deadline variables, the gate's PowerShell hook, the hook with the automatic copy missing), B123 to B131 (the gate's envelope check, denials, equality with `hook`, denial text, context, the policy path under unusual folder names, the hook role and the full command under each other's file names, the library when its parent has exited, the gate's usage text) and A33 to A39 (the gate's Google Antigravity hook in both layouts, decoy files on `PATH` and in the current folder never used, end to end, session context, the rules following the role under another file name). Every existing check passes unchanged. G42 checks the shell hosts against controls in which no helper copy is reachable, B123 also covers the gate started through a `libexec` folder spelled in capitals, and G44 prints its identifier with PASS or FAIL like the other grouped checks.

## 2.0.0-alpha.1

The project and the program are renamed from process-guard to process-tree-guard. This is the first step toward 2.0.0; behaviour is otherwise unchanged.

- The package and the primary executable are `process-tree-guard`. Its automatic mode is the same executable under a name ending in `-auto`, as before: `process-tree-guard-auto.exe`.
- Compatibility aliases, kept through all of 2.x and removed in 3.0: the same executable installed as `process-guard.exe` or `process-guard-auto.exe` behaves identically to the new names. The name is the only thing read, so a name ending in `-auto` selects automatic mode under either family.
- Every `hook` subcommand works under both names. The envelope check accepts an envelope that names the executable it runs from or the same executable under its other name in the same folder. `hook antigravity` wraps with the automatic copy of its own name family (`process-tree-guard-auto.exe` for `process-tree-guard.exe`, `process-guard-auto.exe` for `process-guard.exe`; any other file name keeps the 1.x behaviour and uses `process-guard-auto.exe` alone), requires that copy to be present, and passes through unchanged a line already in the wrapper form of either family or already a valid envelope of either name.
- The automatic deadline is read from `PROCESS_TREE_GUARD_AUTO_TIMEOUT`, then `PROCESS_GUARD_AUTO_TIMEOUT`, then `HARNESS_AUTO_TIMEOUT`; the first one that is set is used. The tests read `PROCESS_TREE_GUARD_TIMING`, then `PROCESS_GUARD_TIMING`, and `PROCESS_TREE_GUARD_EXE`, then `PROCESS_GUARD_EXE`, in the same way.
- Unchanged: the deadlines, the 86400 second `--timeout` maximum, exit codes 124 and 125, containment, every existing check, and the messages on standard error (`PROCESS_TIMEOUT`, `PROCESS_OWNER_EXITED`, the `PROCESS_GUARD_ERROR` prefix and the hook denial text). The only wording that changes is the program name in the `--help` usage line.
- Releases attach the one executable `process-tree-guard.exe`, with its documentation files (`LICENSE`, `NOTICE`, `README.md` and `POLICY.md`) and `SHA256SUMS`; the test helper is not part of a release, and the release workflow stops if it is.
- 24 new checks: G29 to G34 (both binary names, and the order of the timing variables), U14 to U18 (both automatic names, the `auto` subcommand, the order of the deadline variables, the PowerShell hook under both names), B117 to B122 (hook mode under both names, and its denial text) and A26 to A32 (the Google Antigravity hook under both names, and under another file name). The existing checks run against the new names.

## 1.5.1

- `hook antigravity` also denies a payload with more than one `toolCall` key, or a `toolCall` object with more than one `name` or `args` key, in any letter case or repeated (check A25). Before, the hook read the last exact match, and a host that chose another candidate could run a command the hook had not checked. The rule applies whatever tool the payload names.

## 1.5.0

Google Antigravity support (integrated development environment, App and command-line interface).

- `hook antigravity` is a PreToolUse hook for the `run_command` tool. It rewrites `CommandLine` to a call to `process-guard-auto.exe` in the guard's own folder, so every shell command runs under an automatic deadline and process tree cleanup. A command that already has exactly that form, or is a valid guard envelope, passes through unchanged.
- The hook answers with `allow`, never `auto_approve`, so it does not bypass the user's own review settings. Limit: review prompts and command-text allow or deny lists may see the Base64 form (`process-guard-auto.exe --command-b64 BASE64`) instead of the original command, so an approver cannot read it and a pattern such as `rm -rf` may not match. Google does not document whether policy is evaluated before or after the rewrite, so command-pattern deny lists should not be relied on together with this hook unless verified on the installation. The `reason` is a fixed sentence and does not quote the command.
- Limit: commands run in a fresh child shell under the wrapper. A command sent to a persistent terminal (`RunPersistent`, `RequestedTerminalID`) no longer changes that shell's state (`cd`, environment variables, virtual environment activation), and a long-running process started this way ends at the wrapper's default deadline of two hours (`PROCESS_GUARD_AUTO_TIMEOUT`).
- A tool whose name is a string other than `run_command` is allowed without change. A payload without a `toolCall` object that has a string `name` is an unrecognised shape and is denied. Only the plain space, tab, carriage return and line feed characters around a line count as separators when the hook decides whether it is already in the wrapper form; a line with any other whitespace around it (for example a no-break space) is wrapped again.
- The hook fails closed with `deny` for unreadable or invalid input, an unrecognised payload, a missing `CommandLine`, more than one key that is `CommandLine` in any letter case or a repeated `CommandLine` key (the host's choice between them is not documented), a missing `process-guard-auto.exe`, or an install path with characters outside `A-Z`, `a-z`, `0-9`, colon, slash, period, underscore and hyphen. It always exits with 0 and prints one JavaScript Object Notation (JSON) object, so every failure the hook detects is a decision. A hook that cannot start, exceeds its timeout or crashes is handled by the host in a way Google does not document; verify the installation.
- Limit: wrapping grows a command by about a third plus the wrapper path, and `cmd.exe` cannot run a line of more than 8191 characters. The hook denies a command whose rewritten line would exceed 8000 characters, about 6,000 bytes of the original, with a reason that tells the agent to write the long content to a file and run the file. A PowerShell command fails above roughly 12,000 characters in any case, because the wrapper encodes it a second time to start PowerShell.
- Limit: a host that runs the rewritten line with `powershell -Command LINE` and no explicit `exit` reads exit code 1 for any non-zero exit of the wrapper, the deadline code 124 included; the deadline is still reported as `PROCESS_TIMEOUT` on standard error. Appending `; exit $LASTEXITCODE` restores the exact code. Git Bash and `cmd` report it exactly.
- Limit: the wrapper detects the shell from the process that starts it. PowerShell and `cmd` are recognised; any other parent runs the command in Git Bash, which must be installed at `C:/Program Files/Git`. The behaviour was verified with each shell as the direct parent; Google does not document which shell `run_command` uses on Windows.
- `hook antigravity-context` prints `POLICY.md` as a SessionStart system message.
- `examples/antigravity/hooks.json` is a complete hook configuration.
- 24 new checks (A1 to A24) in `tests/antigravity.rs`, including the rewritten command run in PowerShell, Git Bash and `cmd`. These tests need a temporary or build scratch folder whose path uses only `A-Z`, `a-z`, `0-9`, colon, slash, period, underscore and hyphen, and stop with a message otherwise.
